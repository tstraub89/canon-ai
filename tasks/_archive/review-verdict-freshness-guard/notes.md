[spec_review] The proposed whole-file mtime/size fingerprint is weaker than verdict freshness: a partial findings edit can change the fingerprint while leaving the prior checked verdict extractable. The acceptance tests need this partial-write case, or the original counter-corruption path remains possible.

[spec_review] The current Claude runner exits the orchestrator on spawn/stall/non-zero/signal failures, and the dispatch loop records `lastCodexExitStatus = 0` for the Claude-owned code_review phase. Non-zero crash parking in `checkAndRoute` is therefore Codex spec_review behavior unless the adjacent wrapper-exit backlog item enters scope.

[spec] Revision round 1 — addressed both spec_review blockers by reshaping the design, not iterating the mechanism. (1) Freshness is now **verdict-scope invalidation** (positive per-invocation evidence): the orchestrator invalidates the authoritative verdict scope before dispatch so an extractable verdict at recovery proves this-invocation authorship — whole-file mtime/size is explicitly rejected. Added AC-1 (soundness property `extractCheckedVerdict(invalidate(x))===null`) and AC-2 (the reviewer's exact partial-write case). (2) Corrected the control flow in Problem: only a Codex **non-zero exit** returns to recovery (`codex.ts:127`); `runClaude` `process.exit`s on every failure and code_review forces `lastCodexExitStatus=0`, so the park branch is Codex-`spec_review`-only by construction — the freshness gate stays agent-agnostic and AC-6 tests the code_review clean-exit recovery path. Also verified build coupling: `dist/scripts/run-task.js` always regenerates; `dist/cli/index.js` only if the touched `validation.ts` code is CLI-reachable (esbuild tree-shakes — `verifyRerouteAmendment` is absent from today's cli bundle), so AC-11/Affected-Files no longer hard-claim both dist files change.

[spec_review] Revision round 2: `extractCheckedVerdict` accepts verdict-looking checkbox lines anywhere in its selected scope, including Findings; a fixture with an unchecked real Verdict section plus `- [x] Approved` under Findings returned `approved`. A sound invalidator cannot both preserve arbitrary non-verdict content and guarantee extraction returns null without first giving extraction/invalidation a shared structural verdict-section definition.

[spec_review] Revision round 2: invalidating the latest existing `## Round` / same-round `## Amendment Review` clears the last completed round before the reviewer appends the new cumulative section, erasing history that AC-1 and both append-style prompts say to preserve. Worktree routing also needs a dual-copy regression because a repo-root write would fail open.

[spec] Revision round 3 — REDESIGN, not mechanism iteration (>=3-iteration scope-expansion checkpoint).
Round-over-round: R1 rejected whole-file fingerprint (cannot prove *verdict* fresh); R2 rejected verdict-scope INVALIDATION on two structural grounds (extractCheckedVerdict has no ## Verdict-section locator, so AC-1 is impossible; invalidating the latest scope destroys completed-round history). Both R1/R2 blockers share one root: any IN-BAND freshness mechanism fights the loose parser grammar + the append-only-history contract. Chasing maximal in-band soundness is what expanded scope each round.
Pivot: DROP in-band freshness entirely. The confirmed bug (Codex spec_review out-of-credits crash, exit 1, returns via codex.ts:127) is fixed soundly by a FAIL-CLOSED park: in checkAndRoute the not-done block, before recoverPhaseForTask, if phase===spec_review and lastCodexExitStatus!==0 -> actionable error + process.exit(2), no retry, no verdict read, no counter increment. Codex-spec_review-only by construction (main.ts:3454 forces lastCodexExitStatus=0 for Claude phases; runClaude process.exits on crash so code_review never reaches recovery non-zero). This writes NOTHING to any artifact, so all three R2 concerns (grammar/AC-1, history destruction, worktree dual-copy) EVAPORATE by construction.
Deliberate tradeoff for the human_spec_gate: a genuine verdict + non-zero exit (MCP noise) + skipped self-bookkeeping now PARKS (manual re-run) instead of the old optimistic auto-advance. That optimism was never sound (cannot tell completion+MCP-warning from crash-with-stale-verdict = the bug). General in-band freshness (to preserve that sub-case) requires first tightening extractCheckedVerdict to a structural verdict-section locator (a load-bearing symbol shared by checkPhaseGate + reroute) -> deferred follow-up.
