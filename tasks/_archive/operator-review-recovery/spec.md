## Problem

Canon has no coherent, audited way for an operator to recover from an agent review they disagree with or that requires a spec change. Two concrete gaps, both confirmed live this cycle on the `upgrade-template-override-nudge` task:

1. **spec_gap recovery is a weaker parallel path than reroute.** When `code_review` returns `spec_gap`, the sanctioned recovery (printed by the orchestrator at `scripts/run-task/main.ts:2806-2814`) is: amend `spec.md` → `canon task phase <id> code_review pending` → `canon run`. That routes straight back into `code_review` — the amendment gets **no Codex spec-lens** and `plan.md` is **not refreshed**. Meanwhile `rerouteFromHumanReview` (`main.ts:2096-2238`) already does all of that (spec_review re-entry, plan refresh, session reset) but is **hard-guarded to `human_review`** (`main.ts:2099`), so it can't be used here.

2. **The spec_gap recovery never increments `reroute_count` → a later reroute collides.** Because recovery routes through `code_review pending` (not `--reroute`), `reroute_count` stays 0 while the operator adds a `## Amendment` heading. A subsequent legitimate `--reroute` then computes `requiredRound = (reroute_count ?? 0) + 1 = 1` (`main.ts:2112`), and the round-1 branch of `verifyRerouteAmendment` (`validation.ts:312-313`) matches that **stale** `## Amendment` instead of requiring a fresh one. We hit this and worked around it by hand-editing `reroute_count`.

3. **No audited override exists for a wrong review.** When a `code_review` `spec_gap` is a false positive, or a `spec_review` `changes_requested` is too nitpicky / factually wrong, the operator's only force-through is `canon task phase <id> <phase> done approved` — which leaves **no paper trail** (no reason, no record of who/why). The one existing audited override, `canon task accept` (`src/task/index.ts`), is hard-scoped to the `implement` phase.

See `docs/BACKLOG.md` → "`code_review` `spec_gap` recovery skips spec_review re-validation and plan refresh — asymmetric with `human_review` reroute" for the full write-up.

## Decision

Unify operator recovery from agent reviews around the two existing, battle-tested mechanisms instead of the weak parallel path:

- **Fix path** — allow `canon run --reroute` from a `code_review` blocked with a `spec_gap` verdict (in addition to `human_review`). It runs the full `rerouteFromHumanReview` machinery, so the amendment is re-validated by Codex spec_review, the plan is refreshed, and `reroute_count` is incremented — which structurally closes the desync (problem 2).
- **Bless / override path** — generalize `canon task accept` from `implement`-only to also accept `spec_review` and `code_review`, with a **mandatory `--reason`**. It sets a new, distinct verdict `sanctioned`, writes the existing `operator_accepted` audit fields, appends an audit line to `notes.md`, and advances the phase — sanctioning the work as-is for a false-positive or trivial review, with a durable paper trail. Like the fix path, it is **bundle-aware**: `canon task accept` already accepts multiple task IDs (`taskAccept(ids: readonly string[], …)`, `src/task/index.ts:551`), so a mixed blocked bundle is recovered as a unit by naming every blocked member — no sibling is stranded (AC-15). It differs from the fix path on sibling verdicts: the reroute reset discards every member's verdict (the tree is re-implemented), but the bless ships the tree as-is, so a member that already carried an **advancing** verdict (`approved`/`approved_with_nits`) keeps it and is merely unblocked, while only members carrying a **non-advancing** verdict (`spec_gap`/`changes_requested`/`needs_re_review`/empty) are relabeled `sanctioned`. This keeps the audit trail truthful — an honest approval is never overwritten as an override.

The operator chooses fix vs. bless; canon does not auto-classify. The two paths preserve this **invariant**: *a `## Amendment [Round N]` heading exists in `spec.md` iff a reroute incremented `reroute_count`*. The fix path adds an amendment and bumps the count together; the bless path adds no amendment and does not touch the count. The recovery message stops recommending the unaudited `canon task phase … done approved`.

**`sanctioned` is mint-by-accept-only** (resolves the spec-review Shape Check). `sanctioned` is a valid verdict *value* on every value surface — so a `status.json` carrying it loads and validates — but the **only** way to set it is `canon task accept <id> <phase> --reason`. The low-level `canon task phase <id> <phase> done sanctioned` is **rejected** with a message pointing at `canon task accept --reason`. Therefore a `sanctioned` verdict in `status.json` *always* implies the `operator_accepted*` audit fields and the `notes.md` audit line — the paper trail can never be absent. The accept path writes `status.json` directly (exactly as the existing `implement`-accept does at `src/task/index.ts:798-800`) and does **not** run the phase-close artifact-verdict gate (`checkPhaseGate` → `verdictMustMatchArtifact`, `scripts/run-task/validation.ts:966-983`); the review artifact (`review.md` / `spec-review.md`) legitimately keeps the agent's *original* verdict (`spec_gap` / `changes_requested`) as the historical record, and the sanction lives in the audit fields + the notes line. No `Sanctioned` artifact checkbox is introduced and the verdict-match gate is not special-cased — it is simply off the accept path. This is one of the two resolutions Codex's spec review named; we take the accept-only branch because it keeps the audit-trail guarantee that motivates the whole task.

## Non-Goals

- **No auto-classification of bless vs. fix.** The operator decides which path; the spec_gap block presents both. We are not adding heuristics to guess intent.
- **No change to `implement`-accept semantics.** `canon task accept <id> implement` keeps its current behavior (auto-commit skip, optional reason, SHA pin). This task only *extends the command's accepted phase set*; it does not alter the implement path.
- **The low-level `canon task phase <id> <phase> <status> [verdict]` escape remains** for the pre-existing verdicts. It is not removed and not hardened against the desync — it is a deliberate low-level tool. This task only redirects the *recommended* spec_gap recovery away from it toward the two audited paths. The **one** carve-out: the brand-new `sanctioned` verdict may **not** be set through `canon task phase` (it is accept-only by AC-8); this is not a removal of the escape but a property of the new verdict — every verdict that exists today still works exactly as before through `canon task phase`. Hardening `canon task phase` itself against the `reroute_count` desync is out of scope.
- **Full-send `spec_gap` auto-amend stays a separate BACKLOG item.** This task is operator-driven recovery only; it does not add any automated amendment drafting under `full_send`.
- **No new top-level command.** Reuse `canon run --reroute` and `canon task accept`; do not introduce a parallel `canon sanction`/`canon override` surface.

## Acceptance Criteria

### Fix path — `--reroute` from spec_gap

- [ ] **AC-1** (relaxed precondition, bundle-aware): `rerouteFromHumanReview` (`main.ts:2096`) accepts an invocation when **either** (i) every task's current phase is `human_review` (unchanged), **or** (ii) every task is at `code_review` with `status === 'blocked'` **and at least one** task in the invocation has `verdict === 'spec_gap'`. Any other combination still rejects with the existing `--reroute requires …` die message (updated to name the now-allowed spec_gap case). The two quantifiers are deliberate (and individually justified per the bundle-gate `every()`-vs-`some()` rule, `docs/patterns.md`): the **`every` blocked floor** is the safety guard — a single blocked+spec_gap task must not drag a sibling that is mid-`implement` or at another phase into a destructive reset; the **`≥1 spec_gap` trigger** is what justified blocking the bundle in the first place (the gap is unfixable from the implement side). A single-task invocation is a bundle of one, so it collapses to: the lone task must be `code_review` blocked+`spec_gap`. Verify (single-task cases here; bundle cases in AC-14): unit/subprocess tests — (a) `human_review` allowed; (b) lone `code_review` blocked+`spec_gap` allowed; (c) lone `code_review` blocked **without** `spec_gap` rejected; (d) `code_review` non-blocked rejected; (e) some other phase rejected.

- [ ] **AC-2** (full machinery runs): A `--reroute` from a spec_gap-blocked `code_review` performs the same generic resets as a `human_review` reroute — increments `phases.implement.reroute_count`, sets `implement.rerouted = true`, resets `implement`/`code_review`/`qa`/`human_review` to `pending`, and for a full-tier task resets `spec_review`/`plan` to `pending` and clears the `sessions.codex_spec_review` slot. (The spec_gap-specific entry-state clearing is verified separately in AC-13.) Verify: state assertions on a spec_gap-blocked fixture after `rerouteFromHumanReview` match the resets a `human_review` reroute produces.

- [ ] **AC-3** (desync closed at the root): After a `--reroute` from spec_gap, the amendment-round numbering is consistent — `verifyRerouteAmendment` requires `## Amendment` for the first reroute (when `reroute_count` was 0 at pre-flight) and `## Amendment Round N` for the Nth, and a stale heading from a prior round can never satisfy a later round's requirement. Verify: a test that drives spec_gap → `--reroute` (round 1) → `human_review` → `--reroute` (round 2), asserting the required heading is bare `## Amendment` then `## Amendment Round 2`, and that a leftover bare `## Amendment` does **not** satisfy the round-2 pre-flight.

- [ ] **AC-4** (recovery message rewrite — both surfaces): Both the console block printed when `code_review` returns `spec_gap` (`main.ts:2801-2816`) **and** the `reason` string persisted into the escalation via `autoBlockPhase` (`main.ts:2796-2800`) present exactly the two audited paths: (a) **fix** — amend `spec.md` with a `## Amendment` heading, then `canon run <ids> --reroute`; (b) **bless/override** — `canon task accept <ids> code_review --reason "<why>"`. Because the `spec_gap` block blocks the *whole* bundle (AC-14), **both** recovery commands must name the full set of blocked task IDs in the invocation (`taskIds`), **not** only `specGapIds` — instructing the operator to reroute/accept only the gap task would strand a blocked sibling (AC-14 fix-side, AC-15 bless-side). Both surfaces currently recommend `canon task phase <id> code_review pending` (the unaudited weak path) — that recommendation must be removed from **both** the printed block and the persisted `reason`. Neither may instruct `canon task phase <id> code_review pending` or `… done approved` as the recommended recovery. Verify: capture the printed block and the stored escalation `reason` in a test; assert each contains `--reroute` and `canon task accept` with `code_review` + `--reason`, that both commands list the full blocked-bundle IDs (in a 2-task fixture), and assert the absence of the `code_review pending` / `done approved` recommendation in each.

### Bless/override path — `canon task accept` for review phases

- [ ] **AC-5** (phase set + mandatory reason, bundle-aware): `canon task accept <id...> <phase>` accepts `phase ∈ {implement, spec_review, code_review}` (previously `implement` only) and **one or more** task IDs (the command is already multi-ID for `implement`; the review-accept path inherits that). For `spec_review` and `code_review`, `--reason "<text>"` is **required** — the command exits non-zero with a clear message if it is missing or empty; the single `--reason` applies to every task in the invocation (one operator decision over the shared bundle, mirroring how `implement`-accept pins one shared SHA across the bundle). For `implement`, `--reason` remains optional (behavior unchanged). Verify: `accept code_review` with no `--reason` errors; with `--reason` succeeds; `accept spec_review` likewise; a two-ID `accept A B code_review --reason` recovers both — advancing each to `qa` with per-task verdicts per AC-15 (gap member → `sanctioned`, already-approved member preserved); `accept implement` still works with no reason.

- [ ] **AC-6** (sanction + advance, from blocked or verdicted state): Accepting a single `spec_review` or `code_review` (the task being overridden necessarily carries a non-advancing verdict — `spec_gap`/`changes_requested`/`needs_re_review`/empty — an already-advancing phase wouldn't be blocked) sets that phase `status = done` with `verdict = sanctioned` (the bundle case, where a *sibling* may carry an advancing verdict to preserve, is AC-15) (written directly, **without** invoking `checkPhaseGate` — the accept command is the authorized override, so the artifact-verdict-match gate is not on its path), and re-derives the top-level `status` pointer to the next phase so the next `canon run` dispatches forward. It works whether the phase is currently `blocked` (spec_gap / auto-blocked) or carries a normal verdict (e.g. `spec_review` `changes_requested`). On the next `canon run`, the pipeline advances (`spec_review` → `plan`; `code_review` → `qa`) and does **not** re-run the sanctioned phase nor re-fire the `spec_gap` block. Verify: from a `code_review` spec_gap-blocked fixture, `accept … code_review --reason` → phase `status` `done`, `verdict` `sanctioned`, top-level `status` pointer `qa`; one dispatch step from that state routes to `qa` without re-entering `code_review`. Same shape for `spec_review` `changes_requested` → `plan`.

- [ ] **AC-7** (durable paper trail): A `spec_review`/`code_review` accept appends an audit line to `tasks/<id>/notes.md` recording the date, the phase, that it was an operator sanction over the agent verdict, and the verbatim `--reason` text; and sets `operator_accepted = true`, `operator_accepted_at`, and `operator_accepted_sha` on the phase entry. The pre-existing `escalations[]` entry (if the phase was auto-blocked / spec_gap-blocked) is **left intact** — the audit record is "spec_gap fired, then operator sanctioned," not erased. Verify: after accept, `notes.md` contains a line with the phase + reason text; `status.json` phase entry has the three `operator_accepted*` fields populated; and any prior `escalations[]` entry for that phase is still present.

- [ ] **AC-8** (distinct verdict value, mint-by-accept-only): A new verdict value `sanctioned` is recognized on every **value** surface: the `_VERDICT_VALUES` array that derives the `Verdict` union (`scripts/run-task/types.ts:18`), `VALID_VERDICTS` + the `assertValidVerdict` error-message string (`src/task/index.ts:19,344`), the CLI help/verdict list (`src/cli/index.ts`), and the `_verdict_values` help string in the scaffolded status template (`.canon/templates/status.json:52` + its `templates/` mirror). `assertValidVerdict` accepts `sanctioned` **only** for `spec_review`/`code_review` — the existing `REVIEW_PHASES` guard (`src/task/index.ts:340-341`) already rejects *any* verdict on non-review phases, so `sanctioned` needs **no** per-phase special-case (unlike `spec_gap`). **`sanctioned` is mintable only via `canon task accept`**: the low-level `canon task phase <id> <phase> done sanctioned` is **rejected** with a message directing the operator to `canon task accept <id> <phase> --reason` (so the `sanctioned` verdict can never exist without its `operator_accepted*` + `notes.md` paper trail). `extractCheckedVerdict` (`scripts/run-task/validation.ts:864`) is intentionally **not** modified — `sanctioned` never appears as a review-artifact checkbox (it is status-only; see Decision), so teaching the artifact parser to recognize it would be dead, misleading code. Verify: (a) `canon task accept <id> code_review --reason "x"` yields `verdict: sanctioned` in `status.json`; (b) `canon task phase <id> code_review done sanctioned` is rejected with a message naming `canon task accept --reason`; (c) `canon task phase <id> plan done sanctioned` is rejected by the existing review-phase guard; (d) a drift-guard test asserts `sanctioned` appears in the `_VERDICT_VALUES`-derived value list, `VALID_VERDICTS`, the CLI help, and the status-template `_verdict_values` string — deriving the human-readable strings from the single `_VERDICT_VALUES` source where practical, rather than duplicating the literal (per `docs/lessons-learned.md`).

- [ ] **AC-9** (routing treats `sanctioned` as advance): `checkAndRoute`/dispatch advances on a `sanctioned` verdict exactly as on an approval — `spec_review` `sanctioned` → `plan`; `code_review` `sanctioned` → `qa` — and the `spec_gap` block (`main.ts:2792`) does not fire when the `code_review` verdict is `sanctioned`. Verify: routing tests for both phases; a test that a `sanctioned` code_review does not trigger the spec_gap escalation.

### Cross-cutting

- [ ] **AC-10** (invariant holds): A `spec_review`/`code_review` accept makes **no edit to `spec.md`** (adds no `## Amendment` heading) and does **not** change `phases.implement.reroute_count`. Together with AC-2 (reroute is the only sanctioned path that adds an amendment, and it bumps the count), this preserves the invariant *`## Amendment [Round N]` exists iff `reroute_count` was bumped*. Verify: snapshot `spec.md` byte-content and `reroute_count` before/after an accept and assert both unchanged.

- [ ] **AC-11** (stale sanction cleared on reopen): When a sanctioned `spec_review`/`code_review` phase is later reopened (by `--reroute` or `canon task phase <id> <phase> pending`), its `operator_accepted*` fields and `sanctioned` verdict are cleared, so a stale sanction can never mask a fresh review. Verify: sanction `code_review`, then reroute → assert `operator_accepted*` removed and verdict reset to `''`; same for `canon task phase … pending`. (Generalizes the existing `clearImplementOperatorAcceptance` behavior to review phases.)

- [ ] **AC-12** (docs + BACKLOG close-out): `AGENTS.md`, `CLAUDE.md`, and `docs/pipeline-orchestrator.md` document (a) `--reroute` is allowed from a `code_review` spec_gap, (b) `canon task accept` covers `spec_review`/`code_review` with a mandatory `--reason` and the `sanctioned` verdict, and (c) the fix-vs-bless recovery taxonomy. The corresponding `docs/BACKLOG.md` entry is marked resolved. Verify: `npm run sync-templates:check` and `npm run docs-refs-check` pass; the docs name the new flows and the `sanctioned` verdict.

- [ ] **AC-13** (clean spec_gap-entry-state reset — no half-reset wedge): This is the *novel, delicate* part of the fix path, split out from AC-2 for dedicated verification. After a `--reroute` from a `code_review` that was `blocked` with verdict `spec_gap`, the post-reroute `code_review` entry has `status === 'pending'` and `verdict === ''` (no residual `blocked` status, no residual `spec_gap` verdict) and its `iterations_current_loop`/`preflight_rejections_current_loop` are `0`, so the task neither wedges nor re-fires the spec_gap block on the next `canon run`. Verify: a test that reroutes from a spec_gap-blocked fixture and asserts the exact post-state of the `code_review` entry (pending, empty verdict, zeroed loop counters), then drives one dispatch step and asserts it routes into `spec_review` (full tier) rather than re-entering or re-blocking `code_review`.

- [ ] **AC-14** (mixed-bundle spec_gap recovery — no stranded sibling, *fix* path): The `code_review` `spec_gap` handler **intentionally blocks the entire bundle**, not only the gap tasks — `autoBlockPhase(taskIds, …)` (`main.ts:2817`) stays scoped to the full `taskIds`, **not** narrowed to `specGapIds`. This is correct because bundle members share one branch, one commit history, and one review loop: an `approved` sibling must not advance to `qa` while a rerouted gap task is about to force a re-implementation of the shared tree (that would ship a review of code that is about to change). Recovery therefore reroutes the **whole** bundle together — `canon run <all-ids> --reroute` is accepted by AC-1 (ii), and the existing reset loop (`main.ts:2154-2222`, which already iterates every `taskId`) resets **every** member's `code_review` to a clean `pending`/`''` with zeroed loop counters, **including** a sibling that was `blocked` while carrying a non-gap verdict (`approved`/`changes_requested`/`needs_re_review`/empty — `autoBlockPhase` sets `status='blocked'` but leaves `verdict` untouched, confirmed at `state.ts:204-206`). No member is stranded and none keeps a stale verdict. A bundle where **not every** member is `code_review` blocked (e.g. one task still at `implement`) is rejected by AC-1's `every`-blocked floor, so a sibling at a wrong phase can never be swept into a reset. Verify: a 2-task bundle fixture — (a) A=`code_review` `blocked`+`spec_gap`, B=`code_review` `blocked`+`approved`: `rerouteFromHumanReview(['A','B'])` is accepted, and post-reroute **both** A and B have `code_review.status === 'pending'`, `verdict === ''`, and zeroed `iterations_current_loop`/`preflight_rejections_current_loop`; (b) A=`code_review` `blocked`+`spec_gap`, B=`implement` `pending`: `rerouteFromHumanReview(['A','B'])` is rejected with the `--reroute requires …` die message and neither task's status is mutated.

- [ ] **AC-15** (mixed-bundle spec_gap recovery — no stranded sibling, *bless* path; symmetric with AC-14): The bless path is bundle-aware so a mixed blocked bundle is recovered as a unit, with no sibling stranded — but, **unlike** the fix path (which discards every member's verdict on reset because the tree is re-implemented), the bless path **preserves a genuinely-approved sibling's verdict** (the tree ships as-is, so an honest `approved` should stay `approved`, not be relabeled an override). Per-task rule, applied to **every** named member of `canon task accept A B code_review --reason "<why>"`:
  - a member carrying a **non-advancing** verdict (`spec_gap` / `changes_requested` / `needs_re_review` / empty) → `verdict = 'sanctioned'` + populated `operator_accepted*` (the operator is overriding the agent here; the shared `--reason` records why);
  - a member already carrying an **advancing** verdict (`approved` / `approved_with_nits`) → verdict **preserved unchanged**; it was `blocked` only by the whole-bundle `autoBlockPhase` (AC-14), so it is simply **unblocked** (no `operator_accepted*` relabel — its review genuinely passed);
  - **every** named member: `status → 'done'`, top-level `status` pointer re-derived to `qa`, and a `notes.md` audit line appended recording the bundle bless + reason (so even a preserved-approved member's unblock is on the record). Prior `escalations[]` entries stay intact (AC-7).

  The existing bundle structural guards still apply (all tasks share `base_branch` and one working tree; prior phases complete) — but the **implement-only** git guards (non-empty `baseRef..HEAD` diff, handoff coverage, SHA-pin) do **not** run on the review-accept path (Known Risks). Because a partial bless strands the un-named sibling, AC-4's recovery message names the full blocked-bundle IDs. Verify: a 2-task fixture — (a) A=`code_review` `blocked`+`spec_gap`, B=`code_review` `blocked`+`approved`: `canon task accept A B code_review --reason "x"` → A `status === 'done'` + `verdict === 'sanctioned'` + `operator_accepted*` set; **B `status === 'done'` + `verdict === 'approved'` (preserved, NOT `sanctioned`) + no `operator_accepted*`**; both top-level pointers `qa`; both `notes.md` files gain the audit line; any prior `escalations[]` entries remain intact (AC-7); (b) the *partial* bless `canon task accept A code_review --reason "x"` (gap task only) leaves B at `code_review` `blocked` — documenting why AC-4's message lists every blocked ID, and matching the fix-path floor that recovery operates on the whole bundle.

## Known Risks

- **Delicate routing surface.** This changes `rerouteFromHumanReview` (a precondition every reroute hits) and `checkAndRoute` verdict handling (every review verdict). A bug mis-routes or corrupts state for every task that reaches a review. The delicate-review rule applies: audit *every* verdict branch when adding `sanctioned`, and verify the reroute resets are complete for the new spec_gap entry state (a half-reset `blocked`/`spec_gap` `code_review` would loop or wedge).
- **`sanctioned` slipping past a gate it shouldn't.** Because `sanctioned` routes like an approval, any verdict check that should treat it differently (e.g. a future gate that must distinguish a real pass from an operator override) needs to read the verdict, not just "did it advance." Mitigation: the distinct verdict (not reusing `approved`) means the override is always legible in `status.json`; AC-8 keeps it out of non-review phases.
- **Desync only fully closed for the *sanctioned* paths.** The invariant holds for `--reroute` (fix) and `accept` (bless). The low-level `canon task phase` escape can still add a `## Amendment` without bumping `reroute_count` (out of scope, Non-Goals) — so an operator who hand-resets and hand-amends could still desync a later reroute. Documented as a low-level-escape caveat, not a sanctioned flow.
- **Review-accept is a *distinct* code path from implement-accept — do not reuse implement's guards.** `taskAccept`'s existing guards (non-empty `baseRef..HEAD` diff, handoff path coverage, SHA-pin-to-skip-auto-commit) exist solely to protect `implement`'s auto-commit. A `spec_review` accept can run *before any implementation exists* (empty diff), and neither review phase auto-commits — so reusing those guards would wrongly reject a legitimate review sanction. The review-accept branch must require `--reason`, set `verdict = sanctioned` + `operator_accepted*` + the `notes.md` line + re-derive the top-level pointer, and skip the implement-only coverage/SHA guards. `operator_accepted_sha` on a review phase is a record-only HEAD pin (no demote-on-rerun meaning, since there is no auto-commit to skip). This is the single largest implementation footgun in the task.
- **Accept-from-blocked state + gate bypass.** Accepting a `blocked` (auto-blocked / spec_gap) phase is new. The transition must set the phase to `done`/`sanctioned` *directly* (the accept path does not call `checkPhaseGate`, so the artifact-verdict-match gate — which would otherwise reject because the artifact still shows `spec_gap`/`changes_requested` — never fires) and must not strand the `escalations[]` entry (the escalation should remain as the record that the spec_gap fired and was then sanctioned — paper trail, not an error).
- **Reason parsing.** `--reason "<text>"` with spaces/quotes must parse correctly and the verbatim text must reach `notes.md` without truncation or shell-mangling in the audit line.
- **Mixed-bundle reroute quantifiers.** The bundle-aware precondition (AC-1) deliberately mixes quantifiers: `every` task blocked (safety floor) AND `some` task `spec_gap` (trigger). Getting these backwards is the canonical bundle-gate footgun (`docs/patterns.md` "Bundle-gate conditions must use `every()`"): a `some`-blocked floor would let a single spec_gap task drag a mid-`implement` sibling into a destructive reset; an `every`-spec_gap trigger would reject the very mixed bundle this AC exists to support. The implementer must wire each quantifier as specified and a test must cover the off-phase-sibling rejection (AC-14 (b)). Keeping `autoBlockPhase` on the full bundle is load-bearing for this story — narrowing it to `specGapIds` would strand approved siblings at `done` on a tree about to be re-implemented (silent bundle-incoherence, not a loud failure).

- **Bless-path bundle symmetry (partial-bless stranding).** The bless path inherits `taskAccept`'s per-task loop, so it is bundle-capable for free — but the operator must name **every** blocked member, because a partial `canon task accept A code_review --reason` sanctions only A and leaves the blocked sibling B stranded at `code_review` (AC-15 (b)). This is *not* a code defect (accept correctly recovers exactly the tasks it's told — sanctioning the ones with a non-advancing verdict, preserving+unblocking the ones already approved); the mitigation is AC-4's recovery message, which prints the **full** blocked-bundle IDs in the bless command so the operator copies the complete set. The implementer must not "helpfully" auto-expand a single-ID accept to the whole bundle — that would silently advance tasks the operator didn't name, violating the audited-override contract. The guard against the *opposite* error (a task at the wrong phase being swept in) is the existing prior-phases-complete check, which rejects accepting `code_review` for a task whose `implement` isn't `done`.

## Human Test Plan

1. Run a task to a point where code review reports a spec problem (a "spec gap"). Read the on-screen recovery message.
2. **Expected**: the message offers exactly two clearly-labeled options — one to amend the spec and re-run the full review (for a real spec change), and one to sanction the code as-is with a required written reason (for a false alarm or trivial gap). It no longer tells you to reset the review phase by hand.
3. Take the **sanction** route: run the accept command for the review with a written reason.
4. **Expected**: the task moves forward to the next stage; the task's notes file gains a dated line recording that you overrode the review and *why* (your reason text); and the task's status shows the review as a distinct "sanctioned" outcome, not an ordinary approval. Try it without a reason — it should refuse.
5. Take the **fix** route on a different task: amend the spec, then run the reroute command from the spec-gap state.
6. **Expected**: the pipeline re-reviews your amended spec, re-plans, re-implements, and re-reviews — the same full path you'd get rerouting after final human review.
7. After that reroute, trigger a *second* reroute later and confirm the spec amendment heading it asks for is the next round number (no confusion with the earlier amendment).
8. Separately, on a task where the spec reviewer was overly picky, sanction the **spec** review with a reason.
9. **Expected**: the task advances past spec review to planning; the notes file records the override and reason.
10. If you ran two tasks together and the spec-gap stop blocked both of them, take the sanction route and name **both** tasks in the one accept command (with a reason).
11. **Expected**: both tasks move forward together — neither is left stuck behind. (The on-screen recovery message lists both task names in the commands it suggests, so you can copy the full set.)
