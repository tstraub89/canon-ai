# Spec: stable-validation-ids — Stable VAL-n validation IDs with exact-match gate + consolidated pre-flight

> Written by: Claude | Review by: Codex
> Status: draft

## Problem

The evidence gates pair the spec's `## Validation Required` items with the handoff's `## Validation Outcomes` rows by **canonicalizing prose**: `canonicalizeValidationCheck` (`scripts/run-task/validation.ts:94-131`) takes the first backtick span (else text before a dash separator), lowercases, and — when the result contains a space — keeps only the last word. Every new prose shape that violates those heuristics produces a false "required check missing from handoff" defect for a check that actually ran and passed.

**Confirmed mechanism (deterministic — fixed inputs hit the same wrong branch every run), verified by code reading against three live incidents:**

1. **Incidental-token capture** (2026-06-27, `add-xs-tier` implement, worked around by hand): the spec item `` Guidance-consistency gate (AC-18) — the Family A / B / D `rg` sweeps return zero matches `` canonicalizes to `rg` (first backtick span is a mid-sentence tool mention), while the handoff's natural Check label `Guidance-consistency gate (AC-18)` canonicalizes to `(ac-18)`. The keys can never pair; the gate stalls `implement`, and the one-shot retry re-fails because nothing tells Codex the gate wants the literal `` `rg` `` token first.
2. **Shared-key clobbering** ([#163](https://github.com/tstraub89/canon-ai/issues/163), gallery_wall `a-gallery-wall-task`, 2026-06-12): a required `` `npm run test:e2e` `` item and its optional `` `npm run test:e2e` with `@cross-browser` `` variant both canonicalize to `test:e2e` — the variant's *first backtick span* is the shared base command — and the last-writer-wins latest-outcome map lets the optional row's `not_configured` clobber the required row's `Pass`, blocking `implement` with a false "required check skipped" even though the required check passed.
3. **Class recurrence at an adopter** ([#200](https://github.com/tstraub89/canon-ai/issues/200)): "missing exact canonical labels in validation rows" forced multiple high-effort implement respawns for purely mechanical handoff-shape problems. This is the third occurrence; the 2026-05-11 canonicalizer patch (strip `npm run`, retry) fixed that day's trigger and not the class.

A second, independent defect compounds the cost: the implement-end evidence gate (`checkImplementEvidence`, `scripts/run-task/main.ts:2741-2766`) **short-circuits** — a malformed Changes-table path cell returns before `validateHandoffAgainstSpec` runs, so a handoff with two defects surfaces them one full Codex respawn at a time. (The `code_review` pre-flight already consolidates all defect classes into one report via `classifyPreflightBlockersFromData`; the implement-end seam is the straggler.)

Each false or serially-surfaced defect costs a full implement respawn (~10 minutes of high-effort Codex) that changes formatting, not code — and can drive the loop toward its auto-block cap with zero reviewer rounds.

Red-first regression tests are included: AC-11, AC-12, AC-13 (prose-matching and consolidation defects), AC-19 (two distinct informational checks whose labels collide under the *old* canonicalizer's last-word rule, so one state is lost pre-fix), and AC-21 (a blank-label informational row silently dropped by the pre-fix empty-`Check` skip, hiding a `Fail`/`human_pending`). AC-20 is a design-invariant guard, **not** red-first: same-label re-run override already works on current code, so it protects the new implementation against a per-row-synthetic-key regression rather than pinning a pre-fix failure. The mechanism is fully reproducible in unit fixtures, so no environment-bound escape applies.

## Decision

Replace prose-based validation matching with **stable per-check IDs**, and make the implement-end evidence gate report all deterministic defects in one pass.

1. **Spec side**: each `## Validation Required` item carries a stable flat ID: `- [x] VAL-<n>: <check description>` (`<n>` a positive integer; IDs unique within the spec, not required to be contiguous or ordered). The description keeps its current free prose — commands, predicates, annotations.
2. **Handoff side**: the `## Validation Outcomes` table (and each iteration `### Re-run validation` table) gains a leading `ID` column. A row answering a required check carries that check's `VAL-<n>`. The `Check` cell is **never matched against spec items** — required pairing is purely by `VAL-<n>`. (For informational rows the `Check` text still carries a bounded *within-handoff* identity role, defined in item 4 — that is the only remaining role of the cell text, and it never crosses the spec↔handoff boundary.)
3. **Matching**: the gates pair spec items to handoff rows by exact `VAL-<n>` ID (case-insensitive). Latest-outcome-per-*identity* override semantics across iteration re-run tables are preserved for both required rows (keyed by ID) and informational rows (keyed by label — item 4). `canonicalizeValidationCheck` is **deleted** — replaced by ID matching for required rows and label identity for informational rows, not retained as a fallback (hard cutover; settled with the operator 2026-07-19).
4. **Informational rows need no ID and stay individually trackable** (resolves the `spec_review` blocker; see `spec-review.md`). A `## Validation Outcomes` / `### Re-run validation` row with an empty ID cell (or `—`) is an informational/extra check — legal, and still subject to exactly the informational classifications it gets today: the non-required plain-`Fail` regression (which, as today, **exempts** `Fail – unrelated`) and `human_pending` counting toward the `human_review` gate. It gains no anti-laundering: the `Fail – unrelated` reference-requirement / changed-file check stays required-checks-only, exactly as today (AC-8). Two distinct informational checks never clobber each other's result, and a later re-run row can still override or clear an earlier informational result for the *same* check — the same latest-wins guarantee required rows get from their ID. **Required and informational rows never share an identity space**: an informational row never carries a `VAL-<n>`, and a `VAL-<n>` never identifies an informational row. A row with a *non-empty* ID that matches no spec item is a format defect (almost certainly a typo), reported with the spec's actual ID list. A row that cannot be identified at all (no ID and no usable stand-in identity) is a **format defect** (item 5) — reported, never silently dropped, because dropping it could hide a `Fail` or `human_pending`. The exact identification mechanism (what makes an informational row's identity, and why it can't reproduce the deleted canonicalizer's cross-artifact failure class) is in Implementation Notes — the binding contract is only the behavior above.
5. **Defect messages stay one-per-class** (per Validation Gate Discipline): missing required ID, unknown ID, duplicate ID in the spec, duplicate ID rows within one table, un-IDed checked spec items, and an **empty-label informational row** (empty ID cell *and* blank/whitespace-only `Check`) each get a distinct message naming the offending ID/line/row and the concrete fix (for the empty-label class: "give the informational row a non-empty `Check` label; if the row was meant to answer a required check, use that check's existing `VAL-<n>` ID and delete the mistaken informational row — do **not** invent a new `VAL-<n>` ID, which would only produce an unknown-ID or duplicate-row defect on the next run"). All are `format`-bucket ("Fix the handoff" / "fix the spec line") except where existing classes already route elsewhere.
6. **Both Validation Required parsers share the same ID grammar, not the same selection.** The gate parser (`parseValidationRequiredChecks`, `[x]`-only) and the implement-prompt preloader (`extractValidationChecks`, `[ ]`+`[x]`) keep their current, intentionally different checkbox semantics — the preloader legitimately surfaces unchecked candidate checks too; this task does not touch that. What they share is the `VAL-<n>:` ID grammar: wherever both parsers select the same checklist line (every `[x]`-checked item), they extract the identical ID for it. Both fail closed on spec ID-shape defects: the preloader's rejection fires during implement prompt build — **before an agent session is spawned** — so a malformed spec (un-IDed checked item, duplicate ID) costs zero agent runs, not one.
7. **Consolidated implement-end evidence note**: `checkImplementEvidence` runs all its deterministic checks (Changes-table shape, diff coverage inputs it already gathers, validation-outcome matching) and reports every defect in a single evidence note, mirroring the pre-flight's existing all-classes-in-one-report behavior.
8. **All outcome-state semantics are untouched**: `pending`/unfilled detection, required-check `N/A` rejection, `deferred_by_spec` citation requirement, `blocked` bucketing, `human_pending` soft-pass + `human_review` hard gate + waiver, the required-check `Fail – unrelated` reference + changed-file anti-laundering path (required-only, per item 4), the non-required plain-`Fail` regression, and predicate-gated skip recording all keep their current classifications and routes. Only the identity each keys off changes: required rows by `VAL-<n>` ID, informational rows by the non-ID identity from item 4 — never the canonicalized prose.

**Hard-cutover consequence (accepted)**: in-flight tasks whose spec/handoff predate the upgrade will fail the gate loudly with the un-IDed-item message, not silently mismatch. The release notes must tell adopters to drain in-flight tasks (or re-run `implement` after re-IDing the spec) before upgrading.

## Non-Goals

- **No AC-Coverage per-ID matching.** The AC gate (`checkAcCoveragePlaceholders`) keeps its current shape-only check; AC-IDs are the numbering precedent for VAL-n, nothing more. Backed by AC-14's unchanged-tests assertion.
- **No legacy prose-matching fallback or migration shim.** `canonicalizeValidationCheck` and its heuristics are deleted, not deprecated (AC-10's zero-match grep backs this). Adopter guidance is the release note, not code.
- **No lettered VAL scheme.** Flat `VAL-1` only — specs don't group validation checks into sections the way ACs sometimes are. A lettered ID is a format defect.
- **No changes to the Result enum or its semantics.** `N/A`, `not_configured`, `deferred_by_spec`, `blocked`, `human_pending`, `Fail – unrelated`, and pending-detection all behave exactly as today (AC-7).
- **No general handoff-schema validator.** The consolidated report covers today's existing defect classes plus the new ID classes — no new validation categories.
- **No cross-task ID uniqueness in bundles.** Matching stays per-task (per-task spec ↔ per-task handoff); `VAL-1` may exist in every bundle member.
- **No forced IDs on informational rows.** Informational/extra checks the implementer records but the spec never required are *not* assigned `VAL-<n>` IDs — their identity is their normalized `Check` label (Decision item 4). We deliberately do not make adopters invent and repeat IDs for throwaway extra checks, and we do not introduce a second informational-ID grammar.
- **No change to predicate-gating behavior** — a predicate-skipped check still writes its row (now with its ID) and a documented skip in Notes.

### Interaction Dependencies

- **`canon task phase <id> implement done` accept path** (`src/task/index.ts`): calls `parseHandoffChangesRows` + `verifyHandoffAgainstDiffFromData` but not the validation-outcome matcher — unaffected by the ID change beyond the rebuilt bundle. AC-10's grep confirms no hidden `canonicalizeValidationCheck` import.
- **Bundle mode**: `classifyPreflightBlockers` already runs per-task with that task's own spec+handoff; only `verifyHandoffAgainstDiff` is bundle-wide. IDs are per-task; no bundle changes.
- **`checkPhaseGate('human_review')`** consumes `countHumanPendingChecks` → `computeLatestValidationResults`; keying by ID must not change its human_pending count or waiver behavior (AC-7).
- **Predicate gating** (`buildAffectedFilesBlock` guidance in `prompts/index.ts`): behavior unchanged; skipped rows carry IDs (AC-9).
- **The two-parser seam**: `parseValidationRequiredChecks` (`[x]`-only) and `extractValidationChecks` (`[ ]`+`[x]`) keep their different checkbox semantics — only the ID grammar is shared (AC-15).

### Data Model Changes

None to `status.json` or persisted schemas. The spec/handoff artifact grammar changes (new ID column, ID-prefixed items) — a template + parser contract change, not a schema field change. Hard cutover: no dual-format tolerance.

### Implementation Notes (non-binding)

Owned by plan/implement; checked by the compiler and tests, not by spec review.

- One shared exported helper for the ID grammar (e.g. `parseValidationId(text): { id, description } | null` around `/^VAL-([1-9]\d*):\s*/i` — note the `[1-9]\d*`, not bare `\d+`, so `VAL-0` is rejected per Decision item 1's positive-integer requirement; add a boundary fixture for it) consumed by both parsers keeps AC-15 trivially true.
- Normalizing IDs to uppercase `VAL-<n>` at parse time gives case-insensitive matching for free.
- **Informational-row identity mechanism (implements Decision item 4)**: a heuristic-free normalization of the `Check` cell — case-fold, collapse internal whitespace, trim, **no** token extraction (no first-backtick / last-word / dash-split — that heuristic *is* the deleted `canonicalizeValidationCheck`). A separate tiny helper (e.g. `normalizeInformationalLabel(check): string`) returning the empty string for a blank/whitespace-only cell lets the caller detect the no-identity defect (AC-21) in one place. Two informational rows sharing a normalized label inside one table resolve latest-in-document-order (the same "latest wins" rule — not a defect). Keeping required and informational keys in one map is fine if the informational key is prefixed (e.g. `info:<label>`) so a `VAL-<n>` and a same-spelled informational label cannot collide; a two-map shape works equally well — the binding contract is only the identity *behavior* in Decision item 4, not the container. This mechanism is safe where the deleted canonicalizer was not because it's matched only against *other rows in the same handoff* (a baseline row against its own re-run rows), never across the spec↔handoff artifact boundary — the false "required check missing" class arose solely from cross-artifact prose alignment, which required matching no longer performs at all.
- The new ID defects should flow through `classifyValidationChecks`'s existing return shape and `buildPreflightReviewBlock`'s existing buckets rather than a new channel.
- **Consolidation seam (implements Decision item 7 / AC-13)**: `checkImplementEvidence` (`scripts/run-task/main.ts:2741-2827`) has independent early returns observed at spec-review time — verify against current code before relying on this list. The Changes-table/diff-evidence axis is internally mutually exclusive (at most one applies to a given fixture, since each later check's precondition requires the earlier ones to have passed): empty Changes table (`files.length===0 && malformed.length===0`, ~2754-2755), malformed row(s) (`malformed.length>0`, ~2757-2760), all-gitignored files (`verifiableFiles.length===0`, ~2787-2791), and a nonexistent/untracked path (reached only once `verifiableFiles.length>0`, ~2796-2823). The validation-outcome check (`validateHandoffAgainstSpec`, ~2762-2766) is logically independent of that axis — it inspects the Validation Outcomes table, not Changes-table shape — and today runs (and returns early) only after the Changes-table axis passes, which is precisely why it can currently be hidden by an earlier Changes-table defect. The fix is to decouple the two: compute whichever single Changes-table-axis condition applies (if any) independently from the validation-outcome check, then report both together when both apply, rather than only reaching the validation check after every Changes-table condition has separately passed.

## Known Risks

- **Hard cutover vs. in-flight tasks**: any task mid-pipeline at upgrade time has a prose-format spec/handoff and will hit the un-IDed-item rejection. Mitigation: the failure is loud and actionable (AC-4's message names the format), and the release note (AC-18) tells operators to drain first. This is deliberate — accepted 2026-07-19.
- **Codex mislabeling IDs** (same ID on every row, typo'd IDs): caught deterministically by the duplicate-ID-in-table and unknown-ID defects (AC-8) with messages naming the fix, so the failure mode costs one consolidated retry, not a loop.
- **Informational-row identity re-introducing prose fragility** (the `spec_review` blocker): the risk is that a non-ID informational identity resurrects the deleted canonicalizer's false-missing class. It cannot — see Implementation Notes for why the mechanism is scoped intra-handoff only, never across the spec↔handoff boundary where the false-missing defects were born. The two failure modes the reviewer named — sibling informational rows clobbering each other, and synthetic keys blocking re-run override — are covered by AC-19 (red-first) and AC-20 (design-invariant guard, green pre-fix). A third edge the reviewer surfaced — a blank/whitespace-only informational label having no identity at all — is a fail-closed format defect (AC-21, red-first), not a silent drop. The residual edge (two genuinely different informational checks the author labeled identically) merges them last-wins, which is strictly safer than the empty-ID collision it replaces and is author-visible (the labels are identical on screen).
- **Spec altitude drift on the identity/consolidation contracts**: rounds 3-4 of `spec_review` found that binding ACs describing exact identity mechanics and an exact defect-class enumeration kept generating fresh consistency defects each revision (AC-7 contradicting item 4's mechanics; AC-13 under-testing item 7's claim). Mitigation applied 2026-07-21: the exact mechanics and the current defect-class enumeration moved to Implementation Notes (non-binding); AC-7 was rewritten as a pure behavioral contract split by identity kind.
- **AC-13's first rewrite demanded a structurally impossible fixture**: round 5 found that `checkImplementEvidence`'s Changes-table/diff-evidence conditions are mutually exclusive by construction (each later check's precondition requires the earlier ones to have passed), so no single fixture can trigger all of them simultaneously. AC-13 now requires a table-driven set of *compatible* pairings — the validation-outcome check against each Changes-table-axis condition independently — grounded in the actual code's mutual-exclusivity structure (Implementation Notes), not an assumption. General lesson for this spec: every AC added or rewritten during auto-revision must be checked against the real branch conditions before being written, not just against the prose problem statement.
- **AC-15's original parity claim ignored the parsers' intentional selection difference**: round 5 found that `parseValidationRequiredChecks` (`[x]`-only) and `extractValidationChecks` (`[ ]`+`[x]`) necessarily produce different ID sets whenever a spec has unchecked items — a pre-existing, deliberate asymmetry this task doesn't touch. AC-15 and Decision item 6 now claim grammar parity (same ID extracted for the same line) only over the subset both parsers select, not full-set equality.
- **Two-parser drift**: the historical risk that the gate and the prompt preloader disagree on an ID for the same checked line. Mitigated structurally by the shared grammar + the shared-subset parity test (AC-15).
- **Byte-identical Validation Matrix test**: `.canon/templates/spec.md` is edited near the matrix block that `tests/validation-matrix-sync.test.ts` pins byte-identical against `implement.md`. AC-1 explicitly requires the matrix block untouched; an accidental matrix edit fails that suite immediately (good — loud).
- **Golden churn**: several prompt builders change injected text; a missed golden regen fails `npm test` loudly (AC-17). Check sibling goldens, not just `promptSpec`.
- **Message-class conflation**: adding new defect classes to an existing report risks a catch-all message. The one-message-per-class rule is load-bearing (patterns.md Validation Gate Discipline); AC-8's distinct-message assertions guard it.
- **This task's own pipeline run is governed by the installed global canon**, which parses the *current* prose format — so this spec's own Validation Required section deliberately stays in today's format. The new format takes effect for tasks authored after this ships and the engine updates.
