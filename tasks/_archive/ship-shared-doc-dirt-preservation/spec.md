# Spec: ship-shared-doc-dirt-preservation — Stop --ship discarding live shared-doc edits in the supervising checkout

> Written by: Claude | Review by: Codex
> Status: draft

## Problem

At `--ship`, when any shipped task is worktree-mode, the orchestrator runs a blanket `gitSafe('checkout', 'HEAD', '--', ...presentSharedDocs)` in the supervising checkout (`scripts/run-task/main.ts:2067-2072`), silently reverting every dirty `PIPELINE_SHARED_DOCS` file — the 3 telemetry files and the 6 managed docs (`scripts/run-task/worktree.ts:9-24`).

**Confirmed mechanism** (confirmed by code trace plus a real data-loss incident in an adopter repo on 2026-07-06): spec and spec_review phases run *before* a task's worktree exists, so their telemetry rows are appended to the supervising checkout's `docs/pipeline-invocations.md` (`recordMetric()` calls in `scripts/run-task/agents/claude.ts:243` and `scripts/run-task/agents/codex.ts:124`, resolving via `getMetricsFile()` in `scripts/run-task/metrics.ts:7` to REPO_ROOT) and sit uncommitted there until a later absorb/commit. When a *different* task ships while those rows are pending, the cleanup discards them. In the incident, shipping task A destroyed the uncommitted pre-implement telemetry rows of in-flight sibling tasks. The same code path would silently discard an operator's uncommitted edits to any of the six managed docs (e.g. `docs/lessons-learned.md`, `docs/patterns.md`) — a worse loss than telemetry.

The cleanup exists for a real reason (introduced in v1.4.0, replacing `flushWorktreeTelemetry()`): a dirty tracked shared doc that differs from the incoming content makes the base-branch checkout at `main.ts:2081-2091` and/or the base pull inside `mergeOpenPRsAndPull()` (`main.ts:1812`) fail with "local changes would be overwritten" — and by pull time the PR merge has already happened, so a failure there strands a half-shipped state. The cleanup cannot simply be deleted; the discard must be replaced with behavior that distinguishes stale mirror dirt from live foreign dirt.

## Decision

Replace the blanket shared-doc discard with a pre-merge classification, split by file class. All classification and any abort happen **before** the first irreversible step (`gh pr merge`) and before the base-branch checkout switch:

1. **Managed docs** (`PIPELINE_MANAGED_DOCS`): if any is dirty in the supervising checkout, `--ship` aborts with an error that names each dirty file and the recovery ("commit or stash your edits, then re-run --ship"). Nothing is merged, nothing is discarded, the operator's edits are untouched. Only operators write these files; silent discard is never acceptable.

2. **Telemetry files** (`PIPELINE_TELEMETRY_FILES` — `docs/pipeline-invocations.md`, `docs/task-quality-log.md`, `docs/lessons-learned.md`): preserve-and-reapply, applied uniformly to all three. For each dirty telemetry file, verify the working copy is a **pure append** over the HEAD copy (working content starts with HEAD content byte-for-byte). If yes: persist the appended suffix to a backup file on disk, log the backup path, then revert the working copy to HEAD.

   The revert-to-HEAD step is byte-for-byte what today's blanket discard already does at this site, so the downstream archive path is unchanged: after the merge, `rewriteArchivedTaskRefs()` (`main.ts:1911`) rewrites task refs in `docs/lessons-learned.md` / `docs/task-quality-log.md`, and `commitArchiveChanges()` (`main.ts:1886`) stages those two files (`stagedPaths` at `main.ts:2226`) and commits+pushes them — exactly the base+ref-rewrite content it commits today, with no preserved suffix in it.

   **Re-append happens after the archive changes are staged but before they are committed — see Amendment (below) for the exact seam.** `commitArchiveChanges()` is split into a `stageArchiveChanges()` step (the `git add -A` call only) and a slimmed `commitArchiveChanges()` (cached-diff check, `git commit`, `git push`); the call site stages first, re-applies each preserved suffix and deletes its backup, then commits and pushes. The insertion point relative to staging is load-bearing: two of the three telemetry files (`docs/lessons-learned.md`, `docs/task-quality-log.md`) are staged and committed by the archive path, so re-appending *before* staging would fold a sibling task's pending telemetry into *this* task's `chore: archive` commit and push it upstream — misattributing the sibling's in-flight rows and violating the "leave uncommitted" contract. The preserved suffix belongs to the sibling task, whose own pipeline will absorb it later; its correct home is uncommitted supervising-checkout dirt, never this task's archive commit. (`docs/pipeline-invocations.md` is neither rewritten nor staged, so its timing relative to staging is indifferent — re-appending it at the same point as the other two is correct for all three.)

   A plain append (no dedup) is correct — under the worktree-canonical model (v1.5.0+), REPO_ROOT telemetry dirt is never mirrored to the task branch (`buildHumanReviewStagePaths` at `main.ts:712` stages active-worktree copies only), so the suffix cannot already exist in the merged content. If the dirt is *not* a pure append, or reading the HEAD copy fails (file untracked / probe error): abort pre-merge exactly like the managed-doc case — fail closed, never discard.

**Classification is a strict two-phase gate**: all dirty shared docs are classified first, and any abort verdict (managed-doc dirt, non-pure-append telemetry, unreadable HEAD copy) wins **before any mutation** — no backup is written and no working copy is reverted anywhere if any file fails classification.

3. A clean supervising checkout ships exactly as today; the trigger condition (only when at least one shipped task is worktree-mode) is unchanged.

The net operator-visible change: `--ship` never destroys uncommitted work. Sibling-task telemetry survives shipping with zero added friction; anything the orchestrator cannot prove safe blocks the ship before the merge with a named-file recovery message.

## Non-Goals

- **No change to the `orphanedStatusPaths` cleanup** (`main.ts:2074-2079`): task-scoped `status.json` mirrors are covered by the worktree-canonical decision; that block stays byte-identical.
- **No change to what the archive commit contains** for `docs/lessons-learned.md` / `docs/task-quality-log.md`: `rewriteArchivedTaskRefs()` + `commitArchiveChanges()` commit the base+ref-rewrite version, byte-identical to today. The preserved suffix is layered on afterward as uncommitted dirt, never committed.
- **No relocation of pre-implement telemetry writes**: moving spec/spec_review telemetry out of REPO_ROOT is the structural fix for the collision and is a separate future task.
- **No change to `--pr` / `--push`**: neither path has a shared-doc discard today; none is added.
- **No new behavior for non-worktree ships**: the trigger condition (some shipped task has `worktree: true`) is preserved as-is.
- **No interactive prompt**: aborts are hard failures with guidance; no confirm-to-discard flow.

### Interaction Dependencies

- `mergeOpenPRsAndPull()` (`main.ts:1812`) — the pull the discard was protecting; the preserve/revert step must run before it (and before the branch switch) so a dirty tracked file can't block the checkout or pull. This is the same pre-switch site the current cleanup occupies.
- `rewriteArchivedTaskRefs()` (`main.ts:1911`) rewrites `tasks/<id>/` → `tasks/_archive/<id>/` in `docs/lessons-learned.md` and `docs/task-quality-log.md` only; `stageArchiveChanges()` (the `git add -A` split out of the former `commitArchiveChanges()`, via `stagedPaths` at `main.ts:2226`) then stages those two files, and the slimmed `commitArchiveChanges()` commits+pushes them. Because two of the three telemetry files pass through this staging step, the re-append must happen **after `stageArchiveChanges()` runs and before `commitArchiveChanges()` runs** — re-appending any earlier lands a preserved sibling suffix in the pushed archive commit; re-appending any later (the pre-amendment design) leaves the suffix unrestored through the commit/push failure paths. `docs/pipeline-invocations.md` is untouched by both, so the same single re-append point (between staging and commit) serves all three uniformly.
- `commitHumanReviewFiles()` / `buildHumanReviewStagePaths()` (`main.ts:712`) stage telemetry from the **active worktree only** (worktree-canonical model, v1.5.0+); REPO_ROOT telemetry dirt is never mirrored to the task branch. This is why the preserved suffix cannot already exist in the merged base content and a plain re-append (no dedup) is correct. If a future change reintroduces a REPO_ROOT→branch telemetry path, the re-append assumption must be revisited.
- The base-branch switch block (`main.ts:2081-2091`) — a dirty tracked file can also block this switch; the classification/preserve step must run before it (the same site as the current cleanup).
- The `orphanedStatusPaths` block (`main.ts:2074-2079`) sits between the current cleanup and the switch; it must remain untouched and ordering-equivalent.

## Known Risks

- **Re-append insertion point (the round-1 reviewed blocker)**: `docs/lessons-learned.md` and `docs/task-quality-log.md` are staged and committed by the archive path, `docs/pipeline-invocations.md` is not. Re-appending before `stageArchiveChanges()` runs silently commits a sibling's suffix into this task's archive commit and pushes it. Killed by placing the sole re-append point after staging and before commit (the Amendment) and by AC-11, which asserts the committed blob excludes the suffix while the working copy includes it.
- **Crash window, narrowed to staging (superseded by Amendment A6)**: the revert→re-append gap spans the merge, proof-establishment, archive-move, and ref-rewrite up to the `stageArchiveChanges()` call — a `die()` anywhere in that span leaves the suffix backed-up-but-unrestored, recoverable via the on-disk backup (AC-7). Once staging succeeds, the suffix is re-appended immediately, before `commit`/`push` run — a commit or push failure after that point requires no restoration at all, since the suffix is already back in the working tree (verified by A2/A3). The remaining window (merge through staging) was not further engineered away: closing it would require decoupling the archive commit's staging from the working tree entirely (e.g., a computed git-plumbing blob instead of `git add -A`), rejected as disproportionate — new failure modes in delicate ship code to close an already narrow, already-recoverable, rare-failure-mode window (branch-reuse edge cases, `gh` API flakiness).
- **Duplicate rows via an unforeseen overlap path**: the no-dedup design assumes no path commits REPO_ROOT telemetry dirt to the task branch (verified true today). If one appears later, the blind re-append would produce duplicate rows — a cosmetic defect, not data loss; the Interaction Dependencies note flags the assumption for future changes.
- **New abort friction**: managed-doc dirt now blocks `--ship`. Intended (fail closed), but the message must name files and the exact recovery. `--force` must NOT bypass this gate (AC-4) — silent data loss is not an operator-electable outcome; commit/stash is always available.
- **Ordering regression**: the classification must run before both the branch switch and the merge; a mistake reintroduces the half-shipped-state failure the original cleanup fixed. AC-3/AC-4/AC-5/AC-6 pin "no `pr merge` invoked" to guard this.
- **Sequential per-file processing**: classifying and mutating file-by-file could revert a telemetry file before discovering managed-doc dirt. The two-phase gate in Decision and AC-3 (mixed-dirt fixture, no backup created, both files untouched) exist to kill exactly this interleaving.
- **Dirt detection is git-status-derived, not content-diff-derived (Amendment Round 2)**: classification is gated on each path's `git status --porcelain=v1` code before any content comparison. The only code eligible for the pure-append/managed-dirt content check is `' M'` (no staged difference from HEAD; working tree modified relative to the index) — every other code (staged add/modify/delete, working-tree delete, rename, untracked) aborts for both file classes with no exception, closing both the SG-1 staged-only-edit regression (a staged edit's code is `'M '`, not `' M'`) and the pre-existing working-tree-deletion/rename gap (never `' M'` either) via one rule rather than per-case carve-outs. Renames get no special handling beyond this same fail-closed abort — a future task could add rename-aware recovery if that becomes a real operator workflow.

## Amendment

> **Round 1 — PR-level Codex review finding (backstop review at `human_review`, PR #185).** The pipeline's own `code_review` approved with nits; the separate PR-level `codex review` backstop found a real P1 the pipeline's lenses missed. Confirmed against the implemented code (worktree at this task's branch): `preservedSharedDocDirt` is reverted at the `classifyAndPreserveSharedDocDirt()` call (pre-merge) and only re-applied at a single point after `commitArchiveChanges()` returns. Between those two points sit numerous `die()` calls (human_review gate check, base-checkout-switch, base-divergence gate, merge-proof failures, `commitArchiveChanges` failure) — and `die()` calls `process.exit(1)` directly (`cli.ts`), which does **not** run pending `try/finally` blocks. Any of those aborts leaves the sibling task's preserved telemetry suffix missing from the working tree, recoverable only if the operator manually finds the on-disk backup — reintroducing, in a narrower but real form, the exact data-loss class this task exists to close.

**Root cause, more precisely**: `commitArchiveChanges()` (`main.ts`) stages `docs/lessons-learned.md` and `docs/task-quality-log.md` via `git add -A` because `rewriteArchivedTaskRefs()` rewrites stale `tasks/<id>/` → `tasks/_archive/<id>/` references inside them immediately beforehand — that is the *only* reason those two files are part of the archive commit at all. Nothing else legitimately dirties them between the initial revert and that point: this task's own writes to those files already landed on `main` via the squash merge, before `--ship` ever runs. Because `git add` snapshots content into git's index and a plain `git commit` commits only the index (not a fresh read of the working tree), the true constraint is narrower than "hold the revert until the whole archive step finishes" — it's "the suffix must be absent from disk only at the instant `git add` runs for those paths."

**Decision for this round**: split the single `commitArchiveChanges()` helper at its existing internal seam — staging vs. committing — so the call site can re-append between the two, and keep the revert held (as today) for everything before it:

1. No change to the initial classify/backup/revert step, nor to anything through `establishMergeProof()` and the archive-move loop — the revert stays in effect exactly as long as it does today, because holding it through the base-checkout switch and `mergeOpenPRsAndPull()` is unavoidable (git refuses to switch branches or pull over a dirty tracked file that differs from the incoming content).
2. **Named seam**: split `commitArchiveChanges(taskIds, baseBranch, stagedPaths)` (`main.ts:1887-1905`) into two functions along its existing internal boundary:
   - `stageArchiveChanges(stagedPaths: readonly string[]): void` — exactly the current `for (const p of stagedPaths) gitSafe('add', '-A', '--', p)` loop (`main.ts:1892`), nothing else.
   - `commitArchiveChanges(taskIds: string[], baseBranch: string): { committed: boolean; stderr?: string }` — the current `stagedPaths` parameter is removed; the function keeps the `git diff --cached --name-only` check, `git commit`, and `git push` exactly as today (`main.ts:1893-1904`), now assuming staging already happened.
3. At the call site (`main.ts:2274`): call `stageArchiveChanges(stagedPaths)` first (staging the still-reverted, suffix-free content — unchanged from today), **then re-append each preserved suffix to its working-tree file and delete its backup**, **then** call `commitArchiveChanges(taskIds, baseBranch)`.
4. This closes the commit-failure and push-failure abort paths specifically (the most likely real failures here, since push is the one step in this sequence that talks to a remote) — by the time either could fail, the suffix is already back on disk as ordinary uncommitted dirt, so no restoration is needed on that failure path.
5. The remaining window (revert through the staging call — covering the base-checkout switch, the merge/pull, the post-merge hook, and merge-proof establishment) is unchanged from the current implementation and is not closed by this round. It is documented, not engineered away: those are rarer failure modes (branch-reuse edge cases, `gh` API flakiness), and closing them would require decoupling the archive commit's staging from the working tree entirely (e.g., staging a computed blob via git plumbing instead of `git add -A`) — assessed and explicitly rejected as disproportionate: it trades a narrow, already-backup-recoverable risk for new plumbing-command failure modes in delicate ship code, for a marginal, rare-case gain.

**Scope**: `scripts/run-task/main.ts`, `tests/run-task-safety.test.ts`, and `tests/run-task-ship.test.ts` only. `commitArchiveChanges()`'s **signature changes** (drops `stagedPaths`, staging moves to the new `stageArchiveChanges()`); its commit/push behavior is otherwise unchanged. No new files, no schema change, no behavior change to *what* gets staged or committed — only *which function performs which step* and *what runs between them*. **Known caller to update**: `tests/run-task-safety.test.ts:1107` (`'commitArchiveChanges stops before push when archive commit fails'`) calls `commitArchiveChanges(['example'], 'main', ['tasks/example'])` directly with the old 3-arg form — this must become `stageArchiveChanges(['tasks/example'])` followed by `commitArchiveChanges(['example'], 'main')`, preserving its existing log assertions (`add -A -- tasks/example`, then `diff --cached --name-only`, then `commit -m chore: archive example`, no push). Grep confirmed no other caller of `commitArchiveChanges` exists in `scripts/` or `tests/`.

## Amendment Round 2

> **Round 2 — `code_review` `spec_gap` finding (SG-1), flagged by all three review lenses (cold-Codex, anchored Claude, cold-Claude) and mechanically verified by the foreman.** Implement built exactly what Round 1 specified; the spec itself never defined behavior for git-index state or working-tree deletions/renames, and that gap is a real regression.

**Problem**: `classifyAndPreserveSharedDocDirt()` (`main.ts`, present-filter/read region ~1939-1956) and `classifySharedDocDirtFromData` (`validation.ts:1587`) derive dirt purely from `fs.existsSync` plus a working-tree-content-vs-`HEAD` diff. Two consequences, both unaddressed by Round 1:

1. **Regression vs. the pre-Round-1 behavior**: a **staged-only** edit (index differs from HEAD, but the working copy has been reset back to HEAD — a normal git slip: `git add docs/decisions.md` followed by a botched `git reset`/`checkout HEAD -- <path>`) is classified `clean` because `workingContent === headContent`. `stageArchiveChanges()`'s `git add -A` is then a no-op for that path (already staged), and `commitArchiveChanges()`'s `git commit` is pathspec-less, so the staged content rides silently into the pushed `chore: archive <id>` commit — unreviewed, misattributed to this task. The pre-Round-1 blanket `git checkout HEAD -- <path>` reset both the index and the working tree, so it would have caught this; the replacement does not. This is a direct hole in the "fail closed on managed-doc dirt" guarantee this task exists to deliver.
2. **Pre-existing, not a regression, but now in scope**: a working-tree **deletion** or **rename** of a tracked shared doc is invisible to the `fs.existsSync` present-filter, so the file never reaches classification at all.

**Change**: replace the `fs.existsSync` + per-file content-read detection with a single batched `git status --porcelain=v1 -- <all 9 PIPELINE_SHARED_DOCS paths>` call, and gate classification on the resulting two-character status code before any content comparison runs. Porcelain semantics (documented, stable): column 1 = index vs. HEAD, column 2 = working tree vs. index; a path absent from the output has both columns clean (matches HEAD exactly). The **only** code eligible for the existing pure-append/managed-dirt logic is `' M'` (space in column 1 — no staged difference from HEAD; `M` in column 2 — working tree modified relative to the index, exactly today's "plain unstaged edit" shape). Every other code — any staged column-1 status (`A`, `M`, `D`, `R`, `C`), any working-tree delete/rename (`D`, `R`, `C` in column 2), or untracked (`??`) — aborts, for **both** file classes, with no exception. This closes consequence 1 (a staged-only edit's code is `'M '`, not `' M'`, so it now aborts instead of silently passing) and consequence 2 uniformly (a deletion's or rename's code is never `' M'`, so it aborts instead of being skipped) via one rule, not per-case carve-outs.

**Named seam — full new type signature**: `classifySharedDocDirtFromData(docClass: SharedDocClass, porcelainCode: string | null, headContent: string | null, workingContent: string | null): SharedDocClassification` (`validation.ts:1587`) — `porcelainCode` is a **new second parameter**; `workingContent` **widens from `string` to `string | null`** (it was non-nullable before this round). `SharedDocEntryInput` (`validation.ts:1618`) gains the same `porcelainCode: string | null` field and its `workingContent` field widens the same way. `SharedDocClassification`'s return shape is unchanged. Logic: if `porcelainCode === null`, return `{ verdict: 'clean' }` immediately (matches today's headContent-equals-workingContent clean case, now decided by git's own state instead of a content diff). If `porcelainCode !== ' M'`, return `{ verdict: 'abort', reason: `git status shows this path as '${porcelainCode.trim()}' — only a plain unstaged modification is eligible for preservation; staged changes, deletions, untracked files, and renames abort` }` for **both** `docClass` values — this new branch runs before the existing `docClass === 'managed'` / pure-append checks, which are otherwise unchanged and only ever reached when `porcelainCode === ' M'`. In `main.ts`, `classifyAndPreserveSharedDocDirt()` builds the porcelain map first; for a path with `' M'`, read `workingContent`/`headContent` exactly as today; for any other present-in-porcelain-output code, skip the content reads entirely (nothing to preserve) and pass `workingContent: null` — `headContent` may also be `null` if `git show HEAD:<path>` is not attempted or fails, since the porcelain-code check now short-circuits before it would matter for any non-`' M'` code. Files absent from the porcelain map need no reads at all (skip, same as today's zero-`present` fast path).
