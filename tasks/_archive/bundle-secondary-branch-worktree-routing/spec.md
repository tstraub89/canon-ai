# Spec: bundle-secondary-branch-worktree-routing — Fix bundle secondary's branch write landing in main instead of the worktree

> Written by: Claude | Review by: Codex
> Status: draft

## Problem

When `canon run <leader> <secondary>` runs a **multi-task bundle in worktree mode**, the first-implement branch recording writes a non-leader ("secondary") member's `branch` field into the **main checkout** instead of the bundle worktree. This leaves the main checkout dirty and the worktree's copy of the secondary's `status.json` with `branch: ""`.

**Confirmed mechanism** (observed live, and traced to source):

1. On first implement, `runImplementPhase` commits all members' task artifacts to the base branch (`scripts/run-task/phases/implement.ts:47`, `commitTaskArtifactsToBase`), then calls `ensureBranch` (`implement.ts:54`).
2. `ensureBranch`'s first-implement worktree path (`scripts/run-task/git.ts:283-302`) creates **one** worktree named after the leader (`ensureWorktree(taskIds[0], …)` → `dev-worktrees/<leader>/`), which inherits every member's `tasks/<id>/status.json` from base (all with `branch: ""`). It then loops over all members:
   ```js
   for (const taskId of taskIds) {
       const s = readStatus(taskId);   // routes through resolveTaskCwd
       s.branch = branchName;
       writeStatus(taskId, s);         // routes through resolveTaskCwd
   }
   ```
3. For a **secondary**, `writeStatus` → `statusFileFor` → `resolveTaskCwd(secondary)` (`scripts/run-task/state.ts:83-108`):
   - The by-id worktree path (`state.ts:86-87`) checks `dev-worktrees/<secondary>/tasks/<secondary>/status.json` — **misses**, because the worktree dir is named after the leader, not the secondary.
   - It falls back to reading the **main** copy's `branch` (`state.ts:89-93`). At this instant the secondary's main `branch` is still `""`, so the `if (branch)` guard is false and resolution falls through to `return REPO_ROOT` (`state.ts:107`).
   - → the secondary's branch write lands in **main**.

   This is a chicken-and-egg: resolution needs the branch set to find the worktree, but this very loop is what sets the branch.
4. After this write, main's secondary copy now carries `branch: "task/<leader>"`, so **later** `resolveTaskCwd(secondary)` reads main's branch and *does* find the leader's worktree via `findExistingWorktreeForBranch`. The dirty main file is therefore **load-bearing** for the rest of the run under today's code — it must not be "fixed" by restoring main without also fixing resolution.

**How confirmed:** A live 2-task bundle run (`canon run task-metadata-helpers canon-snapshot-robustness`) left the main checkout with `M tasks/canon-snapshot-robustness/status.json` whose only change was `branch: "" → "task/task-metadata-helpers"`; the leader's main copy stayed clean; in the worktree the leader's copy had the branch but the secondary's copy had `branch: ""`. The orchestrator also logged `Branch recorded: … (worktree mode — main checkout untouched)`, which was false for the secondary. The source trace above (steps 1–4) matches the observation exactly. The Acceptance Criteria pin this with AC-1's red-first regression test.

**Related but out of scope:** the bundle bootstrap also has a *crash-consistency* hole (a process exit mid-loop can record the leader's branch — the "bootstrap complete" marker both `implement.ts:44-45` and `git.ts:262` gate on — while a secondary is still blank, and the reuse path never repairs it). That mechanism is traced to source but has **not** been reproduced; per canon's reproduce-before-fix rule it is deferred to a follow-up task (see Non-Goals) rather than fixed on paper here.

## Decision

Make secondary→worktree resolution **independent of any mutable main-checkout write** and keep the worktree copy authoritative and main frozen, via two complementary changes:

**Change 1 — `resolveTaskCwd` gains a gated, fail-closed worktree-content scan.** The scan is added *inside* the existing `parsed.worktree === true` block — reached only when the main `status.json` is readable, records `worktree === true`, and the recorded `branch` is **empty** (the exact condition that today falls through to `REPO_ROOT` at `state.ts:107`). It never runs for a `worktree: false` task, which continues to fall straight through to `REPO_ROOT` as today. Reading the `worktree` flag does not require a non-empty main `branch`. When it runs, the scan enumerates existing git worktrees (parsing `git worktree list --porcelain` once into a path→branch map, the way `findExistingWorktreeForBranch` already does) and, for each worktree, evaluates the candidate status file `<worktree>/tasks/<taskId>/status.json`. **Each present candidate is read through `readStatusFromPath` (`state.ts:156-160`), never a raw `JSON.parse` + field read.** `readStatusFromPath` runs `validateStatus` → `validateBranchField` (`state.ts:117-159`), so a syntactically-parseable but schema-invalid candidate — e.g. `{ "worktree": true, "branch": 123 }` (a non-string `branch`) — **throws** rather than being silently accepted. `readStatusFromPath` takes an explicit path and does **not** re-enter `resolveTaskCwd`/`statusFileFor`, so it is recursion-safe (AC-5). Per candidate:

- **absent** (`fs.existsSync` false) → this worktree does not own the task → skip it;
- **present but invalid** — reading via `readStatusFromPath` **throws for any reason** (I/O error, malformed JSON, **or** a schema/branch-field validation failure such as a non-string `branch`) → **fail closed**: `die()`, do **not** skip. A present-but-uninterpretable canonical-candidate copy means ownership cannot be determined; skipping it and later returning `REPO_ROOT` would silently re-dirty main (see Known Risks). Atomic `writeStatusToFile` (tmp-write + rename, `state.ts:174-179`) means a *present* copy is always complete JSON, so this fires only on genuine corruption or invalid metadata, not on a concurrent write;
- **present and valid** (read cleanly through `readStatusFromPath`) → a **match** iff the candidate's own `worktree === true` **and** its recorded `branch` (trimmed) equals **that worktree's own checked-out branch** from the porcelain map. Requiring the candidate's own `worktree === true` prevents a stale divergent branch whose committed `tasks/<taskId>/status.json` happens to record `worktree: false` with a branch equal to that branch from being mistaken for bundle ownership. A candidate that reads cleanly but does **not** satisfy both conditions (empty branch, mismatched branch, or `worktree !== true`) is a **non-match → skip** — not a `die()`. The only die-on-present outcome is a `readStatusFromPath` throw.

Outcomes are tri-state over the matched set, after any present-but-invalid candidate has already forced a `die()`: (i) **exactly one** match → return it; (ii) **≥2** matches → `die()` naming the candidate worktree paths, never guessing; (iii) **zero** matches on a *successful* enumeration → fall through to `REPO_ROOT` (the legitimate pre-implement / genuinely-vanished-worktree case). Independently, if the `git worktree list` **enumeration itself errors or exits non-zero**, the scan `die()`s (fail closed) — it does **not** fall through to `REPO_ROOT`, which would re-dirty main under transient git failure. This routes a bundle secondary to the leader's worktree without ever consulting the main copy's `branch`.

**Change 2 — `ensureBranch`'s first-implement worktree loop writes branch to an override-aware, resolver-free destination.** After `ensureWorktree`, capture its **return value** as `leaderWorktree` (not a re-derived `WORKTREES_ROOT/<leader>`, since `ensureWorktree` may reuse the branch at a non-conventional path). Compute each member's destination as: `<CANON_TASKS_DIR_OVERRIDE>/<member>/status.json` when that env var is set (preserving the documented "override MUST win for reads and writes" contract of `taskDirFor`/`statusFileFor` and the existing bundle-heartbeat test), **otherwise** `<leaderWorktree>/tasks/<member>/status.json`. Read/write via `readStatusFromPath`/`writeStatusToFile` — never `writeStatus`/`statusFileFor`, which would re-enter the buggy `resolveTaskCwd` for a secondary. The main checkout is never written. As a zero-cost ordering choice, iterate secondaries first and the leader (`taskIds[0]`) last — the leader's branch is the marker `worktreeAlreadyCreated` and the reuse gate key off, so setting it last does not *worsen* the deferred crash-consistency issue (see Non-Goals); no crash-recovery behavior is claimed or tested in this task.

The two changes are consistent: the bootstrap loop (change 2) populates every worktree copy's `branch` via a resolver-free write, after which change 1's scan matches those copies on all subsequent reads/writes — so main stays clean and the worktree copy carries the branch. During bootstrap itself the scan intentionally finds no match (the worktree copies still carry the inherited empty `branch`), which is exactly why change 2 writes the destination directly instead of relying on the scan.

**Alternative considered and rejected — legitimize the main write by committing it.** Writing every member's `branch` into main *before* `commitTaskArtifactsToBase` (so the branch rides the base commit, main stays clean, and the existing main-hint path in `resolveTaskCwd` keeps routing secondaries) would avoid new scan machinery entirely. It loses for two concrete reasons:
1. *Crash-window wedge state.* If the process dies after the base commit but before `ensureWorktree`, main records `worktree: true` + a set `branch` with no worktree on disk. Every subsequent `resolveTaskCwd` — including the recovery re-run's first `readStatus(taskIds[0])` inside `ensureBranch` — hits the main-hint path and `die()`s ("worktree expected but missing") before any code that could recreate the worktree runs. Recovery requires manual status surgery. The chosen approach has no equivalent *wedge*: its own crash window (a mid-loop exit can strand a blank secondary — see Non-Goals) degrades to the pre-fix dirty-main behavior in that rare corner rather than hard-blocking the pipeline, and its proper fix is deferred to the reproduce-first follow-up.
2. *It flips two load-bearing first-implement switches.* `runImplementPhase` decides whether to skip `commitTaskArtifactsToBase` via `Boolean(primaryStatus.branch)` (`implement.ts:45`), and `ensureBranch` takes its branch-reuse path on the same test (`git.ts:262`) — a path that calls `ensureWorktree` without a start point, assuming the branch already exists. Pre-setting `branch` flips both switches before the branch/worktree exist.
(The alternative would restore `die()` orphan detection for secondaries — acknowledged; the wedge state costs more than that buys.)

## Non-Goals

- **Not** cleaning up the already-dirty `tasks/canon-snapshot-robustness/status.json` in the current main checkout. That is a pre-existing artifact of the bug on a different task's state; this fix prevents *new* occurrences only. (Verified: this fix touches no file under `tasks/canon-snapshot-robustness/` or `tasks/task-metadata-helpers/`.)
- **Not** coupling the fix to the `task-metadata-helpers` / `canon-snapshot-robustness` tasks it was discovered alongside — this is an independent orchestrator bug.
- **Not** fixing the bundle bootstrap's **crash-consistency hole** (mid-loop process exit stranding a blank secondary behind a set leader branch, with no reuse-path repair). The mechanism is traced to source but **not reproduced**; per canon's reproduce-before-fix rule it is deferred. **This deferral is tracked here, self-contained** (this task does not edit `docs/BACKLOG.md` or any other tracker file — see the operator-prerequisite bullet below). The follow-up must: (a) construct the deterministic repro first — a state fixture with the leader worktree present, its copy `branch: "task/<leader>"` (the "bootstrap complete" marker `implement.ts:44-45` and `git.ts:262` gate on), a secondary worktree copy `branch: ""`, and both main copies `""` — and observe the stranding through the reuse path (no nondeterministic mid-loop kill); then (b) fix the blank-secondary and stale-branch-mismatch cases together by making the reuse block (`git.ts:262-277`) repair every member before returning, failing closed on a member whose branch is non-empty but ≠ the leader's. Filing that follow-up (a fresh canon task, or a `docs/BACKLOG.md` entry) is left to the operator so this task's diff stays scoped to the fix. This task neither claims nor tests any crash-recovery behavior; in that unreproduced corner the pre-fix dirty-main behavior can still occur.
- **Operator prerequisite (not a task deliverable):** a prior spec round left an uncommitted `docs/BACKLOG.md` edit (the crash-consistency entry) dirty in the supervising checkout. Because `docs/BACKLOG.md` is neither under `tasks/` nor one of the three telemetry files, `findDirtyRepoRootSourcePaths()` (`git.ts:218-227`) classifies it as source dirt and `assertRepoRootCleanBeforeFirstWorktree()` (`git.ts:229-242`) would **abort first-implement**. That edit must be **reverted** before the pipeline reaches implement — the `human_spec_gate` (set on this task) is the natural checkpoint. This task no longer produces or depends on that edit, and reverting it loses no information: the deferred work is fully described in the bullet above.
- **Not** preserving secondary orphan-worktree `die()` detection for the *confirmed-absent* case. Accepted tradeoff (see Known Risks): post-fix, when the worktree scan **succeeds and finds no match** (the secondary's worktree has genuinely vanished, or none exists yet pre-implement), resolution falls through to `REPO_ROOT` rather than `die()`-ing, because dying on an empty `branch` would break legitimate pre-implement resolution (before any worktree exists). This is distinct from a scan that **cannot run** (the `git worktree list` invocation errors/exits non-zero) or that finds a **present-but-invalid** candidate — both of which fail closed with `die()` per AC-3. The leader still governs existence of the shared bundle worktree.
- **No** `status.json` schema change; no change to the `worktree: true/false` contract, bundle membership model, or the `CANON_TASKS_DIR_OVERRIDE` / `CANON_WORKTREES_ROOT` env semantics.
- **Not** changing leader or single-task resolution/recording behavior (both already resolve via the by-id path and write to the worktree), and **not** modifying `ensureBranch`'s reuse path (`git.ts:262-277`) at all — it stays byte-identical.

## Acceptance Criteria

- [ ] **AC-1 (wrong-main-write regression test, red-first):** A new test in `tests/run-task-safety.test.ts` sets up a **real-git** 2-task bundle (leader + secondary, both `worktree: true`, `branch: ""`, artifacts committed to base) using the existing `makeGitFixture` pattern, then invokes `ensureBranch([leader, secondary])` with worktree creation. It asserts, after `ensureBranch` returns: (a) the **worktree** copy `<leaderWorktree>/tasks/<secondary>/status.json` has `branch === "task/<leader>"`; (b) the **main** checkout's `tasks/<secondary>/status.json` is unchanged (`branch` still `""`, file not dirty per `git status --porcelain`); (c) `resolveTaskCwd(secondary)` returns the leader's worktree path. **Red-first evidence:** on the pre-fix code the test fails on **(a)** — the worktree copy's `branch` is still `""` — and **(b)** — main's secondary copy is dirty with `branch` set to `task/<leader>`. Assertion **(c)** is a post-fix *correctness* check, not the red signal: on pre-fix code `resolveTaskCwd(secondary)` also happens to return the leader worktree, but only *because* of the wrongly-populated main branch hint (Problem step 4) — so (c) passes pre-fix while (a)/(b) fail. The test must fail on pre-fix code (via (a) and (b)) and pass after the fix (all three).
- [ ] **AC-2 (bootstrap destination for every member, main untouched):** After `ensureBranch`'s first-implement path (change 2) in worktree mode, for **every** bundle member (leader and all secondaries) the member's `branch` is recorded in the override-aware destination: `<CANON_TASKS_DIR_OVERRIDE>/<member>/status.json` when that env var is set, else `<leaderWorktree>/tasks/<member>/status.json` where `leaderWorktree` is the path **returned by `ensureWorktree`**; and the **main checkout** copy is left untouched (no write to any member's main `status.json` in a real, non-override run). Verified by AC-1's assertions plus the existing bundle-heartbeat test (AC-6) confirming the override-root destination.
- [ ] **AC-3 (resolution match rule + fail-closed):** `resolveTaskCwd(taskId)` resolves a bundle secondary to the leader's worktree only when the main `status.json` is readable **and** records `worktree === true` **and** its recorded `branch` is empty (the scan is gated inside the existing `worktree === true` block; a `worktree: false` task is never scanned and falls through to `REPO_ROOT` as today). A worktree is a **match** only when its own `tasks/<taskId>/status.json` (i) exists, (ii) reads and validates cleanly through `readStatusFromPath` (JSON parse **plus** `validateStatus`/`validateBranchField`), (iii) records `worktree === true`, and (iv) records a `branch` equal to **that worktree's own checked-out branch** — **without reading or requiring** the main checkout's `branch` field for the secondary. Fail-closed outcomes: (i) a candidate status file that is **present but fails `readStatusFromPath`** — for any reason: malformed JSON **or** schema/branch-field validation failure (e.g. a non-string `branch: 123`) — → `die()` (never skipped, never a zero-match); (ii) the `git worktree list` enumeration **errors or exits non-zero** → `die()` (never a `REPO_ROOT` fall-through); (iii) **≥2** worktrees match → `die()` naming the candidate paths; (iv) enumeration **succeeds with zero matches** (every candidate is absent or reads cleanly-but-non-matching; none present-but-invalid) → fall through to `REPO_ROOT` (the legitimate pre-implement / vanished-worktree case).
- [ ] **AC-4 (disambiguation / no-false-match / gating / fail-closed tests):** Unit-style tests in `tests/run-task-safety.test.ts` prove the scan's negative behaviors, each targeting a distinct way a naive scan would go wrong: **(a) inherited-dir no-false-match** — an unrelated worktree on branch `B2` that merely *inherited* `tasks/<taskId>/` from base (its copy's `branch` is `""` or `≠ B2`) is **not** matched. **(b) main-copy `worktree: false` not scanned** — a task whose main `status.json` has `worktree: false` resolves to `REPO_ROOT` even when a stale worktree contains a matching `tasks/<taskId>/status.json`. The stale worktree's fixture must sit at a **non-by-id path** (i.e. **not** `<worktreesRoot>/<taskId>/`) so the direct by-id fast-path (`state.ts:86-87`, checked *before* the main `worktree` flag) does not short-circuit and resolve it regardless — only a non-direct candidate proves the content scan is gated off by the `worktree: false` main flag. **(c) candidate `worktree: false` not matched** — a worktree whose own `tasks/<taskId>/status.json` records `worktree: false` with a `branch` equal to that worktree's checked-out branch is **not** matched; `resolveTaskCwd(taskId)` does not resolve to it (falls through to `REPO_ROOT` if it is the only candidate). **(d) multi-match → die** — with **two** worktrees each satisfying the full match rule, `resolveTaskCwd(taskId)` `die()`s naming both candidate paths rather than silently picking one. **(e) enumeration failure → die (fail closed)** — when the `git worktree list` invocation exits non-zero, `resolveTaskCwd(taskId)` `die()`s rather than falling through to `REPO_ROOT`. **(f) present-but-invalid candidate → die (fail closed)** — two sub-cases, each making `resolveTaskCwd(taskId)` `die()` rather than skip into a zero-match `REPO_ROOT` fall-through: **(f1)** a `tasks/<taskId>/status.json` that is **present but unparseable** (malformed JSON); **(f2)** a `tasks/<taskId>/status.json` that is **parseable but schema-invalid** — concretely `{ "worktree": true, "branch": 123 }`, a non-string `branch` that `validateBranchField` rejects. Reading every candidate through `readStatusFromPath` (not raw `JSON.parse`) is what makes (f2) a `die()` rather than a silent non-match. Use the existing fake-git / `withFakeGitEnv` / `FAKE_GIT_WORKTREE_LIST_FILE` harness; add a `FAKE_GIT_WORKTREE_LIST_FAIL=1` lever to `setupFakeGit` (mirroring the existing `FAKE_GIT_FAIL_COMMIT` / `FAKE_GIT_DRIFT_DIFF_FAIL` levers) to force the non-zero `git worktree list` exit for (e).
- [ ] **AC-5 (no self-reference recursion):** The new scan and the change-2 destination computation resolve paths using only raw `fs` reads + `git` invocations + `readStatusFromPath`/`writeStatusToFile` — they must **not** call `readStatus`/`writeStatus`/`statusFileFor`/`taskDirFor` (which route back through `resolveTaskCwd`). Candidate read + validation uses `readStatusFromPath`, which takes an explicit path and does not re-enter `resolveTaskCwd`/`statusFileFor` (`state.ts:156-160`), so it is recursion-safe. Verified structurally: a grep of the new scan helper(s) in `scripts/run-task/state.ts` and of the changed `ensureBranch` blocks in `scripts/run-task/git.ts` shows no call to those four functions. (Preserves the self-reference-cycle break documented in `docs/decisions.md` §"Worktree-canonical task state from implement onward".)
- [ ] **AC-6 (leader / single-task / override unchanged):** Existing worktree behavior is preserved: `resolveTaskCwd(leader)` still returns the leader worktree via the by-id path, and a single-task worktree run records its branch into the worktree (not main). The existing bundle-heartbeat test in `tests/run-task-safety.test.ts` **continues to pass unchanged** — with `CANON_TASKS_DIR_OVERRIDE` set, both members' branch writes still land in the override root (assertions at `tests/run-task-safety.test.ts:1106-1109`) — and the existing `resolveTaskCwd` secondary-routing test (`:1272`) and reuse-path test (`ensureBranch bypasses dirty source guard when worktree branch is already recorded`, `:1153`) still pass. main-checkout (`worktree: false`) branch recording is unchanged. If any existing test must change, that is a spec-level contract change and is called out here — none is expected.
- [ ] **AC-7 (existing branch-hint `die` path intact):** The existing main-hint `die("Worktree … expected but missing")` path in `resolveTaskCwd` (reached when `worktree === true` and the recorded `branch` is **non-empty** but no worktree for that branch is found — covered by test `:1325`) is retained; the new scan sits on the sibling **empty-`branch`** sub-path within the same `worktree === true` block and does not remove or alter the non-empty-branch `die`. For a task whose main `status.json` records `worktree: true` with a non-empty `branch` but no worktree on disk, `resolveTaskCwd` still `die()`s as today.
- [ ] **AC-8 (log accuracy):** The first-implement worktree log line in `ensureBranch` is accurate for bundles after the fix (main genuinely untouched). If retained verbatim it is now true for secondaries; any change keeps it truthful and does not claim a main write occurred.
- [ ] **AC-9 (build artifacts):** `npm run build` is run and the committed `dist/cli/index.js` and `dist/scripts/run-task.js` match the fresh build (`git diff --exit-code -- dist/` clean). Both artifacts are declared in Affected Files.
- [ ] **AC-10 (validation clean):** `npm run lint`, `npm run type-check`, `npm test`, `npm run build`, and `npm run docs-refs-check` all pass.

- **`CANON_TASKS_DIR_OVERRIDE` fast-paths in `taskDirFor` (`state.ts:47-49`) and `statusFileFor` (`state.ts:111-113`)** are unchanged. ## Known Risks

- **Self-reference recursion (highest risk).** If the scan or the write helpers read/write status via `readStatus`/`writeStatus`/`statusFileFor`, they recurse (`resolveTaskCwd → statusFileFor → resolveTaskCwd …`) and break the cycle-break documented in `docs/decisions.md`. Mitigation: AC-5 forbids those calls; use raw `fs` + `git worktree list --porcelain` + `readStatusFromPath`/`writeStatusToFile`.
- **Deferred crash-consistency corner (accepted, tracked).** The bootstrap records N members across N separate file writes; a mid-loop process exit can strand a blank secondary. In that unreproduced corner the pre-fix dirty-main behavior can recur (scan finds no match → `REPO_ROOT` fall-through on the stranded member). Accepted per Non-Goals: strictly better than today (today the bug fires on *every* bundle first-implement; post-fix only in the crash corner), no hard wedge, and a reproduce-first follow-up (specified self-contained in Non-Goals; to be filed by the operator) owns the real fix. Change 2's secondaries-first ordering is a zero-cost choice that avoids *worsening* this corner.
- **Present-but-invalid candidate must fail closed (not skip).** A candidate `tasks/<taskId>/status.json` that exists but cannot be safely interpreted means ownership is undeterminable; skipping it and returning `REPO_ROOT` would route the next secondary read/write to the valid main copy and re-dirty main, silently hiding broken canonical state. "Invalid" is **not** limited to unparseable JSON: a *parseable* file with a schema-invalid field (e.g. `branch: 123`, a non-string) is equally uncomparable to the checked-out branch, so "readable JSON" alone is insufficient validation for a fail-closed ownership decision. Mitigation: read every candidate through `readStatusFromPath` (which runs `validateStatus`/`validateBranchField`) and treat **any** throw as present-but-invalid → `die()`, distinct from absent-candidate skip (AC-3, AC-4(f1)+(f2)). Note this is conservative: a corrupt or schema-invalid `tasks/<taskId>/status.json` in *any* worktree makes `resolveTaskCwd(taskId)` die; acceptable for a delicate path, and atomic writes mean it fires only on genuine corruption/invalid metadata.
- **Candidate `worktree:false` false-match.** A stale divergent branch could commit `tasks/<taskId>/status.json` with `worktree:false` and a `branch` equal to that branch. Mitigation: the match rule requires the candidate's own `worktree === true` (AC-3), with a negative test (AC-4(c)).
- **Enumeration failure must fail closed (not fall through).** The pre-existing `findExistingWorktreeForBranch` collapses "git failed" and "not found" into `null`; the new scan must **not** repeat that on the empty-`branch` path — a failed `git worktree list` there would fall through to `REPO_ROOT` and re-dirty main under transient git failure. Mitigation: AC-3 + AC-4(e) require a distinct enumeration-failed signal that `die()`s, with a forced-non-zero-exit test.
- **Disambiguation (inherited dir).** Every worktree inherits `tasks/<member>/` from base, so "scan for any worktree containing `tasks/<id>/status.json`" would match unrelated worktrees. Mitigation: require own `worktree:true` + own-branch equality (AC-3/AC-4(a)). At bootstrap (before change 2 writes the worktree copy) the scan intentionally returns no match — which is why change 2 writes the destination directly rather than relying on the scan during bootstrap.
- **Override-contract regression.** If change 2's writes ignore `CANON_TASKS_DIR_OVERRIDE`, the documented "override MUST win" contract breaks and the existing bundle-heartbeat test fails. Mitigation: AC-2/AC-6 require the override-aware destination and the unchanged existing test as the guard.
- **Performance.** The scan adds one `git worktree list --porcelain` invocation on the secondary-resolution empty-branch path only (parsed once into a path→branch map). `resolveTaskCwd` is called per phase boundary, not per file; no hot-loop concern.
- **Orphan detection weakened for secondaries (accepted, scoped).** When the scan *succeeds and finds no match*, a secondary whose worktree truly vanished routes to `REPO_ROOT` instead of `die()`. Chosen tradeoff (Non-Goals): dying on empty-`branch` would break pre-implement resolution. The leader still triggers the existing detection where its own state qualifies.
- **Detached-HEAD worktrees.** A worktree in detached-HEAD state has no `branch refs/heads/…` line; the path→branch mapper must return null/skip it so it can never satisfy the branch-equality test.
- **dist drift.** Forgetting `npm run build` leaves stale `dist/` and the `--pr` base-drift gate / CI rejects. Mitigation: AC-9 + Affected Files declare both artifacts.
