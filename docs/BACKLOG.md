- [x] **base-drift gate should warn (not silently drop) when `### Affected Files` has rows it can't reach** *(filed 2026-06-06 from the `multi-agent-code-review` ship cycle, where it aborted the first `--pr`; resolved 2026-06-08 — superseded by the 1.10.0 multi-table fix: `parseAllTablesH3` (`scripts/run-task/markdown-table.ts:168`, used at `validation.ts:1111`) now reads ALL tables under `### Affected Files`, so tables 2..N are no longer dropped and the proposed "warn" fallback is moot)*
  - **Problem**: The `--pr`/`--push` base-drift gate builds its allow-list from `parseAffectedFilesFromSpec`, which calls `parseTableH3` — and `parseTableH3` (`scripts/run-task/markdown-table.ts:115-158`) reads **only the first contiguous markdown table** under the `### Affected Files` heading, breaking at the first non-`|` line. If a spec author writes the Affected Files section as *several* tables under bold sub-headings (e.g. one table per subsystem, separated by blank lines), tables 2..N are **silently dropped** from the allow-list. Every path in those dropped tables then reads as base-drift and aborts the push, even though the author explicitly declared them. During `multi-agent-code-review` the section was six sub-tables → only table 1 parsed → tables 2-6 (main.ts, types.ts, validation.ts, verdict surfaces, docs, tests, dist) all flagged as drift. The gate *does* warn on multi-path *cells* (`parseHandoffPathCell` rejects >1 backtick) but is silent about whole unreachable tables, so the failure presents as "your declared files are drift" with no hint that the parser never saw them.
  - **Decision (proposed)**: when assembling the allow-list, detect the multi-table shape and warn loudly. Cheapest version: after `parseTableH3` returns, scan the remaining lines under `### Affected Files` for any later `|`-delimited table block; if found, emit `⚠️ spec.md '### Affected Files' has N additional table(s) the parser does not read — consolidate into ONE contiguous table (one path per row). Rows in tables 2+ are NOT in the allow-list.` and list the unreachable paths. Optionally upgrade `parseTableH3` to a `parseAllTablesH3` variant for this call site so multi-table sections parse correctly — but the warn-first fix is the load-bearing one (it turns a silent footgun into an actionable message; the parser upgrade is a nicety).
  - **Scope / risks**: keep the existing single-table contract for everything else that uses `parseTableH3` (handoff Changes table parsing relies on the break-at-blank-line behavior). If upgrading the parser, do it only for the Affected-Files allow-list path, not globally. Pure/fast — no new I/O.
  - **Workaround until fixed** (operator lesson, already in memory): write `### Affected Files` as ONE contiguous single-path-per-row table; use directory-form (`dist/`, not `dist/**`) for subtree matches.
  - **Effort**: `S`. Warn pass ~15 lines + a test; optional `parseAllTablesH3` ~20 lines + tests.

- [x] **Clear stale `verdict` when a review phase resets to `pending`** *(filed 2026-06-06 from a Codex PR-review finding on `multi-agent-code-review` #140 — refuted as a blocker, kept as hygiene; shipped 1.10.2 — every reset path now clears `verdict = ''` (`scripts/run-task/main.ts:2198/2224/2294/2749`, `src/task/index.ts:441/1025`); CHANGELOG [1.10.2])*
  - **Problem**: When a review phase (`spec_review` / `code_review`) is reset to `pending` (e.g. auto-block recovery, manual re-run), its `verdict` field is left at the prior value. A stale `verdict` on a `pending` phase is internally inconsistent state.

So the stale value is overwritten before it can mislead the dispatcher — confirmed by a second independent Codex agent. This is a "don't leave inconsistent state on disk" cleanup, not a correctness fix.

- [ ] **Full-send `spec_gap` auto-amend** *(deferred from `multi-agent-code-review` MVP, 2026-06-06)*
  - **Context**: `multi-agent-code-review` added the `spec_gap` verdict: the synthesis foreman classifies a finding as `spec_gap` when the implementation is correct but the spec is missing/wrong/ambiguous, and the orchestrator **halts for human amendment** rather than rerouting to implement. In the MVP this halt fires **even under `full_send`** — full-send tasks still stop at a spec_gap.
  - **Problem**: a `full_send: true` task is an explicit "don't interrupt me before the PR" call, yet a `spec_gap` breaks that contract by halting. The MVP chose halt-always because auto-amending a spec from an LLM verdict is delicate (it mutates the human-authored `spec.md` on the strength of a review finding) and the infra to do it safely didn't exist yet.
  - **Decision (proposed, when picked up)**: under `full_send`, on a `spec_gap` verdict, have a focused Claude session draft a spec **Amendment** section addressing the gap, re-run `spec_review` on the amendment, then continue the pipeline — instead of halting. Gate behind `full_send` only; non-full-send stays halt-for-human. Relates to the existing "QA auto-amends spec.md's Affected Files when promoting" idea (below) — both mutate spec.md programmatically and should share whatever guardrails that boundary needs (provenance marker, human-visible diff in `done.md`, never touch ACs without a re-review).
  - **Risks**: auto-mutating human-authored `spec.md`; an LLM `spec_gap` that's actually a code bug in disguise would get papered over by a spec edit. Mitigate by always routing the auto-amendment back through `spec_review` before resuming, and surfacing the amendment prominently at human_review.
  - **Effort**: `M`. New full-send branch in the spec_gap handler + amendment-drafting prompt + re-review wiring + tests; the delicate part is the guardrails, not the plumbing.

- [x] **`code_review` `spec_gap` recovery skips spec_review re-validation and plan refresh — asymmetric with `human_review` reroute** *(filed 2026-06-07 from the `upgrade-template-override-nudge` ship cycle; resolved 2026-06-08 by task `operator-review-recovery`, which allows `--reroute` from a blocked `code_review` `spec_gap` and adds audited `canon task accept ... --reason` review sanctions)*
  - **Problem**: When `code_review` returns `spec_gap`, the orchestrator blocks and the sanctioned recovery (the message it prints) is: amend `spec.md` → `canon task phase <id> code_review pending` → `canon run`. That routes the amended spec **straight back into `code_review`** — it never re-enters `spec_review`, so the amendment gets **no independent Codex spec-lens**, and `plan.md` is **not refreshed** (no `## Reroute Plan` section, no re-plan). Contrast the `human_review` path: `--reroute` on a full-tier task re-enters at `spec_review` → `plan` → `implement` → `code_review`, giving the amendment a fresh Codex review and a plan update. The asymmetry is backwards relative to risk: a `spec_gap` *means the spec was proven wrong*, which is exactly when a fresh spec-lens on the fix is most valuable — yet that path gives the amendment *less* review than a human_review reroute (where the spec was merely incomplete for the human's taste). And `--reroute` is **hard-guarded to `human_review`** (`"--reroute requires all tasks to be at human_review"`), so there is currently **no sanctioned path** to re-spec_review an amendment authored in response to a spec_gap. Likely unintentional / underspecified when `spec_gap` was added (multi-agent-code-review), not a deliberate "spec_gap amendments need less scrutiny" decision.
  - **Confirmed second-order bug — `reroute_count` desync corrupts a *later* reroute (same ship cycle, 2026-06-08)**: the spec_gap recovery has the operator author an `## Amendment` section, but because recovery routes through `code_review pending` (not `--reroute`), **`reroute_count` is never incremented**. If a subsequent, legitimate `--reroute` then happens (e.g. a Codex PR-level review surfaces a P2 after the task reached `human_review`), the reroute heading gate computes `requiredRound = (reroute_count ?? 0) + 1 = 1` (`main.ts:2112`) and the round-1 branch (`validation.ts:312-313`) accepts *any* `## Amendment` heading — so it **matches the stale spec_gap-era `## Amendment`** and routes Codex against that already-implemented scope instead of the new amendment. The operator-visible symptom: a bare `## Amendment` already exists, so adding a second bare one is ambiguous, but titling the new one `## Amendment Round 2` *also* fails to be required/matched because the gate still thinks it's round 1. Manual workaround used this cycle: set `phases.implement.reroute_count = 1` by hand so `requiredRound` becomes 2 and the gate requires `## Amendment Round 2`. That hand-edit is exactly the "don't hand-edit status.json" smell — it only exists because spec_gap recovery left the counter inconsistent. **Whatever fix this entry lands must increment `reroute_count` (and set the round-appropriate `## Amendment` heading expectation) as part of spec_gap recovery, so the amendment-round numbering stays consistent with the reroute machinery and no later reroute collides with a stale heading.**
  - **Partial backstop that exists today**: the `code_review` foreman re-reads the *full* amended `spec.md` and re-fills the Stage-1 AC table for every AC (including any new one), so an internally-contradictory or still-ambiguous amendment re-trips `spec_gap` and pings the human again rather than shipping. But that's the *code*-lens validating the amendment, not an independent *spec*-lens, and it does nothing about the stale plan.
  - **When the gap bites vs. doesn't**: it only matters for amendments that **change required behavior** (the fix needs re-implementation — the `code_review pending` re-review then returns `changes_requested` → auto-routes to implement, and Codex implements off the review findings + amended spec with no plan update). For "bless the current behavior" amendments (document existing behavior so the existing code is compliant), routing back to `code_review` is exactly right and no spec_review/plan refresh is wanted — so any fix must **not** force the heavy path on that case.
  - **Decision (proposed)**: give `spec_gap` recovery a spec_review re-validation of the amendment, mirroring the reroute machinery. Two candidate shapes: **(a)** allow `--reroute` (or a dedicated `--amend`) from a `code_review` + `spec_gap` state, re-entering at `spec_review` with the existing `## Amendment` heading convention + reroute bookkeeping (`rerouted=true`, `reroute_count`, clear the `codex_spec_review` / `claude_review` session slots so the amendment is read fresh); **(b)** auto-detect on `canon run` from a `spec_gap` block that `spec.md` gained a new `## Amendment` section and route `spec_review` → `plan` → `implement` → `code_review` instead of straight `code_review`. Either way, gate the heavy path so "bless current behavior" amendments (no new/changed ACs) can still take the cheap `code_review`-only route — e.g. only escalate when the amendment adds/changes an AC.
  - **Relationship to "Full-send `spec_gap` auto-amend" (above)**: that entry auto-*drafts* an amendment under full_send and re-runs `spec_review` on it before continuing — i.e. it *already assumes* the spec_review-re-validation path this entry says is missing for the manual case. The two should share the same "amendment → spec_review → continue" wiring; build the manual path here first and full-send auto-amend layers on top.
  - **Scope / risks**: don't regress the cheap bless-current-behavior recovery; preserve reroute bookkeeping so counters/sessions stay consistent; ensure the worktree (not REPO_ROOT) spec.md is the one re-reviewed (per worktree-canonical state). Mostly orchestrator routing + a guard on the `--reroute` precondition or a new dispatch branch.
  - **Effort**: `S`–`M`. Routing + precondition change + session-slot clearing + tests; the design choice (allow `--reroute` from spec_gap vs. auto-detect amendment) and the "which amendments warrant the heavy path" gate are the judgment calls.

- [x] **Worktree-canonical task state from implement onward — eliminate REPO_ROOT/worktree sync ambiguity** *(framed 2026-05-22 from PR #95's ship cycle and the follow-on flushWorktreeTelemetry / commitTaskArtifactsToBase fixes; shipped 2026-05-26 in PR #104 / 1.5.0 — `taskDirFor` rewired through `resolveTaskCwd` via new `taskDirForRepoRoot`; sync machinery deleted; CLI commands worktree-aware; pre-implement telemetry absorbed at scaffold time. Telemetry discrimination gate carved out as separate entry below; `parseAffectedFilesFromSpec` parser-cwd entry resolved as a side-effect of the SSOT refactor.)*
  - **Problem**: Canon's worktree-mode tasks today maintain TWO copies of task state: one in `REPO_ROOT/tasks/<id>/` and one in `dev-worktrees/<id>/tasks/<id>/`. The two are kept in sync via `syncWorktreeArtifacts` (worktree → REPO_ROOT) and the explicit copy loop in `runImplementPhase` (REPO_ROOT → worktree). Reasons for the duplication:
    - Pipeline code reads task artifacts via `taskDirFor()` → REPO_ROOT-relative paths, so REPO_ROOT must be fresh during phase boundaries.
    - Operator workflows (per current CLAUDE.md: "ensure tasks/<id>/spec.md in the MAIN repo, not the worktree, has an Amendment section") rely on REPO_ROOT-side editing for reroute amendments.
    - Visibility — operator can `cat REPO_ROOT/tasks/<id>/done.md` without `cd`'ing to the worktree.
  - **The cost**: ambiguity. Both surfaces are "live." Operators drift between editing REPO_ROOT and editing the worktree, edits get clobbered on the next sync, and the sync mirror leaves REPO_ROOT visibly dirty during pipelines — tempting Claude (or the operator) to commit those dirty files "to clean up before the PR," which recreates the just-fixed `commitTaskArtifactsToBase` bug class from a different angle.
  - **Decision (proposed)**: Promote the worktree to canonical-from-implement-onward. Eliminate the duplication by:
    - REPO_ROOT's `tasks/<id>/` stays FROZEN at the pre-implement snapshot (the state at `canon run` first-invocation time). No further sync writes touch it.

    - Discrimination at finer granularity than file-level (per-row task-ID attribution).   - **Risks to watch**:
    - **Non-`appendFileSync` writer regression**: if a future change introduces an in-place write to a telemetry file (e.g., a "fix typo" automation), the snapshot approach correctly flags that as a non-current-invocation edit and dies. Same failure mode as the parser approach would have had; both depend on the append-only invariant. Document this in the `docs/decisions.md` entry: "do not introduce non-append writers to `PIPELINE_TELEMETRY_FILES`."
    - **Race against pre-implement phase telemetry**: spec_review and plan phases append rows; the snapshot must be taken BEFORE those phases run, not at `commitTaskArtifactsToBase` entry (by which time current-invocation appends are already in the file and would be wrongly classified as pre-snapshot). Solution: snapshot at orchestrator entry, before `dispatch()` runs any phase. Verify with an integration test that runs spec_review → plan → implement and asserts no false foreign-detection.

Snapshot records absence (e.g., `snapshot[file] = 0` or sentinel); if the file later exists and is dirty, the whole file counts as "current-invocation append" (correct). If the file existed and was deleted (rare, operator edit), the snapshot offset would be > current size → treat as foreign edit → die.

With `multi-agent-code-review` (currently in `plan`) restructuring code review into multiple cold/anchored lenses + a synthesis foreman, the architect reviewer is better realized as one of those cold lenses. The phase-level infrastructure (new `PHASE_ORDER` entry, new routing in `checkAndRoute`, new `status.json` phase block, new templates) goes away; the prompt design — context isolation, adversarial persona, forced counterfactual, four shape questions, three-way verdict — is exactly what a cold sub-agent lens should do. This entry is preserved for the prompt design detail below; whoever specs the architect lens in `multi-agent-code-review` should draw from it.
  - **Original scope (still valid as lens design)**: A cold sub-agent that asks a fundamentally different question than the anchored reviewer: "ignoring whether the patch technically works, is this the right *solution shape* for the problem?" Fresh session, strict context isolation, opinionated senior-engineer persona, forced counterfactual. Three-way verdict: `agree`, `concern_for_human_attention`, or `block_due_to_architecture_risk`.
  - **Why it's wanted**: code review is line-level — "does this implementation match the spec?" QA is operational — "can we verify behavior with tests?" Neither asks the 30k-ft question: "did this *solve the stated problem*, or did it just satisfy the ACs?" "Are we painting ourselves into a corner?" "Is the spec's framing still right in light of what got built?" Today that check is implicit in the human gate — the human reads `done.md` and either notices semantic drift or doesn't. A structured architect review pre-flags specific shape concerns rather than relying on the human to spot them cold.
  - **Why same-model is acceptable here (the no-self-review principle, refined)**: canon's no-self-review rule strictly read is "no same-model review of the same question with the same context." Architect review asks a *different question* than code review (solution shape vs. line-level correctness), in a *different context* (fresh session, no code-review rationale, opinionated persona). It is not self-review under the strict reading even though both phases are run by Claude. Persona-shift produces independence of question, not independence of blind spots — accepted weakness. This is the *best* place to relax cross-model purity because the failure modes that matter at 30k ft (corner-painting, scope drift, "satisfied ACs but didn't solve the problem") are intuition-level, not LLM-blind-spot-level. The principle should be promoted into `AGENTS.md` as part of this work so the rule is explicit before the phase ships.
  - **Triggering rules**:
    - **Required** for `task_size ∈ {M, L, XL}` and any `delicate: true` task.
    - **Skipped** for `task_size = S` non-delicate (overhead not justified for tiny patches).
    - **Bundle mode**: triggered if any task in the bundle would individually trigger it. One architect review per bundle, not per task — the question is about the bundle's overall shape.
  - **Phase shape and gating**:
    - Runs only when `code_review.verdict ∈ {approved, approved_with_nits}`. If code review is `changes_requested`, the pipeline iterates implement → code review as today. Architect review is downstream of code-review approval; it never fires against a known-broken state.
    - **Single-shot, no review-loop.** Architect review is not iterative — its concerns are upstream-of-implementation (spec / plan / shape), not implementation defects. A `block_due_to_architecture_risk` verdict halts and routes to the human, who decides whether to revise spec, replan, or override. No automatic bounce back to Codex (different from `code_review` failures).
    - `agree` → orchestrator advances to `qa` silently.
    - `concern_for_human_attention` → orchestrator advances to `qa`, sets a flag the QA prompt reads to surface the concern in `done.md` under a new *Architect concerns* section.
    - `block_due_to_architecture_risk` → orchestrator halts, prints the concern, exits non-zero. Operator triggers `--reroute` (existing mechanism) to route back to spec/plan, or overrides via manual phase update.
  - **Inputs (context isolation is load-bearing)**:
    - `spec.md`, `plan.md` (full).
    - The diff (`git diff <baseline>...HEAD`).
    - `code_review.verdict` only — **NOT** the rationale or finding text. Sharing rationale anchors the architect review onto the code review's prior conclusions, defeating the persona-shift. Worth A/B testing whether to share the verdict at all (see Risks).
    - `handoff.md` (full, including any *Iteration N* sections).
    - **Explicitly excluded**: `review.md` body, `notes.md`, prior architect-review artifacts.
  - **Prompt design constraints**:
    1. **Fresh session, adversarial persona.** "You are a senior engineer pulled in to challenge this result, not bless it. Default disposition is skeptical. If the work looks fine, you must defend that conclusion against your own challenge."
    2. **Question explicitly different from code review.** Asks: "Did this solve the problem stated in the spec, or just satisfy the ACs?" "Does anything look like a corner-painting choice future work will regret?" "Is the spec itself still the right framing in light of how this came out?" Does NOT ask "is the code correct" or "does the diff match the spec line-by-line."
    3. **Forced counterfactual.** "What would a senior engineer have done differently if starting from scratch today, knowing what we know now?" Makes the persona do real comparative work and prevents passive acceptance.
    4. **Output schema forces explicit position.** Three-way verdict mandatory. Free-text concern justification required only on `concern_for_human_attention` or `block_due_to_architecture_risk`. Verdict is not the path of least resistance — the model must actively choose a stance, including a defended `agree`.
  - **Artifact and status integration**:
    - New artifact: `tasks/<id>/architect-review.md`. Template carries the four-question structure (problem still correctly framed? solution shape appropriate? hidden future-cost / corner-painting risk? human attention warranted?) plus the verdict and (when non-`agree`) the concern justification.
    - `status.json` gains `phases.architect_review` with `status` and `verdict` fields, mirroring the existing phase shape so the dispatcher reuses routing logic.
    - QA prompt updated to read `architect-review.md` and surface non-`agree` concerns under *Architect concerns* in `done.md`.
    - `docs/task-quality-log.md` gains a column for architect-review verdict and a column for "did it catch something not already in code review or QA." This is how the phase earns its keep empirically.
  - **What's built (estimated 400–600 lines)**:
    - `phases.architect_review` field in `status.json` schema + `src/task/index.ts` subcommand.
    - `runArchitectReviewPhase()` in `run-task.ts` (single-shot dispatch, three-way verdict parsing).
    - Routing in `checkAndRoute`: `agree` / `concern_for_human_attention` → `qa`; `block_due_to_architecture_risk` → integrate with existing reroute mechanism.
    - Prompt template (canon-supplied default + project overlay hook).
    - Artifact template `.canon/templates/architect-review.md`.
    - QA prompt update for *Architect concerns* surfacing.
    - `AGENTS.md` updates: documenting the new phase, the no-self-review principle's "different question, different context" framing, and the three-way verdict.
    - `CLAUDE.md` updates: pipeline-mode role lists architect review; explicit guidance on the persona, context isolation, and counterfactual.
    - `docs/task-quality-log.md` schema additions.
  - **Failure mode to watch — "architect-review-as-cosplay"**: same-model review with a thin persona produces bland approvals that look like signal but aren't. Symptoms: high `agree` rate with vague concerns, the model echoing code review's framing despite isolation, "looks good" with no counterfactual content. Mitigations are all in the prompt: force the counterfactual, exclude code-review rationale, structure the output schema to require explicit position-taking, monitor verdict distribution in the quality log. After 20–30 M/L/XL tasks, audit: did this phase catch issues not already in code review or QA? If not, the prompt or context isolation is too weak — tighten or remove. The phase has to earn its keep.
  - **Risks to watch**:
    - **Anchoring on code-review verdict**: even seeing `approved_with_nits` may bias the architect toward agreement. Consider stripping verdict context entirely and only telling the architect "code review has passed; your job is shape, not correctness." Worth A/B testing both variants (with-verdict vs. without-verdict) on the first 10–15 tasks.
    - **Persona drift across sessions**: opinionated personas tend to soften when given long context. Keep architect-review prompts short and tight; the spec + plan + diff is already a lot of input. Hold the line on excluding code review's rationale and `notes.md`.
    - **Bundle mode interaction**: triggering on the largest task in a bundle is right. Output is one architect review per bundle, not per task. The schema and prompt must handle multi-task input gracefully.
    - **Interaction with `--reroute`**: `block_due_to_architecture_risk` should integrate with the existing reroute mechanism rather than introduce a separate halt path. Reroute already routes back to spec/plan; architect-review block routes the same way with the concern as the reroute reason.
    - **Cost ceiling**: another full-pipeline phase costs tokens. The S-skip rule keeps it off small patches. If real-world cost/value ratio looks bad after the audit, consider gating architect review behind `delicate: true` only rather than M/L/XL broadly.
  - **Punted to later**:
    - **Cross-model architect review** (using a third model for this phase) — interesting future direction but adds dependency on model availability and undermines canon's two-model thesis. Revisit if same-model architect review proves too weak after the 20–30-task audit.
    - **Per-AC architect review** (one verdict per AC vs. one per task) — overkill at this granularity.
    - **Iterative architect review** — explicitly out of scope; the phase is single-shot by design.
    - **Architect review on conversational fast-tier specs** — fast tier doesn't have an architect review pass today. Whether to add a lightweight pre-implement architect review on full-tier spec authorship is a separate question; punt until the post-code phase has shipped and we know whether the value is in pre- or post-implement framing.
  - **Effort**: `M`. Most novel logic is the verdict parsing and three-way routing; the rest follows existing phase patterns. Touches dispatcher routing, so this benefits from one round of grilling against an actual M-tier task spec before code lands. Pipeline-infra-changes-are-inline applies; this is the shape of work that goes inline.
