# Lessons Learned

> Distilled cross-task insights. The QA phase appends entries here when a task surfaces a reusable insight that would have changed how a *different* task was approached.

## How to use this doc

This file accumulates over the lifetime of the project. Entries land here from two paths:

1. **QA distillation (automated, append-only)**: At the end of each task, the QA phase reads `tasks/<id>/notes.md` (raw scratchpad observations from any phase) and asks "would this have changed how a *different* task was approached?" If yes, it **appends** one entry for that task. If no, the detail stays in `notes.md` only. QA never edits, prunes, promotes, or reorganizes existing entries — appending its own task's entry is the only write it makes to this file.

2. **Lessons sweep (human-initiated and human-approved only)**: Promoting entries into permanent docs and pruning the buffer is a **human decision**. Agents never perform it autonomously, and no entry count ever auto-triggers it. Two occasions call for a sweep: (a) when this file exceeds ~15 entries — the QA phase notices and *signals* it with a one-line note in the task's `done.md`, but does not act; and (b) at the end of a release milestone — a human-recognized occasion, since the QA phase has no notion of release boundaries and emits no signal for it. Either way, a human runs the sweep when they choose to:
   - **Promote durable truths** to the right permanent doc — `docs/patterns.md` (a pitfall), `docs/decisions.md` (a settled decision), or `AGENTS.md` / `CLAUDE.md` (a workflow / spec / review rule). Then prune the entry here.
   - **Prune task-specific entries** that turned out not to generalize. Just delete them — the detail lives in the task's `notes.md` and the git history of this file.

The goal: this file is a *staging area*, not a permanent archive. Entries that prove durable get promoted by a human; entries that don't get pruned by a human. The total count stays manageable. Tombstones from past promotions are not preserved — `git log docs/lessons-learned.md` is the audit trail.

## Entry format

Each lesson is a short paragraph with this shape:

```markdown
### Short imperative title naming the rule

*(date YYYY-MM-DD, source: TASK-ID or `manual`)*

The rule, then the failure mode it prevents (specific incident if recent), then the concrete prevention (what to grep for, what to verify, where the canonical example lives). Reference symbols/files via the `` `SYMBOL` in `path/file.ts` `` form.
```

The title is the lesson — a future reader scanning headings should learn the rule from titles alone. Resist the urge to make it cute or descriptive of the bug; name the *rule that prevents the bug*.

The fix: reset every derived field at every site that writes the ID — there's no single chokepoint for this. Canonical reset rule: reset derived state at every writer of the ID field. ### When a literal AC conflicts with an already-tested behavioral invariant, preserve the invariant and narrow the fix

*(2026-07-13, source: upgrade-destination-classification)*

A late-added AC can be worded more broadly than the spec author intended, especially when it's inserted during spec_review to close a gap ("this file should refuse the same as any other managed target") without re-checking it against the suite's existing tested contracts for that specific file. Concrete case: AC-13 asked `scripts/docs-refs-config.mjs` to refuse untracked-existing content "the same as any other managed target" — read fully literally, that would also make a *tracked-clean* customized config overwritable whenever its content diverged from the shipped template, silently destroying committed adopter customizations that an existing, passing test explicitly protected (the exact bug class the task was fixing, reintroduced for one file). At plan time, the resolution was to keep the "adopter fully owns tracked-clean content forever" invariant untouched and satisfy the AC's literal test scenario (untracked + non-identical) narrowly, documenting the interpretation and isolating it to one branch so a human or reviewer could redirect cheaply if they disagreed. Rule: before implementing a broadly-worded AC, grep the existing suite for tests already protecting the specific surface it touches; if the literal reading would flip a passing test's asserted behavior, narrow the implementation to the AC's concrete scenario and flag the interpretation rather than guessing which one wins.

### When a mechanism keeps failing for the same structural reason across rounds, drop the mechanism class instead of iterating within it

*(2026-07-16, source: review-verdict-freshness-guard)*

When successive spec_review rounds reject different designs for the same underlying incompatibility — not new bugs in the current attempt, but the same root conflict resurfacing in a new shape — the fix is usually to abandon the whole mechanism class rather than refine it again. Concrete case: round 1 rejected a whole-file fingerprint (can't prove the *verdict* is fresh, only that the file changed); round 2 rejected verdict-scope invalidation on two structural grounds (the parser has no `## Verdict`-section locator, so proving invalidation is impossible to verify; and invalidating the latest scope destroys completed-round history the artifact is required to preserve). Both rejections shared one root: any *in-band* freshness mechanism — one that makes the shared, cumulative, append-only artifact self-describe its own freshness — fights the parser's loose grammar and the artifact's history-preservation contract at the same time. Chasing maximal in-band soundness was itself what expanded scope each round. Round 3 pivoted to a fail-closed park that reads no artifact at all on the crash path, and every prior structural objection evaporated by construction. Rule: at the 3+-round scope-expansion checkpoint, before proposing another refinement, check whether the last two rejections share a structural root; if they do, ask whether eliminating the mechanism class that root lives in is cheaper than patching around it again.

### A "retired wording is gone" AC needs a semantic sweep, not just the primary rejection string

*(2026-07-17, source: allow-comma-separated-multipath-cells)*

When a spec ACs a grep for "the old wording is gone everywhere," the first-draft grep pattern tends to key off the literal string from the primary code path (e.g. the parser's own rejection message) and misses paraphrased occurrences elsewhere that describe the same retired behavior in different words. Concrete case: the initial AC-9 grep targeted `multiple paths in one cell|one path per (row|line)`, which caught the parser and its tests, but `docs/BACKLOG.md` described the same retired constraint as `rejects >1 backtick` and `single-path-per-row` — different phrasing, same stale claim — and slipped through spec_review's first pass. The fix was widening the regex after a human/Codex re-read of the affected docs, not adding more exact-phrase variants blind. Rule: when an AC greps for retired wording across `docs/`/templates/prose surfaces (not just code identifiers), read every file the change touches for paraphrases of the retired claim before finalizing the grep pattern — an exact-string grep only proves the literal phrase is gone, not that the retired behavior is undocumented everywhere.

### Canonicalize real git worktree paths before comparing them, in both tests and resolver code

*(2026-07-18, source: bundle-secondary-branch-worktree-routing)*

On macOS, a worktree created under a temp directory is reported by git canonically under `/private/var/...` even when the test's own `os.tmpdir()` call supplied the `/var` alias — so a bare string-equality assertion between an expected fixture path and git's reported worktree path fails purely on spelling, not on actual routing logic, and only on macOS (Linux CI has no such symlink to expose the gap). Concrete case: the AC-1 real-git regression test asserting `resolveTaskCwd(secondary) === leaderWorktreePath` needed `fs.realpathSync` on both sides to pass reliably. The same asymmetry can leak into production code, not just tests: this task's new content-based worktree scan returns git's realpath-canonicalized path, while the pre-existing by-id resolution path returns a non-canonicalized `path.join(...)` — two different strings for the same directory on a symlinked filesystem, latent until some future caller does exact string-equality between two resolved cwds. Rule: any test or resolver code that compares a real (non-fake) git worktree path against a locally-constructed path should canonicalize both sides through `fs.realpathSync` (or neither) — don't let one resolution branch canonicalize and another not.

### An over-mechanized spec silently converts spec_review into code review of pseudocode

*(2026-07-19, source: update-install-root-provenance)*

When a spec's Acceptance Criteria and Decision text drift down to code altitude — literal regexes, exact seam-member lists, transcript formats, literal invocation strings — spec_review stops checking behavioral contracts and starts reviewing untyped pseudocode instead: each round's "underspecified" finding gets answered with more prose, which becomes more reviewable surface for the next round, a ratchet that doesn't converge. Concrete case: this task's spec churned 7 rounds before an operator diagnosed the pattern (round 6-7 findings were literal bugs in pseudocode the *previous* revision itself had added, not new design gaps) and restructured — ACs kept to behavioral contracts only, with mechanics (fixture layout, exact git commands, seam member names) moved into a new "Implementation Notes (non-binding)" subsection explicitly owned by plan/implement, checked by the compiler and tests rather than by spec_review. Rule: if spec_review rounds are re-litigating exact regexes, literal file layouts, or verbatim command strings rather than contracts, that's a sign the spec has dropped to code altitude — extract the mechanics into a clearly-labeled non-binding Implementation Notes section before revising again, rather than trying to word the same mechanism more precisely.

### Before hardening a brittle check, ask whether another layer already owns the concern — deleting it can beat making it robust

*(2026-07-21, source: stable-validation-ids, abandoned pre-implementation)*

A recurring bug (validation-check matching between spec and handoff false-blocking valid work, 3 incidents) was scoped as a feature to make that matching *robust* via stable per-check IDs. It churned 6 spec_review rounds — a new class of finding each round (informational-row identity, AC/code contradictions, parser-selection asymmetry, bundle-ID collision) — before the operator stopped and asked "are we building something useful or just pedantic?" The reframe that dissolved it: the deterministic spec↔handoff matching was a *low-value layer that duplicated a concern another layer already owned*. `docs/decisions.md` "Validation runs inside agent phases" already designates Claude's Stage 1 code review as the validation verifier, and explicitly notes the deterministic layer cannot catch the real failure modes (a check silently skipped, a failure mislabeled "unrelated"). So the matching wasn't worth hardening — it was worth deleting. The replacement was a fraction of the size: drop the prose canonicalizer entirely, keep only the pre-flight checks that key off the literal Result value (unexplained Fail, unfilled placeholder, blocked, anti-laundering — all near-zero false-positive), and let Stage 1 own per-check coverage. No new format, no cutover, shipped inline. Rule: when a brittle mechanism resists round after round of hardening, before writing more spec to fortify it, ask (1) does an existing layer already own this concern, and (2) does this mechanism actually catch the failure modes that matter? If another layer owns it and the mechanism only catches cheap/rare cases, delete the mechanism and lean on the layer — the round-over-round grind with a new-bug-class each round is itself the signal that the scope, not the wording, is wrong (see also [[iteration-vs-design-signal]] and the over-mechanized-spec lesson above). A skeptical "useful or pedantic?" from the operator is the same signal arriving by a different route.

### A high spec_review round count is only a design-churn signal if each round's finding is a new failure class — check the content, not the count

*(2026-07-22, source: fix-installed-provenance-version)*

The existing rule (see [[iteration-vs-design-signal]] above and the auto-block escalation message) says repeated `changes_requested` "usually means the spec has a structural or scope issue." This task hit the 3-round auto-block and ran to 6 rounds total, which by count alone looked exactly like that signal — but reading the rounds' actual content showed the opposite: round 1 caught native-canon-in-a-linked-worktree misclassifying as installed, round 2 caught the mirror case (an installed canon inside a submodule adopter misclassifying as vendored), and rounds 3–6 were incremental fine-tuning of assertions *within those same two already-identified edge cases* (an `orchestrator_commit` assertion tightened, a field name pinned down, a test-seam typing gap closed) — never a third, previously-unseen misclassification path. The operator diagnosed this explicitly before accepting via `canon task accept`: "Round shape read: r1 (worktree) + r2 (submodule) hardened detection against real git topologies; r3 is single-assertion edge-fine-tune, converging — not a redesign signal." Rule: at a spec_review escalation checkpoint (3+ rounds), don't read the round *count* as the churn signal by itself — read whether each round's `changes_requested` names a **new** structural case the spec hadn't covered (real design gap, keep revising) or **narrows an existing, already-identified** case (convergence, safe to accept once remaining findings are addressed). The distinguishing question is the same one [[iteration-vs-design-signal]] and the over-mechanized-spec lesson use for the opposite call: is this round's finding a new bug class, or the same one getting more precise?

### A guardrail prompt's calibration is implicit to the model it was tuned for — check it on every model-generation bump

*(2026-07-23, source: recalibrate-spec-review-for-stronger-reviewer)*

A "push to find fault" / "silence is a failure mode" framing in a reviewer prompt is not a neutral instruction — it's calibrated to counteract a specific weakness (an earlier model that under-fires without prodding). Canon upgraded `spec_review` to the 5.6 Codex generation without re-checking that framing, and three tasks in one week (`update-install-root-provenance`, `stable-validation-ids`, `fix-installed-provenance-version`) burned 6–7 rounds each on manufactured blocking findings against specs that were already sound — the stronger, more literal model executed the "keep pushing" instruction exactly as written, which is the failure mode once the model no longer needs pushing. Vendor guidance corroborated the mechanism (the 5.6 generation is documented as higher-recall/lower-precision than its predecessor, and OpenAI's own guidance for it is "stop over-prompting"). No executed prompt A/B or precision/recall eval backed the fix — a prompt's effect on a stochastic reviewer isn't a one-shot-reproducible property, and building that harness would itself be the over-mechanization this fix corrects (see the over-mechanized-spec lesson above); the evidence was convergent internal incidents plus vendor guidance, with a live dogfood run as the empirical guard. Rule: whenever a model-generation default changes for an agent role carrying a guardrail or review-disposition prompt (`spec_review`, `code_review` lenses/foreman, any future reviewer role), re-check that prompt's calibration against the new generation's known disposition before assuming the wording still fits — look specifically for "push harder," "silence is failure," or unbounded-scope framings, since a stronger model executes those literally instead of compensating for them. Durable version of this rule lives in `docs/decisions.md` ("Guardrail prompts carry an implicit model-strength calibration").

### A zero-result AC for a retired term must be cross-checked against every other spec section that already permits some hits to remain

*(2026-07-24, source: default-codex-models-to-5-6-generation)*

`spec_review` round 1 caught the spec's own AC-2 requiring **zero** repo-wide hits of the retired model identifiers, while the same spec's AC-7 and Docs Impact separately, and correctly, permitted some of those hits to remain (incidental test fixtures, a non-required backlog line, the release-time changelog step) — a self-contradiction the spec author hadn't cross-referenced while writing the grep-based gate. The fix wasn't tightening the grep; it was splitting AC-2 into an explicit two-bucket classification (a zero-result gate on current-state surfaces only, plus a named permitted-to-remain set covering every other hit the spec's other sections already allowed). Rule: when writing a codebase-wide "zero hits of X" AC for a retired term/identifier, before finalizing it, scan the rest of the spec (other ACs, Docs Impact, Non-Goals) for any place that already tolerates the term surviving somewhere (a historical doc, a release-time step, incidental test data) — fold those into an explicit allowlist bucket in the same AC rather than leaving a literal zero-result gate that a later section quietly contradicts.

### Enumerate every caller and classify agent-vs-orchestrator execution context before asserting how a mechanism works in a spec

*(2026-07-25, source: reconcile-qa-quality-log-summary)*

A spec claim like "counter X only increments on event Y" or "a writer can only be invoked from surface Z" is a claim about control flow, and control-flow claims need every caller traced, not just the path the author had in mind — a helper named for one trigger routinely serves several, and whether a given call site runs inside an agent's own session versus the orchestrator's process is invisible from the function body alone. This task burned three consecutive spec_review blocking rounds on exactly this gap: round 1 asserted `implement.reroute_count` meant a human-review rejection, but `rerouteFromHumanReview()` also increments it for blocked `code_review` `spec_gap` recovery; round 2 proposed an agent-invoked writer command, but `runQaPhase` awaits the agent's session before it can read `done.md`, and the QA prompt renders that exact command for the agent to run *inside* that same session — making the design architecturally impossible; round 3 nearly missed a fourth `qa → done` completion path (documented operator recovery in `.claude/skills/canon-pipeline/SKILL.md` and its `templates/` mirror) that only surfaced from a full grep across the skills docs, not from the mechanism the author already had in mind. The pre-flight review that finally converged differed only in explicitly instructing its ground-truth agent to (a) grep every caller of the function or counter in question, not just the discussed path, and (b) classify each call site as in-agent-session or orchestrator-context before the spec asserts anything about it. Rule: when a spec's Problem or Decision section states a fact about how an existing mechanism behaves, or where a new one can hook into orchestrator control flow, make caller-enumeration plus execution-context classification an explicit authoring or pre-flight step — not something left for spec_review to catch after the fact.

### `npm test -- <file>` in this repo silently runs the whole suite, not the named file

*(2026-07-27, source: doctor-quality-log-header-check)*

The `npm test` script hard-codes `tests/*.test.ts` as its Vitest target, so appending specific file arguments after `--` (a normally-valid Vitest CLI pattern) has no scoping effect — every invocation runs the full suite regardless. This task ran `npm test -- tests/cli.test.ts tests/run-task-quality-log.test.ts` intending a fast targeted check and got the full ~1066-test run instead (harmless here since it still passed, but wastes the time a scoped run was meant to save, and could mislead someone who reads a partial-looking command in a validation table and assumes it was scoped). Rule: to run a subset of this repo's tests, invoke Vitest directly (e.g. `npx vitest run tests/cli.test.ts`) rather than piping file paths through the `npm test --` script; check `package.json`'s `test` script for a hard-coded glob before assuming `--` args scope any `npm run` script in a new-to-you repo.

### An operator-facing recovery message's state-dependent clauses must be derived together and pinned with a state-varying pair, not a both-states string search

*(2026-07-31, source: preroute-review-loop-autoblock)*

When one persisted message has to describe both a state-independent fact (what a recovery command does) and a state-dependent fact (what runs next from *this* state), writing them as two separately-authored sentences lets the second one drift out of sync with the first without any test catching it — because the obvious test (`assert.match` for a substring) only checks that wording is present somewhere, not that it's the *correct* wording for the state the fixture is in. This task hit the exact same defect shape twice: round 1's code review found the reset command's recovery text promised "another implementation pass" was still possible with no disclosure that the reset itself had just accepted the current implementation as-is; the round-2 fix added that disclosure as a new trailing clause, concatenated onto the existing state-independent body — which reintroduced the class it was fixing, because the trailing clause was *also* written state-independent and was false at the backstop checkpoint (where re-implementation genuinely isn't next). Both times, the test that was supposed to catch it instead locked in the wrong text, because it asserted the same substring against both states rather than asserting opposite outcomes per state. The fix that actually converged (round 3) extracted one parameterized clause-builder consumed by both loops' reason-builders, taking the state as an explicit argument, so the state-dependent half can only be written once. Rule: when an operator-facing message mixes a state-independent fact with a state-dependent one, generate the state-dependent clause from an explicit state argument inside a single shared builder — never as a second sentence appended ad hoc — and pin it with a test that asserts *opposite* outcomes across a state-varying pair (`match` in state A, `doesNotMatch` in state B), not a `match`-only assertion run once per state.
