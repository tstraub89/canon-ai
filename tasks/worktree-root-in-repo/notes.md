- [spec_review] The no-legacy-fallback decision is not covered by changing only the default: `ensureWorktree()`/`getActiveCwd()` in `src/orchestrator/worktree.ts` and `resolveTaskCwd()`/`isOrphanedWorktreeState()` in `src/orchestrator/state.ts` still scan every registered worktree by branch, so a registered `../dev-worktrees/<id>` would be reused after the default moves to `.canon/worktrees/`.
- [spec_review] The revised root-scoped lookup also changes the lifecycle cases handled by `--ship`: `shipTasks()` falls back to `REPO_ROOT` for orphaned state and `teardownWorktree()` only derives the default `<root>/<task-id>` path, so legacy or accepted in-root non-default worktree paths need an explicit ship/refusal contract and cleanup coverage.
- [spec] Revision 3 answers both round-2 blocking findings by DELETING the "legacy worktree" third state that revision 2 invented, not by adding the two contracts round 2 asked for. Both findings share one root: a new state class must be taught to every consumer of worktree resolution, and there are more consumers than revision 2 enumerated (`resolveShipCwd`, `teardownWorktree` were rounds 2's; more would follow). Root-scoping the lookup collapses out-of-root into canon's EXISTING "worktree missing" state, which `resolveTaskCwd`, `getActiveCwd`, `isOrphanedWorktreeState`, `resolveShipCwd`, and `ensureWorktree` all already implement. Net: five fewer changed sites, `src/task/index.ts` and `main.ts` logic drop out entirely.
- [spec] Root-scoping is not a policy preference — unscoped resolution is incoherent with `assertManagedInvocationRoot()`, which already classifies any worktree outside the effective root as `foreign-worktree` and refuses. Without scoping, canon would resolve a task to `../dev-worktrees/<id>`, hand it to an agent, then refuse that agent's own `canon task phase` from inside it.
- [spec] Two residual items from round 2 are real independent of the deleted mechanism: teardown-by-derived-path (fixed, AC-7, red-first) and `--ship` leaving an unmigrated worktree behind (accepted explicitly + named in the changelog; refusing would strand an approved task).
- [spec] Feasibility hazard found while specifying AC-7: giving `teardownWorktree()` the branch via `readStatus()` routes through `resolveTaskCwd()`, which `die()`s when nothing resolves — that would convert `--ship`'s tolerated partial-cleanup state into a crash AFTER the merge lands. AC-7 pins teardown as no-op-not-error and the Implementation Notes name the non-fatal read route.
- [spec_review] The current first-worktree lifecycle leaves the main-checkout `status.json` branch blank: `ensureBranch()` writes the branch into the worktree copy, and an existing regression test asserts the main copy remains blank. With the spec's required root-scoped lookup, `isOrphanedWorktreeState()` returns false on that blank branch and `resolveTaskCwd()` falls back to `REPO_ROOT` when its secondary scan finds no in-root match, so AC-6's out-of-root missing behavior cannot be obtained by narrowing the lookup alone.
- [spec] Revision 4 deletes the root-scoping mechanism class entirely rather than hardening it a fourth time. Rounds 1/2/3 were all scope-expansion on one structural root: narrowing resolution redefines an existing state (`worktree missing`) for every consumer, and each round found another consumer or lifecycle state. Round 3's is unrecoverable within the approach — `ensureBranch()` leaves the main-checkout `status.json` branch blank *by contract* (`tests/run-task-safety.test.ts:1719-1727` asserts both the blank branch and a clean `git status` on that file), so a scoped lookup yields silent `REPO_ROOT` resolution, not a loud refusal.
- [spec] Replacement mechanism: resolution stays location-blind (zero changes to `findExistingWorktreeForBranch` x2, `scanWorktreesForSecondaryOwnership`, `resolveTaskCwd`, `isOrphanedWorktreeState`, `getActiveCwd`, `resolveShipCwd`, `teardownWorktree`), and ONE refusal lands at the `canon run` entry in `main()`. Every round-2/round-3 finding is moot by construction: ship untouched and exempt, teardown untouched, blank-branch state never classified, `canon task list` row unchanged.
- [spec] Deliberate narrowing of the guarantee: "no legacy fallback" becomes "no legacy *run*". `canon task phase/accept` on an unmigrated task still read/write the true state in the old worktree. Stated in Problem + Non-Goals so it is a documented boundary, not an unhandled case.
- [spec] Dropped from revision 3: AC-7 teardown widening (would let `--ship` force-remove an out-of-root directory once resolution is unscoped — the one destructive outcome this task must not create), and the `getActiveCwd()` message edit (unobservable: `readStatus()` → `resolveTaskCwd()` dies first in every non-override path).

- [spec_review] `canon task` still calls `assertManagedInvocationRoot()` before dispatching any task subcommand. An invocation from an unmigrated sibling worktree is therefore rejected by the existing foreign-worktree guard before `taskPhase()` or other subcommand resolution runs, despite revision 4's unqualified “No refusal outside `canon run`” and claim that task subcommands continue to resolve the old worktree.

Moving the effective root therefore reclassifies a pre-3.0.0 sibling worktree `canon-worktree` → `foreign-worktree` with zero code change — revision 4's unqualified "No refusal outside `canon run`" was wrong.

Revision 5 therefore corrects the guarantee instead of dropping a fourth mechanism.
