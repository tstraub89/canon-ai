# Spec: archive-review-on-reroute — Reroute archives `review.md` so a fresh round-1 review can't wedge on a stale trailing round verdict

> Written by: Claude | Review by: Codex
> Status: draft

## Problem

A `--reroute` resets `code_review` to a fresh round 1 but leaves the task's cumulative `review.md` untouched. When that file already holds `## Round N` sections from pre-reroute review rounds, the post-reroute round-1 verdict is invisible to the verdict parser and the phase wedges.

**Confirmed mechanism, reproduced** (this is a deterministic mechanism — fixed inputs hit the same wrong branch every run; it was confirmed by executing the actual parser against a constructed fixture during spec exploration, not just traced):

1. `extractCheckedVerdict` (`src/orchestrator/validation.ts:831-833`) scopes verdict parsing to the **last** `## Round N` section body, falling back to whole-file only when no `## Round` heading exists. Executed repro: a fixture with a stale `## Round 3` containing `- [x] Changes requested`, followed by a fresh whole-file-level `## Final Verdict` with `- [x] **Approved**`, returns `changes_requested` — the stale round wins. A fresh pre-flight-rejection append (`## Verdict` block) after stale rounds is equally invisible.
2. `rerouteFromHumanReview` (`src/orchestrator/main.ts:2588-2606`) resets `code_review.status`, `verdict`, `iterations_current_loop`, `iterations`, and `preflight_rejections_current_loop` — but contains no `review.md` handling anywhere in the reset loop (grep-verified), so pre-reroute `## Round N` sections survive on disk.
3. The code-review round number derives from the zeroed counter: `buildPipelineState` (`main.ts:219-225`) sets `iterations` from `iterations_current_loop`, and `promptCodeReview` (`src/orchestrator/prompts/index.ts:468-482`) computes `isRound1` / `roundN` from it. `bundleHasRealPriorReview` (`prompts/index.ts:447`) forces round 1 only when `review.md` is absent or a template stub — a populated post-reroute `review.md` does not trigger it. The foreman is therefore told "This is Round 1" while `review.md` shows `## Round 3`.
4. The round-1 foreman instruction (`src/orchestrator/prompts/templates/code-review-foreman.md:99`) says to fill the template structure directly and **not** wrap the review in a `## Round 1` section — so the fresh verdict lands outside any `## Round` heading, in exactly the position step 1 proves unparseable.
5. Both exits misbehave: `checkPhaseGate` (`validation.ts:936-949`) dies with `verdict mismatch: status.json wants '<fresh>', review.md has '<stale>'` when the foreman runs `canon task phase <id> code_review done <verdict>`; `tryEvidenceAdvance`'s `code_review` branch (`main.ts:2965-2972`) can instead silently auto-advance on the stale verdict. The reroute-aware evidence branch at `validation.ts:920` covers only `spec_review` and `plan`.

This became materially more reachable when PR #228 widened `--reroute` admission: the loop-cap auto-block it newly admits *guarantees* a multi-round `review.md` at reroute time. The exposure predates #228 for any `human_review`-origin reroute of a task whose review took ≥2 rounds.

**A second, related leak confirmed during exploration:** the reroute reset drops `sessions.codex_spec_review` (full-tier, `main.ts:2627`) but not `sessions.claude_review`. Policy is that code-review round 1 always starts fresh (`src/orchestrator/phases/code-review.ts:329`; documented in `docs/pipeline-orchestrator.md`), so the post-reroute round 1 is unaffected — but post-reroute **round 2** resumes the surviving pre-reroute review session, which carries every pre-reroute round's context and believes the review is several rounds further along. `canon task reset-code-review` already drops this session for exactly this reason; the reroute reset should match.

## Decision

**Make the reroute reset reuse `reset-code-review`'s shipped archival mechanism, and align its session cleanup.** No parser changes, no prompt-structure changes, no new `status.json` fields.

1. **Archive `review.md` per rerouted task.** Extract the archive step from `taskResetCodeReview` (`src/task/index.ts:1100-1148`) — rename `review.md` to `review-prior-<n>.md` in the same task dir, leaving `review.md` absent — into one shared helper with two call sites: `taskResetCodeReview` (unchanged apart from the allocator rule below) and `rerouteFromHumanReview`'s per-task reset loop (new). **`<n>` is one greater than the highest `<n>` already present in the task dir** (1 when none is), so the archive a given reset creates is always the numerically greatest one there. That monotonic rule *replaces* `taskResetCodeReview`'s current lowest-unused-number scan (`src/task/index.ts:1122-1123`; see Non-Goals): the two rules agree on every archive set canon can produce — canon only ever creates `review-prior-*.md` and never deletes one, so the set is contiguous from 1 — and diverge only after an operator manually deletes an archive, where lowest-unused files the newest findings *below* older ones and makes "the newest archive" unidentifiable. Item 3 depends on that identifiability, so the allocator and the lookup are one invariant, owned by one module: **numerically greatest `review-prior-<n>.md` == the archive this reset just created.** An absent `review.md` is load-bearing and already-handled state: `bundleHasRealPriorReview` then force-pins round 1, and `src/orchestrator/phases/code-review.ts` treats it as a first run — so the post-reroute review deterministically gets genuine round-1 semantics regardless of foreman prompt compliance. A `review.md` that is still the pristine template stub (its review never ran — reachable post-#228 via the `code_review`-pending entry state) is left in place and produces no archive file: a stub contains no `## Round` headings, so the wedge cannot occur, and archiving it would only produce noise.
2. **Drop `sessions.claude_review` in the reroute reset**, exactly as `taskResetCodeReview` does, closing the round-2 stale-session resume.
3. **Repoint both exempt-sibling prompt surfaces at the archived findings.** On a spec_gap-entry bundle reroute, a non-`spec_gap` sibling with a non-advancing prior verdict is told its prior review findings "at `tasks/<id>/review.md` remain binding" — in **two** prompts: `promptImplementReroute`'s exempt-task line (`src/orchestrator/prompts/index.ts:400`) and `promptSpecReview`'s reroute-branch exempt line (`prompts/index.ts:168`), which renders *first* on a full-tier reroute. After this change that file has been archived, so both lines must direct the reader to the archived file that actually holds those findings: the archive *this reroute created*, located at render time as the numerically greatest `review-prior-<n>.md` in the task dir — which item 1's monotonic allocator is what makes that lookup correct. The lookup runs at render time rather than being handed the name from the reset, because the reroute prompt is also rendered by a later plain `canon run` (the reset persists `implement.rerouted`, so a run that dies after the reset re-renders the reroute prompt in a process that never archived anything); an in-memory handoff would dangle on exactly that path. The advancing-verdict exempt line and all other reroute prompt text are unchanged.

All file operations — the archive rename and the render-time newest-archive lookup alike — route through the worktree-canonical resolvers (`resolveTaskCwd` / `taskDirFor`), matching how both existing mutators and `bundleHasRealPriorReview`'s existing `review.md` probe already work.

## Non-Goals

- **No change to the verdict parser.** `extractCheckedVerdict`'s last-round scoping is deliberate, test-pinned behavior (`tests/run-task-validation.test.ts:3431-3505` intentionally has artifact and `status.json` verdicts disagree; `tests/run-task-extract-verdict.test.ts` pins latest-round-wins in both directions). Its fence-blindness (a `## ` line inside a fenced code block can truncate round scoping) is a real, separately-reproduced defect owned by the existing BACKLOG entry prescribing a shared structural verdict-section locator — not this task.
- **No `handoff.md` archival.** `handoff.md` is also cumulative (`## Iteration N`), but no confirmed wedge exists there and `reset-code-review` doesn't archive it either. If implementation surfaces a concrete handoff analog, file it — don't fix it here.
- **No change to `taskResetCodeReview` beyond the archive-number allocator.** It becomes a caller of the shared helper; its counter resets, session drop, phase guard, and stdout messages stay as they are, and the existing `reset-code-review` tests must pass unmodified (AC-3). The one intentional delta is the allocator rule — lowest-unused → highest+1, per Decision item 1. Output is identical for every contiguous archive set, which is the only kind canon produces and the only kind any existing test constructs (`grep -rn "review-prior" tests/` asserts only `review-prior-1.md`: `tests/task-cli.test.ts:888,956,2394` and `tests/run-task-safety.test.ts:6327`). The two rules differ only in the operator-deleted-gap case, where highest+1 is required by item 3 and lowest-unused is silently wrong for *both* callers — a `reset-code-review` in a gapped dir today files the freshest review under a number that sorts below stale ones. `taskResetSpecReview`'s separate `spec-review-prior-` loop keeps its lowest-unused scan: nothing looks up "the newest spec-review archive", so it has no invariant to break, and unifying the two archivers is optional cleanup this task does not take on.
- **No change to reroute admission, the Amendment pre-flight, the exemption predicate, or the reset loop's counter handling** — all settled by PR #228. This task only adds the archive step and the session drop to the existing reset loop.
- **No new `status.json` field** (e.g. persisting the archived filename). The exempt-sibling prompt locates the newest archive at render time; State Schema Discipline is not triggered.
- **S-2 (`--full-send` tasks can never be rerouted) and S-3 (`checkRerouteEvidence` guards only two of four reset phases)** stay in `docs/BACKLOG.md` as separate tasks.

## Acceptance Criteria

- [ ] **AC-1 — red-first regression: the wedge scenario parses cleanly after a reroute.** A test in `tests/run-task-reroute-preflight.test.ts` seeds a task with a multi-round `review.md` (a filled template plus a trailing `## Round 2` section whose checked verdict is `changes_requested`), reroutes it via the existing `runReroute` harness, then writes the fresh round-1 review the way the foreman does — **appended into the file that exists at that path, coexisting with any surviving prior content, never a whole-file overwrite** (a filled template with `- [x] **Approved**`, no `## Round` heading) — and asserts: `review.md` was absent immediately post-reroute, `review-prior-1.md` exists and contains the `## Round 2` content, and the fresh review passes `checkPhaseGate` for `code_review` with verdict `approved`. **Red-first**: before the fix, `review.md` survives the reroute, the appended fresh review lands after the stale `## Round 2`, and `checkPhaseGate` reports the stale `changes_requested` — the executed-repro mechanism above. The append semantics are load-bearing: a whole-file overwrite in the test would erase the stale rounds and mask the wedge pre-fix.
- [ ] **AC-2 — the archive step, the newest-archive lookup, and the filename convention live in one module, and their shared invariant is unit-tested.** One shared module (see Affected Files) defines: the rename-to-`review-prior-<n>` archive helper with the highest+1 allocator (called by both `taskResetCodeReview` and `rerouteFromHumanReview` — neither call site carries its own rename loop), the newest-archive lookup AC-8 needs (numeric max over `review-prior-(\d+)\.md`, not lexicographic), and the `review-prior-` filename constant both use. The invariant is pinned directly by a unit test over a **non-contiguous** archive set containing a two-digit member: seed a task dir with `review-prior-2.md`, `review-prior-10.md`, and a populated `review.md`, run the archive helper, and assert (a) the helper reports and creates `review-prior-11.md`, (b) the lookup returns that same file, (c) `review-prior-2.md` and `review-prior-10.md` are byte-unchanged, and (d) `review.md` is gone. This single test kills both failure modes at once — a gap-filling allocator (which would create `review-prior-1.md` and leave the lookup pointing at `review-prior-10.md`) and a lexicographic lookup (which would return `review-prior-2.md`). Verified structurally: `grep -rn "review-prior-" src/` hits only (a) that module and (b) the pre-existing `spec-review-prior-` literal in `src/task/index.ts`'s `taskResetSpecReview` — a substring collision explicitly permitted to remain (the spec-review archiver is out of scope; unifying it is optional cleanup, not required). Call sites that need the filename (prompt line, stdout messages) interpolate the helper's return value or the exported constant rather than re-hard-coding the string.
- [ ] **AC-3 — `reset-code-review` is unchanged except for the allocator rule.** The existing `reset-code-review` tests (including the worktree-routing test in `tests/task-cli.test.ts`) pass without modification — no test file edits, no assertion rewrites. Its phase guard, counter resets, session drop, and stdout wording are untouched; the single sanctioned behavior delta is the shared allocator's highest+1 numbering (Decision item 1, Non-Goals), which is observable only in a task dir whose archive numbering already has a gap.
- [ ] **AC-4 — a template-stub `review.md` is not archived.** Rerouting a task whose `code_review` never ran (entry state `code_review` `pending`, `review.md` still the pristine scaffold) leaves `review.md` in place, creates no `review-prior-*.md`, and the reroute succeeds — verified by a unit test.
- [ ] **AC-5 — repeat reroutes number archives monotonically, including across a deleted archive.** A second reroute of the same task (round-2 Amendment) archives the intervening `review.md` as `review-prior-2.md` without disturbing `review-prior-1.md`. The same test then deletes `review-prior-1.md` and reroutes a third time: the new archive is `review-prior-3.md` — never a reused `review-prior-1.md` — and `review-prior-2.md` is byte-unchanged. Verified by a unit test driving the real reroute path (not the helper in isolation, which AC-2 already covers).
- [ ] **AC-6 — worktree-canonical routing.** For a worktree-backed task with a `review.md` present in both the supervising checkout and the worktree, the reroute archives only the worktree copy; the supervising checkout's `review.md` is byte-unchanged. Companion test cloned from the shape of the existing `task reset-code-review routes to the task worktree status.json` test in `tests/task-cli.test.ts` (per the `docs/patterns.md` companion-test rule for new task-artifact mutators).
- [ ] **AC-7 — `sessions.claude_review` is dropped on reroute.** After a reroute of a task whose `status.json` carries `sessions.claude_review`, the written status has no `claude_review` key; `sessions.codex_spec_review` handling is unchanged (still dropped on full-tier only). Verified by a unit test asserting both.
- [ ] **AC-8 — every reroute prompt that names the prior findings points at the archive that reroute created.** Two surfaces currently direct an agent at `tasks/<id>/review.md` for prior findings, and both must repoint at the archive that the reroute just created for that sibling (a file that exists after the reroute) while still stating the findings remain binding: (a) `promptImplementReroute`'s non-advancing exempt-sibling line (`src/orchestrator/prompts/index.ts:400`), and (b) `promptSpecReview`'s reroute-branch exempt line (`prompts/index.ts:168`) — the spec_review prompt renders *first* on a full-tier reroute, so it is the earliest surface that would otherwise dangle. The advancing-verdict exempt line (`:397-399`, names only `handoff.md`) is unchanged. **Verified through the production sequence, not a prompt lookup over pre-seeded archives** — a direct lookup cannot catch an allocator/lookup mismatch, because it never runs the allocator. Extend the existing mixed spec_gap bundle fixture (`tests/run-task-reroute-preflight.test.ts:926`, "rerouteFromHumanReview preserves `<verdict>` verdict for exempt failing sibling") so the exempt sibling's task dir carries a **non-contiguous** archive set (`review-prior-2.md`, `review-prior-10.md`) *plus* a populated `review.md` holding the findings under test; run the real reroute; then render both prompts against the resulting on-disk state and assert, for the exempt sibling's line in each: it names `review-prior-11.md` (the archive that reroute created, whose content is the pre-reroute `review.md`), it does **not** name `review-prior-10.md`, and it does not name that task's bare `tasks/<id>/review.md`. Write the negative assertions so `review-prior-<n>.md` cannot satisfy them (match the full `tasks/<id>/review.md` path, not a bare `review\.md` substring). Additionally update the two existing static exempt-line assertions in `tests/run-task-prompts.test.ts` — including the `assert.match(specReviewLine, /review\.md/)` pin at ~:373, which pins the old pointer and must be rewritten to the archived-file pattern, not deleted — and regenerate the golden entries.
- [ ] **AC-9 — the stale-`review.md` evidence hole is closed.** Arrange a task *at* `code_review` with a populated `review.md` whose trailing verdict is `approved` — the state where `tryEvidenceAdvance`'s `code_review` branch (`main.ts:2965-2972`) would advance on the artifact — then reroute it and drive/set the task back to `code_review` without any fresh review being written. Assert the evidence path does **not** mark `code_review` done: post-archive there is no `review.md` (or only a fresh template), and `tryEvidenceAdvance` reports no artifact instead of advancing on the pre-reroute verdict. **Red-first**: pre-fix, this arrangement advances on the stale approved verdict — the test must construct the state where the pre-fix advance actually fires, not merely reroute and assert nothing happened while the phase pointer sits elsewhere.
- [ ] **AC-10 — archive failure fails closed, before any `status.json` mutation.** All archives for the invocation happen **before** the first `status.json` mutation of the reset loop. If any task's archive rename throws (e.g. an injected `fs.renameSync` failure or a permissions fixture), the reroute aborts with an error naming the task and the failed rename, and **no** task in the invocation has its `status.json` mutated — byte-identical before/after for every member. Already-completed renames from the same invocation may remain on disk (nothing is lost — the rename preserves content) and the error must say so. Verified by a unit test injecting an archive failure in a two-task bundle where the *second* task's archive fails, asserting both tasks' `status.json` files are byte-unchanged and the first task's completed archive is reported.

The `reset-code-review` row is untouched.
- [ ] **AC-12 — generated artifacts regenerate.** `tests/run-task-prompts.golden.json` regenerates with changes confined to the reroute-prompt entries affected by AC-8; `dist/orchestrator/run-task.js` and `dist/cli/index.js` rebuild via `npm run build`; `npm run sync-templates:check` passes. ## Known Risks

- **The exempt-sibling pointer is the trickiest AC, and its correctness is an allocator↔lookup contract, not a lookup detail.** The prompt must *find* the archive on disk at render time rather than be handed the name (an in-memory handoff dangles on the reachable "reset succeeded, run died, operator re-runs `canon run` without `--reroute`" path). That puts "which file is newest" in two places at once, and either half alone silently points the agent at round-old findings: a gap-filling allocator plus a numeric-max lookup diverges the moment an archive has been deleted, and a lexicographic lookup diverges the moment `<n>` reaches two digits. Decision item 1 makes highest+1 the only allocator, AC-2 pins allocator and lookup against one gapped two-digit fixture, and AC-8 proves the pair through the real reroute path. Residual risk is an implementer "restoring" lowest-unused for `reset-code-review` parity — AC-2's fixture is the pin against that. If the lookup finds nothing at all, fail toward the current wording's *intent* (findings remain binding) rather than naming a nonexistent file.
- **Archiving is a destructive-looking move on a live artifact.** Nothing is deleted — the rename preserves every byte in the task dir — but operators and agents who expect `review.md` to hold review history post-reroute will find it relocated. AC-11's doc note and the reroute's stdout (implementer may add a per-task "archived review.md → review-prior-N.md" info line, matching `reset-code-review`'s message) keep it discoverable.
- **Helper extraction can silently change `reset-code-review` in ways AC-3 doesn't see.** The extraction deliberately changes one thing (lowest-unused → highest+1) and must change nothing else; its worktree-dir resolution in particular is load-bearing and must stay `taskDirForCwd(resolveTaskCwd(id), id)`. AC-3's existing tests only exercise the fresh-dir case (they assert `review-prior-1.md`), so they cannot distinguish the two allocators or catch a base-dir regression on their own — the AC-6 worktree companion test and AC-2's gapped fixture are what cover those two axes.
- **The stub-detection predicate must not misclassify a real review.** If "template stub" is detected too aggressively (e.g. any file lacking `## Round` headings), a real single-round filled review would be left un-archived — reintroducing a variant of the wedge on the *next* reroute when a `## Round 2` lands after it. Detection should reuse the existing template-unfilled predicate (`isTemplateUnfilled` / the logic behind `bundleHasRealPriorReview`), not a new heuristic; a filled round-1 review with no `## Round` heading must still be archived. AC-4's test covers the stub side; AC-5's repeat-reroute test covers the filled-round-1 side implicitly (its first archive is a filled template with a trailing round).
- **Golden regeneration over-reach.** Same class as #228: regeneration accepts whatever changed. AC-12 bounds the expected diff to the AC-8 entries; anything else is a defect to report, not commit.
- **This is orchestrator hot-path, `delicate: true` work.** A bug in the archive step corrupts task state for every rerouted task. The fail-closed contract is binding via AC-10: all archives precede the first `status.json` mutation, and any archive failure aborts the whole invocation with every member's status byte-unchanged (already-completed renames remain on disk and are reported — content is never lost). The residual risk is an implementer weakening the two-pass ordering into per-task interleaving; AC-10's second-task-fails bundle test pins against that.

## Human Test Plan

1. Take a task whose code review went through two or more rounds, then got rerouted with a spec amendment.
   Expected: after the reroute, the old review is preserved under a "prior review" file in the task's folder, and the review file itself starts clean for the new round.
2. Let the rerouted task's fresh review round finish with an approval.
