# Completion Summary: upgrade-destination-classification — canon upgrade: refuse untracked-existing targets, fail closed on git errors

> For the human. This is what you need to know.

## What Changed

`canon upgrade` used to decide whether it was safe to overwrite a file by asking git one yes/no question ("is this dirty?") — and it got the answer wrong in two dangerous ways. An untracked file sitting at a canon-managed path (one you'd hand-created but never `git add`ed) was treated as "clean" and silently overwritten with no way to get the content back, since git never had a copy of it. And if the git check itself failed for any reason (git missing, a broken repo), the tool assumed everything was safe and wrote over everything. This task replaces that single dirty/clean check with a proper classifier that sorts every write target into one of six buckets — absent, byte-identical, tracked-and-clean, tracked-and-modified, untracked-but-present (including gitignored), or "git couldn't tell me" — and only writes to the buckets where the content is actually recoverable. Everything else is refused with a message naming the exact remedy (commit it, move it aside, or pass `--force`), and refusal is all-or-nothing so a single unsafe target still blocks the whole run, same as today. `--force` now overrides all three refusal classes (it already covered one), but it still cannot force through a malformed `.gitignore` canon block — that stays a hard stop. `--check` runs the identical classifier so its preview is never out of sync with what a real run would do.

A first code-review round caught a real bug in the initial implementation: a `git rm`'d (staged-deleted) tracked file was being classified as "absent" and silently recreated, defeating the exact protection this task was built to add. That's fixed — the classifier now checks git's dirty/status output before it checks trackedness, so both a plain `rm` and a staged `git rm` of a tracked file correctly refuse as "tracked and modified."

## Files Changed

- `src/cli/commands/upgrade.ts` — replaced the boolean `isPathDirty` check with a destination classifier (`absent` / `canon-identical` / `tracked-clean` / `tracked-dirty` / `untracked-existing` / `unverifiable`); wired refusal for the three unsafe classes; added per-class CLI messaging (`printUpgradeRefusals()`); routed the docs-refs-config scaffold source through the same shared gate.
- `tests/cli.test.ts` — new fixtures for every class and the six write sources touched by the gate, including the untracked sentinel regression, the forced git-failure case, gitignored-existing, staged deletion (`git rm`), and `--check`/real-run parity; the old test that asserted the buggy "untracked doesn't refuse" behavior is inverted.

## How to Test

1. In a canon-adopted repository, create a file with your own recognizable content at a canon-managed path that git isn't tracking. Run `canon upgrade` with no flags. Expected: it refuses, names your file, explains that git can't restore it because it was never tracked, and your content is untouched.
2. Run `canon upgrade --check` on the same repository. Expected: it reports the identical refusal it would enforce for real and changes nothing.
3. Re-run `canon upgrade --force`. Expected: the file is replaced and listed as updated.
4. Run `canon upgrade` in a directory where git can't answer (e.g., not a git repo) that has a modified canon-managed file present. Expected: it refuses and says it can't verify safety because git — its safety boundary — is unavailable.
5. Run `canon upgrade` in a fresh, non-git directory with none of canon's files present. Expected: files scaffold normally — nothing is lost, so nothing is refused.

## Proposed Changelog

- **`canon upgrade` now refuses to overwrite a canon-managed file that git cannot restore, and fails closed instead of open when git itself can't be checked.** Previously, an untracked (or gitignored) file sitting at a canon-managed path was treated as "clean" and silently overwritten — unrecoverable, since git never had a copy. And if the underlying `git status` probe failed for any reason, every target was treated as safe to write. `canon upgrade` now classifies every target before writing: untracked-but-present and gitignored-but-present files refuse (new), and an existing target refuses when git's own state can't be determined (new) — both overridable with `--force`, same as the existing tracked-and-modified refusal. Absent targets and byte-identical content are unaffected, so fresh scaffolds and idempotent re-runs still proceed without `--force` even when git is unavailable. `--check` reports the identical classification a real run would enforce. ([#187](https://github.com/tstraub89/canon-ai/issues/187))

## Decisions Made

- **Git-probe failure degrades per-destination rather than aborting the whole command.** An existing, non-identical destination refuses when git can't answer; an absent destination still scaffolds. This keeps greenfield (non-repo) installs working and preserves several existing fixtures that intentionally exercise the no-git path.
- **Gitignored-existing folds into the same `untracked-existing` refusal class as plain untracked**, rather than getting a distinct fourth bucket — both are exactly the "git cannot restore this" class, and a bare `git status --porcelain` can't tell them apart from tracked-clean, so the classifier establishes trackedness explicitly via `git ls-files` first.
- **`scripts/docs-refs-config.mjs`'s pre-existing "fully adopter-owned once present" contract was preserved over AC-13's most literal reading.** AC-13 (added by spec_review round 1) said this file should refuse untracked-existing "the same as any other managed target" — but a fully literal reading would also overwrite a *tracked-clean* customized config whenever its content differs from the shipped template, silently destroying committed adopter customizations (the exact bug class this task fixes, reintroduced for one file). Resolution: absent / locally-deleted-tracked / untracked-existing / unverifiable configs route through the shared refusal gate; a tracked-clean present config stays untouched regardless of content, exactly as it already was on `main`. Flagged in `plan.md` at plan time and confirmed correct in code review round 2.
- **`--force` widened to cover all three refusal classes, but explicitly still does not override a malformed `.gitignore` canon block.** That's a separate, non-`--force`-overridable failure mode (AC-5b), unchanged by this task.
- **Kept the regenerated `dist/cli/index.js` in the diff** even though the spec's Affected Files table didn't list it, since `package.json` publishes it as the `canon` bin and `npm run build` regenerated it from the authorized source change. Code review confirmed zero drift and accepted it as in-scope.
