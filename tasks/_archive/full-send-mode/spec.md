# Spec: full-send-mode — Full-send mode: spec to draft PR with no human interrupts

> Written by: Claude | Review by: Codex
> Status: draft

## Problem

Canon's current end-to-end flow requires the human to engage at two interrupts: `human_spec_gate` (after spec_review, before plan) and `human_review` (after qa, before `--pr`). For tasks where the human wants to commit at task creation and let canon run to completion without babysitting — the strategy-memo use case James pushed for — there is no first-class way to skip both interrupts. Today's escape valve is hand-editing `status.json` (clear `human_spec_gate`, then run `canon run --pr` manually after QA), which is undiscoverable, error-prone, and bypasses the safety checks that the formal flow runs at `human_review`.

The intent in this use case is "I trust the grilling + canon's review chains end-to-end; open a draft PR when QA passes and let me look at the PR." Canon should provide that as a deliberate mode, not as an undocumented status.json edit.

> *Terminology note*: this spec uses "human" for the person at the keyboard, "operator Claude" for the conversational Claude session the human talks to, and "pipeline Claude" for the fresh Claude sessions canon spawns for plan/code-review/qa/spec-revision phases. The two Claude roles are different sessions with different responsibilities.

## Decision

Add a `full_send: boolean` field on `status.json` (default `false`). When `true`:

1. **At spec_review → planning**: the existing `human_spec_gate` interrupt is skipped (full-send implicitly forces `human_spec_gate: false`; setting both flags to conflicting values is silently overridden to "full-send wins").
2. **At qa → human_review**: instead of stopping at human_review and waiting for the human to invoke `canon run <id> --pr`, the dispatcher runs the existing `human_review` invariant gate (`checkPhaseGate`), then invokes the existing `--pr` flow inline. On success, advances `human_review.status = done` and prints a banner pointing at the draft PR URL.
3. **At any pipeline halt that is NOT a clean QA-done**: full-send respects the halt. Failed gates, auto-block, halted phases all behave as today — full-send only changes the post-clean-QA branch, never bypasses safety.

The flag is set via two CLI surfaces: `/canon-spec` (the conversational skill — propagates full-send intent into the pipeline invocation) and `canon run --full-send <id>` (the direct CLI flag, used either by operator Claude immediately after task creation, or retroactively mid-pipeline). The retroactive surface also writes `human_spec_gate: false`, so a task currently paused at the spec gate resumes immediately. `--reroute` clears `full_send` automatically and prints a message explaining why; humans who want to re-trust the rerouted result invoke `canon run --full-send <id>` again.

There is intentionally **no** `canon task new --full-send` flag. `canon run --full-send` handles both creation-time and mid-pipeline cases because the field is written before any phase runs. `/canon-spec`'s flow is: grill → `canon task new <id> "Title"` → write spec.md (with banner) → `canon run --full-send <id>`. The retroactive flag does all the field-setting work.

When `full_send: true` is set alongside `delicate: true`, the human must pass `--force` at the `canon run --full-send` invocation. The combination is not contradictory — canon's review chains still run with the upgraded model on delicate tasks — but the commitment is high enough to warrant explicit acknowledgment.

When `full_send: true`, `spec.md` carries a one-line banner near the top, written by `/canon-spec`:

```
> **Full-send mode**: This spec was produced in full-send mode.
```

The detailed explanation of what full-send mode means lives in `AGENTS.md` (general guidance, all readers), `CLAUDE.md` (operator-Claude detection guidance — when to pass `--full-send` based on human's natural-language signals), and `CODEX.md` (spec_review rigor note — full-send raises Codex's bar). The Codex spec_review prompt reads `full_send` from status.json and raises its rigor (full-send specs have no downstream human safety net before the PR opens; spec_review and code_review are the rigor layers).

## Non-Goals

- **Auto-merge**: canon does not merge the PR for the human. The draft PR is the artifact; the human flips it to ready and merges (or runs `canon run --ship`) at their discretion. Full-send removes the pre-PR interrupt, not the merge decision.
- **Auto-flip draft → ready**: the PR stays draft after full-send opens it.
- **CI-aware behavior**: canon does not inspect CI status, wait for green, or condition any full-send behavior on CI. Adopter CI is out of canon's contract.
- **New retry logic**: full-send reuses the existing `--pr` flow's idempotency. No new auto-retry, no new exponential backoff, no new retry counters.
- **Tear down + reopen PRs**: full-send never tears down an existing draft PR. Iteration (including post-reroute) updates the existing draft in place via force-push, matching today's `--pr` semantics.
- **A `canon task new --full-send` flag**: not added. `canon run --full-send` handles all paths into the flag-set state (creation-time via operator-Claude-driven workflow, mid-pipeline via direct human invocation). Adding the flag to `canon task new` would duplicate mechanism for no extra reach.
- **A `canon task set-full-send <id>` command**: humans who want to toggle the field without invoking the pipeline can hand-edit status.json (same escape valve canon already uses for other fields).
- **Grilling rigor changes**: full-send doesn't change how `/canon-spec` grills. M+ tasks get the decision-tree walk, S tasks get clarifying questions, per existing CLAUDE.md rules.
- **task_size gating**: full-send is allowed on S/M/L/XL. The human's "I trust this end-to-end" call is theirs to make regardless of size; the PR review on GitHub is still a real human checkpoint after full-send opens the PR.
- **Modifying the spec_review or code_review auto-iteration loops**: today's `changes_requested` routing (spec_review → spec via `promptSpecRevision`; code_review → implement) is unchanged. Full-send relies on these loops continuing to run as today.
- **Multi-branch bundles**: full-send only supports invocations where every task in the bundle resolves to the same branch (today's `--pr` constraint — `commitHumanReviewFiles` takes one `cwd` and opens one PR). A multi-branch full-send invocation is rejected by AC-4c's guard with an actionable message telling the human to split the invocation per branch. Generalizing the `--pr` flow to multiple branches/PRs is its own task and out of scope here.

## Amendment — Test isolation against real telemetry *(2026-05-20)*

Code review iteration 2 approved the implementation but post-QA inspection caught a test-pollution bug that the review missed: the new tests in `tests/run-task-safety.test.ts` (and possibly others) appended 11 `task-a | implement` entries to `docs/pipeline-invocations.md` in the worktree. The entries are uncommitted but would have shipped to `release/v1.4` on `--pr`.

Root cause: `scripts/run-task/metrics.ts:7` declares `METRICS_FILE = path.join(REPO_ROOT, 'docs/pipeline-invocations.md')` at module-load time. `REPO_ROOT` is resolved by `resolveRepoRoot()` in `env.ts` via `git rev-parse --git-common-dir` against the process cwd at module load. When tests spawn a child process to import canon modules (via the `runNodeInline` helper at `tests/run-task-safety.test.ts:229`), the child's cwd is the test's temp dir — but if the temp dir's git common dir is missing or the spawn falls back to `path.resolve(__dirname, '../..')`, REPO_ROOT resolves to the real canon-ai checkout. Any code path the child then exercises which writes telemetry pollutes the real file.

**New AC-13: Test isolation against real telemetry.** Tests MUST NOT write to the real repo's `docs/pipeline-invocations.md`, `docs/task-quality-log.md`, `docs/lessons-learned.md`, or any other real repo-root state. Specifically:

- (a) `metrics.ts` is restructured so `METRICS_FILE` is no longer a module-load-time constant. Either: (i) introduce a `CANON_METRICS_FILE_OVERRIDE` env var that `recordMetric` honors at write time (with fallback to `path.join(REPO_ROOT, 'docs/pipeline-invocations.md')`), OR (ii) replace the constant with a `getMetricsFile()` function called at each write so the path can be re-resolved per call. Either approach must allow tests to redirect telemetry writes to a temp path. Codex picks the cleaner of the two given the existing call shape.
- (b) `worktree.ts`, `state.ts`, and any other module that holds module-load-time path constants computed from `REPO_ROOT` must be audited: if a test invocation can reach the write path, the same override mechanism applies. Codex must enumerate every such file/constant in the handoff Changes table with the chosen override mechanism.
- (c) The new tests in `tests/run-task-safety.test.ts` (and `tests/task-cli.test.ts` if relevant) MUST set the override env var(s) to a temp path before invoking any canon module that could write telemetry. Adopt a shared `withTelemetryIsolation` test helper if more than one test needs it.
- (d) **Cleanup**: revert the uncommitted 11 `task-a | implement` lines in the worktree's `docs/pipeline-invocations.md` (and any other polluted lines surfaced during the audit). The final task branch must have `git diff release/v1.4...HEAD -- docs/pipeline-invocations.md` show ZERO lines added/changed.
- (e) **Regression test**: add a test that, after the test suite runs, asserts `git status -s docs/` reports no changes to `docs/pipeline-invocations.md`, `docs/task-quality-log.md`, or `docs/lessons-learned.md`. If the suite itself can't easily perform this assert (test ordering, etc.), an equivalent CI check in `.github/workflows/` is acceptable instead.

**Impact on existing ACs**: AC-12 test coverage stands; this is additive coverage that hardens the test isolation surface. No prior AC needs revision.

**Why this is amendment-level, not a follow-up**: The 11 polluted entries are real test artifacts that would ship to `release/v1.4` if we `--pr` from the worktree now. Fixing them in a follow-up means shipping pollution to adopters and recovering after the fact. Tests writing to real repo state is also a class of bug that compounds — every new test in this style would add to the corruption.

## Amendment — Bundle-level `every` semantics for spec-gate skip *(2026-05-21)*

Codex's asynchronous PR-level review on PR #95 (commit `717e5d9`) caught two P1 correctness bugs in the spec-gate skip logic. Both are the same shape: the dispatcher checks whether to bypass `human_spec_gate` using `some(t => t.full_send)`, meaning **one** full-send task in a bundle disables the gate for **every** task in that bundle — including tasks where the human did NOT opt into full-send. Mixed bundles silently auto-advance into planning/implementation for non-full-send tasks, contradicting the spec's design intent ("the human's 'I trust this end-to-end' call is theirs to make").

The two locations:

1. **`scripts/run-task/main.ts:2162`** — full-tier spec gate. The conditional currently reads (effectively) `if (tier === 'full' && statuses.some(s => s.full_send))` then skips the gate display block. This is wrong for mixed full/normal bundles.

2. **`scripts/run-task/phases/spec-review.ts:28`** — fast-tier spec gate. `fullSendActive = statuses.some(t => t.full_send)`. Same backdoor for fast-tier mixed bundles.

**New AC-14: Bundle-level gate-skip uses `every`, not `some`.**

- (a) Both call sites switch from `some(t => t.full_send)` to `every(t => t.full_send)` (or equivalent: `statuses.every(s => s.full_send === true)` — explicit `=== true` matches AC-4's status.json migration guidance).
- (b) The spec gate (G2) skip fires only when EVERY task in the invocation has `full_send: true`. If any task is normal, the gate fires for the whole bundle. Operators who want full-send on some tasks but not others can split into separate invocations, OR set `full_send: true` on every task in the bundle.
- (c) New tests cover the mixed-bundle case for BOTH tiers:
  - **Full-tier mixed bundle**: bundle of [full-send task A, normal task B] reaches spec_review.done → spec gate fires (display block visible, pipeline halts), NOT skipped.
  - **Full-tier all-full-send bundle**: bundle of [full-send task A, full-send task B] reaches spec_review.done → spec gate skipped, pipeline continues.
  - **Fast-tier mixed bundle**: same shape, in the fast-tier code path.
  - **Fast-tier all-full-send bundle**: same shape.
- (d) Single-task invocations are unaffected (a single full-send task = "every" trivially holds; a single normal task = "every" trivially false). The mixed-bundle case is the only behavior change.
- (e) `AGENTS.md`'s "Full-send mode" subsection (added in AC-10) gains a sentence: *"Bundle semantics: full-send applies per-task. To skip the spec gate for a bundle, every task in the invocation must have `full_send: true`. A single non-full-send task in the bundle re-engages the gate for all."* Same edit in `templates/AGENTS.md`.

**Why this is amendment-level, not a follow-up**: This is the exact class of bug full-send was supposed to NOT introduce (collapse safety for tasks that didn't opt in). Codex caught it after the initial PR landed. Shipping the fix in the same PR is the right scope — pulling it forward into a follow-up means adopters running 1.4.0 between the bug and the fix have a real risk of silent gate-skip on mixed bundles.

**Impact on existing ACs**: AC-2 (canon run --full-send sets fields), AC-4 (dispatcher tail), and the test surface in AC-12/AC-14 cover the new condition. No prior AC contradicts the `every` semantics; this amendment tightens the implementation to match the spec's design intent. The Non-Goal "task_size gating" is unrelated — bundle-level gating is per-task opt-in, not per-task-size restriction.

### Interaction Dependencies

- **`--ship` flow**: full-send invokes the same PR-creation path that `--ship` later relies on for cleanup. After full-send completes, the task is at `complete` (derived from `human_review.status === 'done'`); subsequent `canon run <id> --ship` then handles the merge + archive normally. No change to `--ship` is needed.
- **`--reroute` flow**: clears `full_send` per AC-6. The mutual exclusion with `--full-send` in a single invocation (AC-6) prevents conflicting intent in one command.
- **`--pr` flow**: full-send invokes the existing `--pr` logic (`commitHumanReviewFiles` + draft PR creation) rather than duplicating it. Force-push idempotency, PR-already-open detection (1.2.0 + 1.3.1), and the existing dirty-tree paths apply unchanged.
- **`canon task accept`**: orthogonal — operates on the implement phase. No interaction.
- **`canon task new`**: unchanged. No new flag. The default-behavior test in AC-12(c) pins that `full_send` defaults to `false` and `human_spec_gate` defaults to `true` — these are template-driven defaults, not flag-driven.
- **Bundle mode**: full-send applies per-task but the bundle is committed atomically. AC-5 specifies that if `commitHumanReviewFiles` fails, no task's `human_review.status` advances. Full-send requires all tasks in the bundle to share one branch (AC-4c); multi-branch bundles are rejected up front. This matches today's `--pr` flow, which already operates on one `cwd`/branch per `commitHumanReviewFiles` call — generalizing to per-task PRs across branches is out of scope (see Non-Goals).
- **`human_spec_gate`**: full-send sets this to `false` at the moment `canon run --full-send` is invoked (whether at first-run after creation or retroactively mid-pipeline). The existing spec-gate display logic at [main.ts:2079-2099](../scripts/run-task/main.ts:2079) gains a `full_send` short-circuit before the spec-gate stop is presented to keep the dispatcher branches readable.
- **`spec_review` and `code_review` iteration loops are unchanged.** Today these loops auto-iterate without human involvement: `spec_review` returning `changes_requested` routes back to `spec` where pipeline Claude (a fresh session, NOT operator Claude) revises via `promptSpecRevision` in [phases/spec.ts:17-29](../scripts/run-task/phases/spec.ts:17); `code_review` returning `changes_requested` routes back to `implement` where Codex iterates. Both loops are bounded by `MAX_REVIEW_LOOPS` and auto-block on overflow. Full-send does NOT modify either loop — the human is no more involved under full-send than they are today during these auto-iterations. If either loop hits auto-block, the pipeline halts as today and the human handles the escalation (raising `MAX_REVIEW_LOOPS` or pivoting). This is the load-bearing reason full-send is safe to ship: the rigor layers (Codex spec_review, Claude code_review) still run end-to-end exactly as today, just without an additional human-eyes pause between them.

### Data Model Changes

New optional field on `StatusJson`:

```typescript
interface StatusJson {
  // ... existing fields ...
  full_send?: boolean; // default false; when true, collapses human_spec_gate and
                       // auto-runs --pr after a clean QA. See AGENTS.md "Full-send mode".
}
```

Default value `false` (absent from status.json is equivalent to `false` for backward compatibility — `status.full_send === true` is the only "active" check anywhere). Both new and existing tasks have well-defined behavior: a task created before this feature lands (no `full_send` field) behaves identically to today.

## Known Risks

- **Dispatcher routing regression risk** *(orchestrator-routing surface; expect human iteration on the dispatcher hunks)*: the QA → human_review boundary is a routing decision that today is straightforward (always stop). Adding a conditional branch widens the surface. The mitigation is the test coverage in AC-12 (d)(e)(f) plus the fact that the new branch only fires when `full_send: true` (explicitly opted-in); a regression that affected non-full-send tasks would be caught immediately by canon-ai's own dogfood pipeline runs on this very task.
- **`--pr` failure semantics**: AC-5's "bundle atomicity preserved" requires careful ordering — the dispatcher must NOT write `human_review.status = 'done'` until every task in the invocation's `--pr` step has succeeded. Partial advances on partial failures would create stuck states. Codex should explicitly verify the write ordering in the implementation; the test in AC-12 (f) covers the failure path but the explicit ordering convention should be documented in a code comment in the dispatcher.
- **Reroute message wording**: the message in AC-6 is opinionated. If adopters find it preachy or misleading, the wording can shift in a follow-up patch. The mechanism (clear the flag, print SOMETHING) is the load-bearing piece; the exact prose isn't.
- **`/canon-spec` skill complexity**: the skill currently handles fast-tier (S) and full-tier (M+) flows differently. Adding full-send is a third axis. The skill should clearly enumerate the resulting matrix (S full-send, M+ full-send, S non-full-send, M+ non-full-send) and verify the branches are internally consistent. The skill's prompt itself doesn't need a code test, but Codex should confirm the SKILL.md flow is consistent across these four cases.
- **NL detection false positives in `/canon-spec`**: AC-8(b) detects "full send" / "full-send" in `$ARGUMENTS`. A task description that genuinely contains the phrase (e.g., a spec about adding full-send mode to canon — exactly this task) could false-positive. Mitigations: (a) AC-8(c)'s acknowledgment line gives the human a chance to redirect before grilling begins; (b) explicit `--full-send` flag is the unambiguous signal for scripted / disambiguating use; (c) operator Claude (per AC-10 CLAUDE.md guidance) can include reasoning about whether the human meant the mode vs. the content, and disambiguate accordingly. Codex should verify the skill's detection regex is narrow enough that obvious content-vs-mode cases don't false-fire; if in doubt, require the phrase to be at the start or end of `$ARGUMENTS`, or in a specific separator position.
- **Banner injection only fires via skill**: AC-9 specifies the spec.md banner is written by `/canon-spec`, NOT by template substitution. If a human invokes `canon run --full-send` on a task whose spec.md was written outside the skill (scripted use, direct CLI), the banner won't be inserted. This is acceptable for v1 — the status.json field is the load-bearing signal, and the banner is informational. If adopters complain, a follow-up could add banner-write into `canon run --full-send`.
- **Forward-compat with future gates**: if canon adds new human-interrupt gates later (e.g., a hypothetical `human_implement_gate`), the full-send umbrella should sweep them by definition. The implementation should establish the convention via a one-line comment in `types.ts` so future gate-additions know to opt into the full-send collapse.
- **Status.json migration**: existing tasks (in progress at the time 1.4 ships) won't have `full_send` in their status.json. The `?:` optional typing handles this, but the dispatcher checks should use `=== true` (not truthy) to make the absent-field case unambiguous. AC-4 phrasing reflects this.
- **Mutual-exclusion check placement**: AC-6's `--reroute --full-send` rejection lives in `parseArgs`. If the check fires after some side effect has already happened (e.g., `parseArgs` is called by other tools that don't expect die() during arg parsing), this could be a problem. The existing `die()` calls in `parseArgs` for `--expect` and unknown options suggest the pattern is fine, but Codex should verify no caller of `parseArgs` is expected to handle invalid-args gracefully.
