# QA Summary: operator-review-recovery

## What Changed

Canon now has two audited paths for recovering when an operator disagrees with an agent review — the "fix" path and the "bless" path. Previously, the only sanctioned recovery from a `code_review` `spec_gap` was `canon task phase <id> code_review pending`, which skipped spec re-validation, didn't refresh the plan, didn't increment `reroute_count`, and left no paper trail.

**Fix path (`--reroute` from spec_gap)**

`canon run --reroute` is now allowed from a `code_review` block with a `spec_gap` verdict, not just from `human_review`. The same full `rerouteFromHumanReview` machinery runs: increments `reroute_count`, resets `implement`/`code_review`/`qa`/`human_review` to pending, and for full-tier tasks also resets `spec_review`/`plan` and clears the session slot. The `## Amendment` ↔ `reroute_count` invariant is now enforced on this path — the round-numbering desync introduced by prior hand-resets is structurally closed.

**Bless path (`canon task accept` for review phases)**

`canon task accept <id...> spec_review --reason "<why>"` and `canon task accept <id...> code_review --reason "<why>"` are now valid. `--reason` is mandatory — missing or empty rejects the command. It writes a new `sanctioned` verdict (a distinct value that routes like approval but is always legible as an operator override), sets `operator_accepted*` audit fields, and appends a dated audit line to the task's `notes.md`. Existing escalations are preserved (the audit trail reads "spec_gap fired, then operator sanctioned," not erased).

**`sanctioned` verdict**

Recognized across all value surfaces: `Verdict` TypeScript union, runtime `VALID_VERDICTS`/`assertValidVerdict`, the CLI help list, and the scaffolded `status.json` `_verdict_values` string. `canon task phase … done sanctioned` rejects with a redirect to `canon task accept --reason` — the audit trail is guaranteed to be present whenever the verdict is.

**Recovery message rewritten**

The spec_gap block message — both the console output and the persisted escalation `reason` — now presents exactly the two audited paths (fix and bless) with full task IDs in both commands. The old `canon task phase <id> code_review pending` / `… done approved` recommendation is gone from both surfaces.

**Bundle-aware**

Both paths handle mixed blocked bundles. The fix path accepts an invocation when every task is `code_review blocked` and at least one carries `spec_gap`; it resets every member (including an approved-but-blocked sibling) to clean `pending`/`''`. The bless path iterates per task: non-advancing-verdict members get `sanctioned` + `operator_accepted*`; a member already carrying `approved`/`approved_with_nits` keeps its verdict and is only unblocked (honest approval is not relabeled as an override). The recovery message prints the full blocked-bundle IDs in both commands.

**Stale-sanction clearing**

A sanctioned review phase that is later reopened via `--reroute` or `canon task phase <id> <phase> pending` has its `operator_accepted*` fields and verdict cleared, so a stale override cannot mask a fresh review.

## How to Test

1. Run a task to the point where code review reports a spec problem (spec_gap). Read the on-screen block.
   - **Expected**: the message names exactly two options — `canon run <ids> --reroute` (fix) and `canon task accept <ids> code_review --reason "<why>"` (bless). No `canon task phase … pending` instruction appears.

2. **Bless path**: run `canon task accept <id> code_review --reason "false positive — ..."`.
   - **Expected**: the task advances to QA; `tasks/<id>/notes.md` gains a dated line with your reason text; `status.json` shows `verdict: "sanctioned"` and the three `operator_accepted*` fields. Try it without `--reason` — it must refuse.

3. **Fix path**: on a different task, amend `spec.md` with a `## Amendment` heading, then run `canon run <id> --reroute` from the spec_gap-blocked state.
   - **Expected**: the pipeline re-enters `spec_review`, re-plans, re-implements, re-reviews — the same full path as a `human_review` reroute.

4. After the reroute in step 3, trigger a second reroute later and check the amendment heading canon requires.
   - **Expected**: it requires `## Amendment Round 2`, and a leftover bare `## Amendment` from round 1 is rejected.

5. **Spec_review bless**: on a task where the spec reviewer was overly picky, run `canon task accept <id> spec_review --reason "..."`.
   - **Expected**: the task advances to plan; notes file records the override and reason.

6. **Mixed bundle**: with two tasks blocked together by spec_gap, run `canon task accept A B code_review --reason "..."`.
   - **Expected**: both tasks advance to QA. The one with spec_gap gets `sanctioned`; any already-approved sibling keeps `approved`.

## Decisions Made

- **`sanctioned` is accept-only** — `canon task phase … done sanctioned` is rejected. This guarantees the `operator_accepted*` + `notes.md` audit trail is never absent when the verdict is present.
- **Review artifact keeps the agent's original verdict** — `review.md` / `spec-review.md` retains `spec_gap`/`changes_requested` as the historical record; the sanction lives in the status audit fields, not a new artifact checkbox. The artifact-verdict-match gate (`checkPhaseGate`) is off the accept path by design.
- **Bless path preserves genuinely-approved siblings** — in a mixed blocked bundle, a sibling carrying `approved`/`approved_with_nits` keeps that verdict (the tree ships as-is; an honest review approval is not relabeled as an override). Only non-advancing-verdict members get `sanctioned` + `operator_accepted*`.
- **`operator_accepted_sha` on review phases is record-only** — unlike implement-accept (where the SHA gates auto-commit skip), there is no auto-commit on review phases; the SHA is a HEAD snapshot for audit only.
