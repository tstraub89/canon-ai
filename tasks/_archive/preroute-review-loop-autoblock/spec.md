# Spec: preroute-review-loop-autoblock — Auto-block review loops before the next revision cycle, not after

> Written by: Claude | Review by: Codex
> Status: draft

## Problem

The `spec_review` and `code_review` loop-cap auto-block checks fire too late: they run only at the *next entry* into that same review phase, which is always after the orchestrator has already burned a full revision cycle. There is no checkpoint between "the verdict that hits the cap arrives" and "a fresh Claude/Codex session starts rewriting the spec or re-implementing the code."

**Confirmed mechanism** (deterministic — traced through the current code, not inferred):

1. `runSpecReviewPhase()` (`scripts/run-task/phases/spec-review.ts:99-113`) checks `maxSpecIter >= specReviewLoopCap` only at the top of that function, i.e. only when `spec_review` is entered.
2. When Codex returns `changes_requested`, its `canon task phase` call runs `taskPhase()` → `updateReviewCounters()` (`src/task/index.ts:395-417`), which increments `iterations_current_loop` and persists it to `status.json` — before `runSpecReviewPhase()` returns control to the orchestrator loop.
3. Control returns to `main.ts`'s dispatch loop, which calls `checkAndRoute('spec_review', taskIds)`. Inside it, `case 'spec_review':` computes `anyChangesRequested` from a freshly re-read `statuses` (`main.ts:3066`) — already reflecting step 2's increment — and, when true and no reroute amendment is in progress, calls `routeBackTo(taskIds, 'spec')` at `main.ts:3112` unconditionally. There is no cap check anywhere in this path.
4. `routeBackTo('spec')` resets `spec` and every downstream phase to `pending` (`main.ts:2541-2576`). The dispatch loop's next iteration therefore runs the `spec` phase — a full Claude session that rewrites `spec.md` — and only once `spec_review` is re-entered afterward does step 1's check ever run.

So every time the cap is about to be hit, the pipeline unconditionally burns one more full revision cycle before a human gets a chance to decide whether to continue, rescope, split, or abandon. `code_review`'s `changes_requested` → `routeBackTo('implement')` path (`main.ts:3187-3195`, cap check in `runCodeReviewPhase()` at `phases/code-review.ts:256-271`) has the identical structure and the identical gap — confirmed by reading the same call sequence for that phase, and by the absence of any test asserting on `"routing back to implement"` (`grep -rn "routing back to implement" tests/*.test.ts` returns nothing, versus one existing but sub-cap test for the spec_review path).

This is a deterministic control-flow gap, not a flaky/environment-dependent one: given a bundle whose `spec_review.iterations_current_loop` (or combined `iterations_current_loop + preflight_rejections_current_loop` for code_review) is already at the cap, a `changes_requested` verdict on the next round routes back every time, with no branch that could do otherwise. The `code_review` gap also covers pre-flight rejections, which route back to `implement` through the same `anyChangesRequested` branch (`taskPhasePreflightRejected()` sets `status='done'`, `verdict='changes_requested'` — `src/task/index.ts:516-546`).

**Where the fix must live (Codex spec review round 2).** The round-1 revision proposed adding the cap check inside `checkAndRoute()` and *skipping* `routeBackTo`. Codex correctly rejected that shape: `autoBlockPhase()` marks only the review phase `blocked` (`state.ts:399-416`) and `deriveTopLevelStatus()` returns the first phase whose status is not `done` (`state.ts:367-380`), so with the rejected spec/implementation left at `done`, the blocked *review* phase stays current. The documented recovery (`MAX_REVIEW_LOOPS=<n> canon run <ids> --step`) would then dispatch that review phase again (`main.ts:3452-3467`), re-reviewing unchanged work — the requested revision would never run, and the same verdict could re-trip the raised cap forever. Verified independently: there is no guard anywhere that refuses to dispatch a `blocked` phase (`grep -n "'blocked'" scripts/run-task/**/*.ts src/task/index.ts` yields only the `autoBlockPhase` write at `state.ts:410`, the reroute detector at `main.ts:2351`, and `VALID_STATUSES`), which is exactly why today's recovery works and why the round-1 shape did not.

The corrected mechanism (see *Decision*) therefore lets `routeBackTo` run — it is what persists the continuation — and moves each loop's cap checkpoint to the **revision phase's own entry**, before that phase spawns its agent. This is a relocation of an existing checkpoint, not a new mechanism, and it needs no new `status.json` state: after the block, the revision phase is `pending` and is therefore the current phase, so a cap-raised resume dispatches the revision *first* and the review only after it completes.

**Consequence of that relocation — `reset-code-review` rejects the state the block now creates (Codex spec review round 3).** Moving the code-loop checkpoint to the `implement` entry changes which phase is current after a block: `implement` rather than `code_review`. `taskResetCodeReview()` derives the current phase and throws unless it is exactly `code_review` (`src/task/index.ts:1084-1088`), so the rescope fallback this task's own message advertises would fail with `reset-code-review only operates on tasks currently at code_review. Current phase: implement.` Shipping the relocation without widening that precondition ships a trap: a block whose documented recovery is refused by the tool that implements it. The widening is provably a no-op for every state the command accepts today — `deriveTopLevelStatus()` returns the first phase in `PHASE_ORDER` whose status is not `done` (`state.ts:367-373`), and `implement` precedes `code_review` in that order (`types.ts:12`), so a task deriving `code_review` already has `implement.status === 'done'`. The newly accepted state (`code_review` `blocked` while `implement` is current) is reachable only through this task's new checkpoint: the other two paths that mark `code_review` blocked — the `spec_gap` auto-block (`main.ts:3150-3185`) and the pre-flight-infrastructure auto-block (`code-review.ts:298-308`) — both fire with `implement` already `done`, so they still derive `code_review`.

The `spec_review` side has no such defect, and the reason is worth pinning rather than assuming: `taskResetSpecReview()` carries **no** phase precondition at all (`src/task/index.ts:1040-1072`) and unconditionally sets `spec` → `done`, `spec_review` → `pending`. It therefore already accepts the post-block state. That asymmetry between the two helpers is load-bearing after this change, so AC-17 locks it with a test instead of leaving it to a future symmetry cleanup that would silently recreate the trap on the spec side.

**Second consequence of the relocation — the two checkpoints persist different states, so "what runs first on resume" is state-dependent (Codex spec review round 4).** The relocation leaves two live checkpoints per loop, and they do not agree on what a resume does next. `autoBlockPhase()` sets only the *review* phase to `blocked` (`state.ts:399-416`), and `deriveTopLevelStatus()` returns the first phase in `PHASE_ORDER` whose status is not `done` (`state.ts:367-373`):

- **Revision-entry block** (the new checkpoint): the revision phase is `pending`, so it derives as current → a cap-raised resume runs the deferred revision, then the review.
- **Review-entry block** (the retained backstop, AC-11): that checkpoint is only reachable *after* a full revision cycle, so the revision phase is already `done` and the `blocked` review phase itself derives as current → a cap-raised resume dispatches the review directly (`main.ts:3453-3467`), re-reviewing work that was already revised.

An unconditional "a spec revision / re-implementation runs first" sentence — which is what round 3's AC-10 required of the single shared reason — is therefore **false at the backstop**, and `autoBlockPhase` persists that reason verbatim into `escalations[].reason`, so the wrong guidance is durable, not just printed. The correction keeps one evaluator per loop (one threshold, one counter formula, one recovery ordering) and has it resolve the resume-order clause from the revision phase's persisted status — the same fact the router reads — so the message and `deriveTopLevelStatus()` cannot disagree. AC-10 asserts both states; AC-11 asserts the backstop's message against the state it actually persists.

Both recovery *options* remain valid and runnable in both states, which is why only the resume-order clause is state-dependent: raising the cap is the right default at either checkpoint (at the backstop it re-reviews the freshly revised work rather than re-revising it), and the reset fallback is accepted in both — the backstop state (`code_review` `blocked`, `implement` `done`) derives `code_review`, exactly what `taskResetCodeReview()` accepts today without the AC-16 widening.

**Secondary defect — the `spec_review` auto-block message advertises an unsafe recovery.** The reason text at `phases/spec-review.ts:101-110` correctly leads with raising `MAX_REVIEW_LOOPS`, but its rescope fallback tells the operator to hand-edit `phases.spec_review.status` and `phases.spec_review.iterations_current_loop` directly in `status.json`. That instruction is incomplete against the canonical helper `taskResetSpecReview()` (`src/task/index.ts:1040-1071`, surfaced as `canon task reset-spec-review <id>` and documented at `docs/pipeline-orchestrator.md:121`), which additionally (a) archives the cumulative `spec-review.md` to `spec-review-prior-<n>.md`, (b) clears `phases.spec_review.verdict`, and (c) drops `sessions.claude_spec` so the next pass runs against a fresh Claude session. A raw file edit does none of the three — and because it bypasses `taskPhase()` entirely, it does not even get the stale-verdict clearing that `taskPhase()` performs on a `pending` transition (`src/task/index.ts:456-459`). The operator is left with a stale `changes_requested` verdict and a stale review artifact on disk, either of which a subsequent clean-exit evidence-recovery read can pick up and mis-route on. `code_review`'s message has the mirror-image defect: it names `canon task reset-code-review <id>` but never mentions raising the cap. This task centralizes both phases' reason text (AC-6), so both are corrected where they are centralized rather than duplicated into a second call site.

**Adjacent live defect found while tracing this one — recorded, not fixed here.** `runSpecPhase()` selects the spec-*revision* prompt via `tasks.some(t => t.specReviewVerdict === 'changes_requested')` (`phases/spec.ts:17`), but `routeBackTo('spec')` clears `spec_review.verdict` before that phase is ever entered, and `buildPipelineState()` reads `specReviewVerdict` fresh from disk on every loop iteration (`main.ts:224`). The condition is therefore unreachable through the normal loop, and `promptSpecRevision` never fires: every spec revision round receives the first-write `promptSpec` instead. Evidence from this task's own run: `tasks/preroute-review-loop-autoblock/.canon-run.log` lines 36 and 155 both print `Phase: spec (Claude writes spec)` — the first-write label — for what were rounds 1 and 2 of a *revision* loop. The implement side already avoids this trap by keying off counters rather than the verdict, with a comment saying why (`shouldUseImplementRevision()`, `phases/implement.ts:11-24`). This is a separate defect class (prompt selection, not loop-cap timing), it changes the prompt every full-tier spec revision receives, and it deserves its own red-first test and review — so this task records it in `docs/BACKLOG.md` (AC-14) and explicitly does not fix it (*Non-Goals*).

## Decision

Move each review loop's cap checkpoint from the **review** phase's entry to the **revision** phase's entry, so the block lands after the verdict is recorded and before the revision agent starts:

- **`spec_review` loop** → checkpoint at the top of `runSpecPhase()` (`phases/spec.ts`), before either `runClaude` call.
- **`code_review` loop** → checkpoint at the top of `runImplementPhase()` (`phases/implement.ts`), before `commitTaskArtifactsToBase`, `ensureBranch`, and the `runCodex` call.

When a checkpoint trips it calls `autoBlockPhase(taskIds, <review phase>, <count>, <reason>)` — the escalation and `auto_block_count` stay on the review phase that looped, matching today's records — and exits `2` without spawning an agent or mutating the revision target's own state.

`checkAndRoute()` is **not modified**: `routeBackTo` continues to run unconditionally inside both `anyChangesRequested` branches. That is deliberate and load-bearing — `routeBackTo` is what persists the continuation contract. After a block **at the new revision-entry checkpoint** the state is: revision phase `pending`, review phase `blocked`, review verdict cleared, so `deriveTopLevelStatus()` selects the revision phase as current. (The retained review-entry backstop persists a different state and therefore a different resume order — see *Problem*.) Consequences of a revision-entry block:

- **Raise the cap and resume** → the dispatch loop runs the deferred revision first, then the review. The continuation Codex asked for, with no new `status.json` field.
- **Resume without raising the cap** → the same revision-entry checkpoint trips again and re-blocks for free, with no agent spawned. The block is idempotent rather than bypassable by a reflexive `canon run`.
- **Any other path** that lands on a revision phase with the loop already at cap is covered by construction.

The existing review-entry checks in `spec-review.ts` and `code-review.ts` stay in place as a backstop, but must be refactored to call the same per-loop evaluator as the new revision-entry checkpoint, so the two checkpoints can never disagree on the threshold, the counter formula, the recovery ordering, or the wording. One evaluator per loop; both call sites consume it.

The single thing that legitimately differs between those two call sites is which phase a resume runs first, because they persist different states (see *Problem*). The evaluator resolves that clause itself, from the revision phase's persisted status — the same fact `deriveTopLevelStatus()` reads — rather than from a checkpoint flag handed in by the caller: a passed flag can contradict the router, a derived fact cannot. The clause names the revision phase while its status is not `done` (revision-entry) and the review phase once it is (review-entry backstop). For a bundle it names the revision phase only when **every** blocked task's revision phase is not `done`, per `docs/patterns.md` "Bundle-gate conditions must use `every()`, not `some()`, on per-task flags"; a mixed bundle is unreachable through the dispatch path, which `assertSamePhase()` (`main.ts:237`, called at `main.ts:3453` before every dispatch) refuses outright before any phase runs.

Both messages' recovery text is corrected while it is being centralized, so the two builders emit the same recovery shape:

- **`code_review`**: currently only tells the operator to run `canon task reset-code-review <id>` — it never mentions raising `MAX_REVIEW_LOOPS`. Lead with raising the cap as the default when review is still converging, and demote the reset command to the fallback for a genuine rescope.
- **`spec_review`**: currently leads with raising the cap correctly, but its rescope fallback is a hand-edit of `status.json` fields. Replace that instruction with `canon task reset-spec-review <id>`.
- **Both**: name which phase a resume actually runs first from the state just persisted — the deferred revision at the revision-entry checkpoint, another review round at the review-entry backstop. Not an unconditional promise of a revision; that is the round-4 correction (AC-10).

Neither builder instructs the operator to edit `status.json` fields by hand.

For that advertised fallback to be real, `canon task reset-code-review <id>` must accept the state the code-loop block now leaves behind. Its precondition widens by exactly one state — `code_review` `blocked` while `implement` is the current phase — and in that state it lands on the same end state a reset from `code_review`-current produces: `implement` `done`, `code_review` `pending`, loop-local counters zeroed, verdict cleared, `review.md` archived, `sessions.claude_review` dropped, `iterations_total` and `auto_block_count` preserved. This mirrors `taskResetSpecReview()`'s existing `spec` → `done` write and is a no-op for every state accepted today (see *Problem*). Every other current phase is still rejected, with the message unchanged. The two recovery paths then read cleanly against each other: **raise the cap** to re-run the deferred revision, **reset** to keep the current work product and get a fresh review of it.

Superseded by this revision (must not exist in the implementation): the round-1 design's cap checks *inside* `checkAndRoute()`, and its proposed `StatusJson[]`-native cap accessor in `scripts/run-task/policy.ts`. The latter is unnecessary — both revision-phase entries already have `TaskContext[]` in scope, so the existing `getMaxReviewLoops(tasks: readonly TaskContext[])` (`policy.ts:63-65`) is the right accessor.

## Non-Goals

- No change to `MAX_REVIEW_LOOPS` defaults or per-tier cap policy (`scripts/pipeline-policy.ts`'s `defaultMaxReviewLoops`).
- No `canon task set` field for the loop cap — it remains env-var only.
- No new `status.json` field, and no change to how counters increment or reset. The continuation contract is carried by the phase statuses `routeBackTo` already writes.
- No change to `checkAndRoute()`. Adding a cap check there is the superseded round-1 design (AC-12 asserts its absence).
- No fix for the `promptSpecRevision` unreachability described in *Problem*. AC-14 records it in `docs/BACKLOG.md`; changing which prompt every full-tier spec revision receives is a separate behavioral change needing its own red-first test and review.
- No change to `rerouteFromHumanReview()` (`main.ts:2346-2529`) — a structurally separate mechanism that resets phases inline and never calls `routeBackTo`. It already zeroes `iterations_current_loop` and `preflight_rejections_current_loop` for the phases it reopens (`main.ts:2461-2500`), which is why the new checkpoints are inert on a reroute (AC-13).
- No change to `code_review`'s `spec_gap` auto-block (`main.ts:3150-3185`) or its pre-flight-infrastructure auto-block (`code-review.ts:298-308`) — both already block before any re-implementation.
- No behavior change inside `taskResetSpecReview()` — it needs none (see *Problem*), and AC-17 pins that. The only change to `taskResetCodeReview()` is the one-state precondition widening in AC-16, required so the fallback the messages recommend is actually runnable; its archive/counter/session semantics are untouched, and no other current phase becomes acceptable.
- No symmetry cleanup across the two reset helpers. Their differing preconditions are deliberate after this change; harmonizing them (either direction) is a separate call.

## Known Risks

- **Delicate surface.** This changes phase-dispatch behavior for the two revision phases — the orchestrator hot path. `delicate: true` and `human_spec_gate: true` are set in `status.json` per `docs/patterns.md` ("Treat the `delicate` flag as load-bearing for the orchestrator's *own* surfaces"): an undetected bug here either blocks healthy tasks at their first revision or lets runaway loops through.
- **False block on a first pass.** The checkpoints now sit on phases that also serve first-time authoring/implementation. A guard that reads a lifetime counter (`iterations_total`) instead of the loop-local one would block every task whose earlier loops summed past the cap. AC-13 pins loop-local-only semantics, including the `iterations_total`-at-cap case.
- **Wrong counter for the spec loop.** `TaskContext.iterations_current_loop` looks generic but is populated from `code_review` only (`main.ts:218-227`). Reusing it in the `spec_review` evaluator would read the wrong loop and silently never block (or block on the wrong signal). AC-7's inverse-case test is the guard.
- **Combined-attempts formula drift.** `code_review` uses per-task `iterations_current_loop + preflight_rejections_current_loop` then max; computing max-of-each and summing over-blocks mixed bundles (a prior Codex P2 finding). Sharing one evaluator between both checkpoints (AC-6) is the structural mitigation; AC-7 is the behavioral one.
- **Side effects above the guard.** `runImplementPhase()` does real work before it spawns Codex — `commitTaskArtifactsToBase` on a first implement and `ensureBranch` always. Placing the checkpoint below either one would create a commit or a worktree for a run that is about to block. AC-2's "no commit created on the base branch" assertion is the guard.
- **Repeated escalations on repeated resumes.** Because a bare resume re-blocks (AC-5), each attempt appends an `escalations` entry and increments `auto_block_count`. That matches today's semantics (today's entry guard also re-blocks on every resume) and is honest durable signal — deliberately not deduplicated, consistent with the project rule that counters are never reset or suppressed.
- **Stale-evidence recovery after a hand-edited reset.** The AC-8/AC-9 message correction is not cosmetic. An operator who followed the old `spec_review` instruction sets `status`/`iterations_current_loop` by hand and leaves `phases.spec_review.verdict` at `changes_requested` plus a cumulative `spec-review.md` on disk; if the next Codex session exits cleanly without self-bookkeeping, clean-exit evidence recovery can read that stale artifact as the current verdict. Pointing at `canon task reset-spec-review <id>` closes that hole. The opposite failure is under-specification: a bundle operator who resets one task re-runs into a partially stale bundle, hence AC-8's per-task framing.
- **Over-widening the reset precondition.** The guard at `src/task/index.ts:1086` exists to stop an operator resetting `code_review` from an unrelated phase (e.g. a task still at `spec`, or already at `human_review`, where zeroing review counters and archiving `review.md` is wrong). Relaxing it to "current phase is `implement`" *without* also requiring `code_review.status === 'blocked'` would let a reset land mid-implementation on any healthy task. AC-16(c) is the guard against exactly that over-widening; AC-16(b)'s "existing tests unmodified" is the guard against under-noticing a behavior change on the accepted path.
- **`implement` → `done` written by a reset.** AC-16 has the command mark the implementation accepted-as-is so the next run reviews rather than re-implements. That is the mirror of `taskResetSpecReview()`'s `spec` → `done` and a no-op on today's accepted state, but it is a real state write on the new one: an operator who wanted a *re-implementation* rather than a re-review must raise the cap instead. The two paths are distinguished in the reason text (AC-8) and in the Human Test Plan, not just in code.
- **Message-assertion brittleness.** AC-8/AC-9/AC-10 assert substrings and their relative order inside human-readable prose. Keep assertions to the named commands, the `MAX_REVIEW_LOOPS` token, the canonical phase name in the resume clause, and their ordering — full-string equality would break on any future wording tweak.
- **The resume-order clause is the one state-dependent sentence, and asserting it once is what round 3 got wrong.** Both checkpoints share an evaluator but persist different states, so a single unconditional "revision runs first" is false at the backstop (see *Problem*). Two failure shapes to watch at implement time: hard-coding the clause inside the shared reason (AC-10(b) catches it), or restoring wording agreement by duplicating the reason per call site (AC-6(a) catches that). Deriving the clause from the revision phase's persisted status is what keeps the message and `deriveTopLevelStatus()` from drifting apart later — a caller-passed checkpoint flag would re-open exactly this defect the next time a third call site appears.
- **`spec` is a substring of `spec_review`.** An unanchored `assert.match(reason, /spec/)` passes in *both* states, so AC-10's discrimination silently evaporates while the test suite stays green. Word-boundary anchoring is load-bearing, not style; the same trap applies to any future assertion distinguishing the two phase names.
- **Integration-test agent stubs.** AC-1/AC-2/AC-4/AC-5 depend on fake `claude`/`codex` binaries that *log* their invocations; the existing `setupFakeCliTools` stubs are silent `exit 0`, so a test that forgets the logging variant would assert nothing and pass vacuously in both the red and green states. The invocation count is the load-bearing assertion, not the exit code — a pre-fix run can also exit `2` for the unrelated reason that the fake agent left the phase not `done`.
- **Recorded-not-fixed adjacent defect.** AC-14 records the `promptSpecRevision` unreachability without fixing it. The risk of deferring is that full-tier spec revisions keep receiving the first-write prompt until that task is picked up; the risk of absorbing it here is a diff spanning two unrelated defect classes plus an un-reviewed change to every full-tier revision prompt. Flagging it for the human at the spec gate is the intended resolution.

## Amendment

Code review round 2 (`review.md`) returned `spec_gap`. All 17 original ACs are met, with every correctness bug (F1, F3, F4, F5) fixed and independently re-verified red-first. Three findings survive that are not fixable at `implement` altitude:

- **R2-1**: `canon task accept <ids> code_review --force` — the documented "bless the gap" recovery — reports `Next phase: qa` while leaving the deferred revision phase `pending`, so the next `canon run` re-implements instead of running QA.
- **R2-2**: `canon watch <id>` reports a healthy cap-raised resume as `state=blocked`, exit `3`, for the entire revision window, because it scans for *any* phase with `status==='blocked'` without checking whether the orchestrator process that would clear it is still alive.
- **R2-3**: the `>=`→`<` cap-comparison rewrite is not `NaN`-equivalent to the original. `MAX_REVIEW_LOOPS=0` — an existing, intentionally-tested value (`tests/pipeline-policy.test.ts:92`, "a valid (suicidal) override") meaning "block on the very next attempt" — now falls through as inert, and any non-numeric value silently disables the guard on all four checkpoints with no warning.

Code review's own framing: R2-1 and R2-2, plus Codex's round-3 spec-review finding (`taskResetCodeReview()`'s precondition), started out looking like three instances of one class — a review phase persists `status==='blocked'` while a *different* phase (the revision phase) is actually current, and a consumer elsewhere assumed the review phase's own status was authoritative. That single-rule framing turned out to be wrong for one of the two consumer families, and the amendment's actual, final contract (below) is a deliberate **split**, not one rule:

- **State-derivation consumers** (`canon task accept`/`reset-code-review`'s preconditions, routing) — the **derived current phase** (`deriveTopLevelStatus()`), not a phase's own status field, is authoritative for "which phase is this task actually working on." This is what R2-1 and the round-3 `reset-code-review` finding fix.
- **Watcher block/settlement consumers** (`canon watch`'s classifiers, `--until`) — a **found `blocked` marker on any phase, gated by orchestrator process liveness** (not phase identity) is authoritative for "is this task genuinely stopped." Gating on the derived current phase instead — this amendment's own rounds 2–6 draft — silently stops reporting the primary block state (AC-20(D)), because that block leaves the *revision* phase current, not the *review* phase. See R2-2 below for why liveness, not phase identity, is the correct signal for this family.

This amendment fixes every consumer review found violating either half of the split. It also closes F13 (three stale operator-guidance surfaces, one of which — `recovery.md` — ships to adopters and now contradicts the project's own "never reset the counter" rule for this exact state) and F11 (a wording nit riding along since the reason builders are already being touched).

### R2-1 — `canon task accept --force` from a loop-cap block

Two independent fixes, since one (the message) covers every caller and the other (the write) covers only the one new state — plus a bundle-semantics decision the write's per-task nature exposes:

1. **Message.** `taskAccept`'s "Next phase" line (`src/task/index.ts:813-816`) is a hardcoded ternary on `phaseArg` (`spec_review`→`plan`, else→`qa`), not derived from state. Replace it with `deriveTopLevelStatus(status)`, read *after* the accept write. This is a strict generalization, not a special case — in every state this replaces, the ternary and the derived value already agree; the new state is simply the first one where they don't.
2. **Write — one predicate, not "not done."** "The preceding phase is not `done`" is too wide: it also matches `in_progress` (the AC-20 healthy-resume shape, where the revision agent may genuinely still be running) and, since `--force` skips `priorIncompletePhases()` entirely (`index.ts:686-693`), it can also match a bundle member with *two or more* incomplete phases (e.g. `plan` and `implement` both `pending`), where writing only the immediate predecessor `done` would leave an earlier phase (`plan`) incomplete and current. The correct, single predicate is: the phase immediately preceding the one being accepted (`spec` for `spec_review`, `implement` for `code_review`) is **both** `pending` **and** itself the task's derived current phase (`deriveTopLevelStatus(status)` equals that preceding phase) — the second conjunct is what rules out the multi-incomplete case, since `deriveTopLevelStatus` would return the *earlier* incomplete phase instead. Only when both hold does `--force` also set that preceding phase's `status` to `done`, mirroring `taskResetCodeReview()`'s existing `implement.status = 'done'` write (`src/task/index.ts:1102-1104`). Outside this exact predicate, `--force`'s write is unchanged: it still only writes the accepted phase's own entry. `priorIncompletePhases()` (`index.ts:381-385`), which gates the *non*-`--force` path, is not touched.
3. **Bundle semantics.** `taskAccept(ids, ...)` holds one independent `StatusJson` per task (`index.ts:601-612`) and validates shared worktree/base branch, but not that every task derives to the same phase. Applying fix 2 per-task can leave bundle members at different derived phases after the write, for which one printed "Next phase" line would be false for some members. Decision: compute each task's post-write derived phase first: if they are not all identical, refuse the whole accept with an error naming the divergent tasks and phases (no partial write), matching the discipline `assertSamePhase()` already applies elsewhere to mixed-phase bundles; only when they agree does the accept proceed and print the single shared "Next phase" line. This bundle-divergence refusal is a second, explicit exception to "unchanged outside the AC-18 predicate" (AC-19) — a mixed-next-phase bundle is a genuinely new, reachable shape (today's `taskAccept` writes each accepted review entry independently with no shared-derived-phase check, `index.ts:748-765`), and this task changes it from "succeeds independently per task" to "refused atomically." AC-19 names both exceptions rather than treating the second as covered by "unchanged."

### R2-2 — `canon watch` misreports a healthy resume as blocked

`findFirstBlockedPhase()` (`src/cli/commands/watch.ts:102-107`) scans all of `PHASE_ORDER` for any `status==='blocked'`, and has **three** call sites, not two: `classifyAttach:280-283` and `classifyIdle:330-333` return `{kind:'auto_block'}` (→ exit `3`, `watch.ts:497`/`670-671`) on any hit, before the liveness probe; `orchestratorStillProgressing()` (`watch.ts:406-414`) also calls it at line `413` and returns `false` ("not progressing") on any hit — which during a live cap-raised resume with a momentarily stale heartbeat (the synchronous no-heartbeat window the function's own comment documents) lets the idle classifier fall through to a false `step_done`/settled read instead of correctly waiting, exactly the outcome that function exists to prevent. A cap-raised resume leaves the just-completed review phase `blocked` while the revision phase (now `in_progress`) is genuinely current, so all three call sites currently misread the revision window as blocked or settled.

A **separate** mechanism has the same defect: `isPhaseSettled()` (`watch.ts:97-100`) treats any `blocked` phase entry as settled regardless of whether it's current, and `--until <phase>` reads that result at three points (pre-attach `watch.ts:531-539`, and the two polling reads at `:597-604`/`:653-660`). During the exact fixture-A resume state, `canon watch <id> --until code_review` exits `0 reason=until` immediately — before the resumed review actually runs — because it sees the stale `blocked` review-phase entry and calls that "settled," independent of `findFirstBlockedPhase()`'s classification path entirely.

**Neither "any blocked phase" nor "current-and-blocked" is the right test on its own — liveness is.** A revision-entry block (the primary, most common shape this task creates) leaves the review phase `blocked` while the *revision* phase is current (original AC-3) — so gating on "the current phase's own status is blocked" misses it entirely: `classifyAttach`/`classifyIdle` would find no `in_progress` phase and no blocked *current* phase, and report `nothing_to_watch` for a task that is genuinely, terminally auto-blocked. Gating on "any phase blocked" (today's behavior) over-fires instead, on the live pre-flight window described above. Both phase-status-only rules are wrong in one direction; the fact that distinguishes them correctly in every case is liveness, not phase identity: every call site that ever writes a `blocked` status calls `process.exit(2)` in the same synchronous stack immediately afterward (confirmed by inspection of all seven current `autoBlockPhase` call sites — the `spec-review.ts` wrapper, one in `spec.ts`, two each in `implement.ts` and `code-review.ts`, and one in `main.ts:3183-3184` — every one is followed by `process.exit(2)` with no intervening branch). So a genuinely blocked task **never** has a live orchestrator process, regardless of which phase carries the `blocked` status or whether that phase is current; a live pre-flight or resume window, by construction, always does.

**Executed confirmation (runtime-dependent mechanism).** This is a timing interaction between the revision's `done` write, review-phase dispatch/pre-flight, and orchestrator PID lifetime — not a fixed-input deterministic branch — so it needs executed confirmation, not just the source trace above. Forced against the current tree: with `implement.status='done'`, `code_review.status='blocked'` and current, and a live PID with a fresh heartbeat, `classifyAttach` returns `auto_block` and `canon watch <id> --until code_review` exits `0 reason=until` — reproducing the false-terminal read exactly as described, confirming the mechanism is real and the repro is executable (not environment-bound).

There are three liveness outcomes, not two, and the existing code already distinguishes them: a resolved single PID (alive or dead), and an **ambiguous** state where `.canon-pid` and the heartbeat name different PIDs that are *both* alive (`ctx.ambiguousPid`, `run-context.ts:99-118`) — deliberately left with `resolvedPid == null` for that case. But today, in both classifiers, the block check runs *before* the ambiguity check: `findFirstBlockedPhase()` returns `auto_block` immediately (`watch.ts:280-283`/`330-333`), and `ctx.ambiguousPid` is only consulted in the branch below, unreached once a block was already found (`watch.ts:285-292`/`335-342`). So today, for a task that is both blocked and ambiguous, `auto_block` already wins over `ambiguous_pid` — the existing refusal-to-attach guard is already skippable by a stale block marker, independent of this amendment. `resolvedPid == null` is not itself a safe stand-in for "not live" — it is also true for a live-but-ambiguous pair — so folding liveness into the block check without also reordering would make that pre-existing precedence bug worse, not better, by making more states resolve through the block branch.

Fix, applied at all four sites (the three `findFirstBlockedPhase()` callers plus `isPhaseSettled()`): keep the existing "is any phase `blocked`" detection unchanged, but **move the ambiguous-PID check ahead of it** — `classifyAttach`/`classifyIdle` must resolve `ambiguous_pid` first and only fall through to block classification when `ctx.ambiguousPid` is not set. This is a deliberate reordering of today's branches, not a preservation of today's precedence. In the remaining, non-ambiguous case, classify a found block as terminal only when the orchestrator is confirmed not live — `ctx.resolvedPid == null || !probeAlive(ctx.resolvedPid)` (the same liveness signal `orchestratorStillProgressing()` already uses, `watch.ts:406-414`); `ctx.ambiguousPid` no longer needs to appear in this specific condition once the reorder guarantees it has already been ruled out. When a single PID is live, treat a found `blocked` phase as still progressing, the same outcome a live PID already produces today for a stale heartbeat. This drops the derived-current-phase check this amendment carried through rounds 2–6 — it was solving the wrong half of the problem, and liveness alone is both necessary and sufficient (`deriveTopLevelStatus` is not needed for this classification decision at all). `orchestratorStillProgressing()` needs the opposite trim: once it has confirmed the PID is alive, its existing `findFirstBlockedPhase(status)` check (`watch.ts:413`) must be deleted rather than reordered — a confirmed-live process is progressing regardless of any blocked marker, stale or current. `isPhaseSettled()` does not currently take a liveness probe; threading one through (or moving its `--until` call sites to check liveness alongside it) is a plan-phase call.

### R2-3 — degenerate `MAX_REVIEW_LOOPS` values

Three things must change together, not just the two parse sites — the amendment review's round-1 pass caught that fixing only the config layer leaves the guard inert, since the shared evaluator has its own, stricter cap check:

1. **Parse sites** (`scripts/run-task/policy.ts:25`, `scripts/run-task/env.ts:136`) run `Number.parseInt(process.env.MAX_REVIEW_LOOPS, 10)` unvalidated. `Number.parseInt` alone is not a sufficient validator: it truncates rather than rejects (`Number.parseInt('1.5', 10) === 1`, `Number.parseInt('2junk', 10) === 2`), so checking `Number.isInteger()` on its *result* never catches a decimal or trailing-junk input — the check must run against the untouched raw string before any truncating parse (e.g. a strict `/^-?\d+$/` test, or `Number(raw)` + `Number.isInteger`, which — unlike `parseInt` — evaluates to `NaN` for `'1.5'` and `'2junk'`). Valid values are integers `>= 0`; invalid values `warn()` naming the rejected raw value and fall back to `null`, so `defaultMaxReviewLoops(nominalSize)` (`pipeline-policy.ts:139-141`) applies as it did before this task. Both parse sites must apply the identical rule.
2. **The evaluator's own cap guard** (`isUsableCap()`, `scripts/run-task/review-loop.ts:7-9`) currently returns `Number.isInteger(cap) && cap >= 1` — it rejects `0` independently of whatever policy/env now allow through. Change the floor to `cap >= 0` so a validated `0` reaches an actual block instead of being separately filtered out one layer downstream. This is the change AC-21's checkpoint-level test (below) exists to pin, since a policy-only fix cannot catch it.
3. `0` stays valid throughout (preserving the existing, tested "suicidal override" semantics at `tests/pipeline-policy.test.ts:92`); only `NaN`/non-integer/negative values are rejected and warned on.
