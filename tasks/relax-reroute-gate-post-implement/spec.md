# Spec: relax-reroute-gate-post-implement — Allow `--reroute` from any phase after a completed `implement` round (`code_review`, `qa`, `human_review`)

> Written by: Claude | Review by: Codex
> Status: draft

## Problem

`rerouteFromHumanReview()` (`src/orchestrator/main.ts`) admits `--reroute` in exactly two cases:

1. Every named task's current phase is `human_review`; or
2. Every named task's current phase is `code_review` **and** that phase's status is `blocked` **and** at least one named task carries `code_review.verdict === 'spec_gap'`.

Anything else dies with `--reroute requires either all tasks at human_review, or all tasks at code_review blocked with at least one spec_gap verdict.` Two real operator scenarios therefore have no sanctioned path:

- **`code_review` auto-blocked on the loop cap with `changes_requested`.** The review-loop cap fires (`autoBlockPhase`, documented under §"Phase Routing + Auto-Block" in `docs/pipeline-orchestrator.md`) and the task sits at `code_review` `blocked` with verdict `changes_requested`. The churn is often the signal that the *spec* is wrong, not just the implementation — but the gate only recognises a `spec_gap`-flavoured block.
- **`code_review` has finished and `qa` has not.** New information arrives while the task's current phase is `qa` (`pending` or `in_progress`). There is no reroute entry at all for `qa`; only a fully-reached `human_review` qualifies.

The available workarounds are all bad: hand-edit `code_review.verdict` to `spec_gap` (bypasses the `canon task` helpers that `AGENTS.md` §Conventions makes the sanctioned route for phase-state changes); or run `canon task accept <id> code_review --reason "…"`, which records the operator-only `sanctioned` verdict — wrong provenance for "the operator is amending the spec" — and still leaves the task to burn a full QA pass and a `human_review` rejection just to reach the existing gate.

The gate's shape is an accident of how it grew, not a decision. It started as `human_review`-only; task `operator-review-recovery` (PR #151) bolted on the `spec_gap` case because that specific escalation needed a re-spec path. Neither addition considered the general question of when a reroute is *mechanically* safe. It is safe exactly when a completed `implement` round exists to build a delta against — which is precisely the set `{code_review, qa, human_review}`.

### Round-1 `spec_review` outcome (design narrowing)

The first draft of this spec paired the gate widening with a **generalised exemption**: any named task lacking an `## Amendment` section would be auto-marked `implement.reroute_exempt`, so a bundle could reroute with only one member amended from any entry state. Codex's round-1 review blocked that on two counts, both correct:

- A `spec_gap` task with no Amendment would be auto-exempted and sent back through implementation against an unchanged spec — but `spec_gap` *means* "implementation cannot resolve this; the root cause is in the spec." The exempt-task prompt can only preserve review findings; it cannot repair a spec gap.
- The widened gate admits `code_review` with status `pending`, where `verdict` is `''`. Auto-exempting such a task would store `reroute_exempt_prior_verdict = ''`, and `isAdvancingPriorVerdict('')` is false, so `promptImplementReroute()` would tell Codex "your prior review findings at `tasks/<id>/review.md` remain binding — read that file and address ALL findings." For a task whose `code_review` never ran, `review.md` is the untouched scaffold stub (`canon task new` copies every `.canon/templates/` file at creation) with placeholder AC rows and no findings. The instruction is unfollowable at best and an invitation to invent findings at worst.

Both findings share one structural root: **granting an exemption from a state whose prior review does not exist or cannot be resolved by implementation.** The existing layer already owns this concern correctly — the `spec_gap`-entry exemption added by task `recovery-surface-hardening` (PR #155) is scoped to a state where every member has a real, completed prior review and the gap tasks are required to amend. Rather than harden a general rule against those two states, this spec **drops the exemption generalisation entirely** and changes only the admission gate. The exemption mechanism ships unchanged.

### Round-2 `spec_review` outcome (scope expansion — accepted)

Round 2 raised two blocking findings. Both are **scope-expansion**, not fine-tuning: each named a surface the spec had not covered, not a case it had covered imprecisely. Both are accepted in full. Together they widen scope from "the gate plus its operator-facing docs" to "the gate, every operator-facing statement of the rule, and every *agent-facing* statement that asserts a `human_review` origin."

1. **A second, independently-rendered CLI help surface.** `printUsage()` in `src/orchestrator/cli.ts:151-159` prints its own `--reroute` block — "Reset a task from human_review back into the post-review fix path" — reached through `parseArgs()`, entirely separate from the top-level help in `src/cli/index.ts:104-110`. This is the surface an operator actually sees from `canon run --help`. Round 1's AC-9 named only `src/cli/index.ts`, so implementing the declared file list would have shipped stale runtime help while AC-9's `src/`-wide grep failed. Added to the surface list.

2. **The reroute prompts assert a `human_review` origin that the widened gate makes false.** Round 1 froze the reroute prompt templates and builders on the theory that admission and prompting are independent. They are not: newly-admitted tasks flow through those same prompts, and the prompts state as fact that a human reviewed or *tried* the previous implementation. On a reroute from `code_review` `pending`, nobody reviewed anything and nothing was ever tried. Confirmed by reading the rendered output in `tests/run-task-prompts.golden.json` — every one of the six reroute golden entries carries at least one such claim. This is adopter-visible agent instruction, not an internal identifier: it tells a fresh phase agent that a review happened, which invites it to hunt for feedback that does not exist.

The fix for (2) is to **generalise the wording, not to persist the entry phase** — and, separately, to keep the actor a **human**, not an "operator" abstraction. After the reset loop runs, `code_review` / `qa` / `human_review` are all back to `pending`, so the entry phase is unrecoverable at prompt-render time; naming it would require a new `status.json` field, which Non-Goals forbid. Every admitted state shares one true description: *a human decided this task needed a spec amendment, wrote it, and rerouted the task after a completed implementation round*. That claim is true in every admitted state, unlike "a human reviewed/ran/tried the prior implementation," which is false in three of the five newly-admitted states. The narrowing is specifically to the false part — *what the human is claimed to have reviewed* — not to the presence of a human at all: reroute is, and remains, a human decision, and the prompt wording must keep saying so. The cost of dropping the false claim is real and accepted — see *Known Risks*.

### Round-3 `spec_review` outcome (scope contraction — finding accepted)

Round 3 raised one blocking finding, and it is correct: **AC-11 was withdrawn, along with every QA-side change it pulled in.**

The withdrawn AC came from the round-2 *sweep*, not from a reviewer — it claimed `src/orchestrator/prompts/templates/qa.md`'s `Human reroute?` bullet carried the same falsified-premise defect as the reroute prompts, because a task rerouted from `code_review` or `qa` would truthfully answer `No`. That reasoning was wrong. `Human reroute?` is not an any-reroute metric that the widened gate blinds; it is deliberately a *human-review-rejection* metric:

- `docs/task-quality-log.md` defines the column as "did the human reject at `human_review` and force a re-implement?"
- `docs/decisions.md` §"Task quality-log row upserted at the qa → done transition" explicitly rejects deriving the column from `implement.reroute_count` **because** that counter "conflates genuine human-review reroutes with blocked code-review `spec_gap` recovery," and states the rule "Do not derive `Human reroute?` from a reroute counter." Distinguishing a human-review reroute from any other reroute is the settled *point* of the column.
- The `ship-shared-doc-dirt-preservation` row is a live instance of that distinction working as intended: `Human reroute?` is `No` while its notes record a `spec_gap` reroute.

So `No` for a `code_review`/`qa`-origin reroute is the correct answer under the existing definition, not a blind spot. AC-11 would have made the same column mean two incompatible things across historical and future rows while leaving its label, parser, and docs unchanged — redefining a settled metric by editing one prompt string. The alternative the reviewer offered — reopen the decision and specify a coherent replacement metric with its own name, documentation, and historical-row treatment — is a separate task with its own design, not a rider on a gate widening.

This is a **contraction**, and it does not weaken the widened gate: nothing in the admission change depends on the quality log. `src/orchestrator/prompts/templates/qa.md`, `src/orchestrator/quality-log.ts`, `docs/task-quality-log.md`, its `templates/` mirror, and the two `promptQa*` golden entries are all now out of scope and must appear in neither the diff nor the handoff Changes table.

## Decision

**Widen the admission gate. Change no routing or state behaviour; correct every statement of the rule and every prompt claim the widening falsifies.**

`--reroute` is admitted when **every** named task's current phase (`getCurrentPhase()`, which delegates to `deriveTopLevelStatus()` rather than trusting the top-level pointer) is one of `code_review`, `qa`, or `human_review` — in any combination of that phase's `status` and `verdict`. Members of one invocation may sit at *different* phases within that set; the reset loop already normalises them.

That set is exactly "a completed `implement` round exists": the derivation returns the first phase in pipeline order whose status is not `done`, so a current phase of `code_review` or later implies `spec`, `spec_review`, `plan`, and `implement` are all `done`. This is the invariant reroute depends on — it sets `implement.rerouted = true` so the reroute prompts read `spec.md` for new Amendment sections, compare against the prior implementation, and update only the delta. Without a completed implementation there is no delta to compute.

Every *behavioural* mechanism downstream of admission is untouched:

- **The Amendment pre-flight is the real expression of operator intent, and its scope does not change.** Every named task must carry `## Amendment` (round 1) or `## Amendment Round N` (round N≥2, where N is that task's `reroute_count + 1`) in the active `spec.md`, with one exception: on a spec_gap-entry reroute, non-`spec_gap` members are exempt. `--force` still bypasses the abort with one warning per failing task.
- **The exemption predicate is unchanged.** `implement.reroute_exempt` / `reroute_exempt_prior_verdict` are still written only on a spec_gap-entry reroute (every named task at `code_review` with status `blocked` and at least one carrying verdict `spec_gap`), and only for the non-`spec_gap` members. The set of `status.json` states that produce an exemption is identical before and after this change: that predicate is a pure function of the statuses, and any state satisfying it was already admitted by the old gate, so widening admission cannot feed it a new state. This is the direct answer to both round-1 blocking findings — a `spec_gap` task still cannot ride along unamended, and no never-reviewed task can become exempt.
- **The reset loop is unchanged.** It already blanket-resets `implement` / `code_review` / `qa` / `human_review` (plus `spec_review` / `plan` on full tier) without branching on the entry phase.
- **The reroute prompt *routing* is unchanged.** The same three reroute templates render for the same phases in the same order. Only their wording changes.

Three classes of statement must change to stay truthful:

- **The operator-facing rule** — five authored surfaces state admission as `human_review`-only or as the two-case pair. All five must state the new rule.
- **The reroute banner** — currently hard-codes the entry state as either `human_review` or `code_review spec_gap`, which becomes a lie for every newly-admitted state. It must be derived from the actual per-task entry state, and the abort message must describe the new rule.
- **The reroute prompts** — must describe a human-directed post-implement amendment (a human decided to reroute and wrote the amendment) instead of a human *review of the prior implementation* that may never have happened. The actor stays a human in both the old and new wording; only the specific false claim — that a human reviewed, ran, or tried the shipped implementation — is dropped.

The consequence of keeping the exemption narrow is deliberate friction: rerouting a **bundle** from a widened entry state requires every member to carry its own Amendment, or `--force`. That matches today's `human_review` behaviour exactly, so nothing regresses; extending sibling exemptions to the new entry states is left to a future task with its own design for the no-prior-review case.

**A fourth thing must be added, not merely corrected: explicit guidance that rerouting is a human decision.** Widening admission makes `--reroute` reachable from states an autonomous pipeline actor could plausibly reach *on its own* — a task auto-blocked at `code_review` with `changes_requested`, or sitting at `qa` `pending` — in a way `human_review`-only admission never was (a human is definitionally already in the loop by the time a task reaches `human_review`). Nothing in `rerouteFromHumanReview()` can check "did a human decide this" — `--reroute` is, and remains, an ordinary CLI invocation with no interactive confirmation step, matching today's behavior. The safeguard is therefore documentation, not code: the surfaces an agent driving canon actually consults before acting must say plainly that deciding to reroute is a human call, not something the agent infers or decides on its own initiative — even under `--full-send` or another autonomous mode.

## Non-Goals

- **No generalised sibling exemption.** Auto-exempting an un-amended task from a non-`spec_gap` entry state is explicitly out of scope, for the two round-1 review reasons above. The only exemption remains the spec_gap-entry one.
- **No reroute from `implement` or earlier.** A current phase of `implement` means `implement.status` is `pending` or `in_progress`: either the task has a plan but no implementation (the request is really a plan revision), or it is mid-implementation (rerouting drops it into a half-written state). `spec`, `spec_review`, and `plan` are unsupported for the same reason. The gate must keep rejecting all of them.
- **No reroute from `complete`.** A task whose every phase is `done` (`getCurrentPhase()` returns `complete`) stays rejected, as today.
- **No new CLI verb, flag, or `--reason` parameter**, and no new `status.json` field. The Amendment section remains the sole human-intent artifact.
- **No persisted entry phase, and therefore no entry phase named inside a prompt.** The reroute banner (AC-7) reports the entry state because it is emitted *before* the reset, while the state is still readable. The prompts render *after* the reset, when it is gone. Making prompts name the entry phase requires persisting it; that is a separate task. Reroute prompts become phase-neutral, not phase-aware.
- **No change** to `verifyRerouteAmendment()`'s round-heading contract, `checkRerouteEvidence()`, `getRerouteExemptInfo()`, `isAdvancingPriorVerdict()`, the reroute prompts' *routing* or *structure* (which template renders when, their step lists, their heading contracts), `detectTier()`, `canon task accept`'s `sanctioned` bless path, or `reset-spec-review` / `reset-code-review`.
- **No change of any kind to the `Human reroute?` quality-log metric** — not its label, not its parser, not its historical rows, and not the QA prompt's answer guidance. It is a human-review-rejection metric by settled decision, and it stays one (see the Round-3 subsection above). Redefining it, renaming it, or replacing it with an any-reroute metric is a separate task.
- **No rename of the `## Human Reroute` heading in `docs/pipeline-orchestrator.md`.** Its body is rewritten, but three shipped code paths cite the section by name (`src/cli/index.ts:110`, `src/orchestrator/cli.ts:159`, and the abort message at `src/orchestrator/main.ts:2511`). Renaming it breaks all three pointers for no benefit. This does **not** extend to `.claude/skills/canon-pipeline/SKILL.md`'s `### 6.` heading, which nothing pins and which AC-9(a) does rename — the two headings differ in whether shipped code depends on the text, not in how stale they read.
- **No rewrite of any dated record.** `docs/BACKLOG.md` and `CHANGELOG.md` state what was true on a date — several entries preserve the pre-widening rule and its error text on purpose — and must not appear in this task's diff at all. The orchestrator-appended telemetry docs (`docs/task-quality-log.md`, `docs/lessons-learned.md`, `docs/pipeline-invocations.md`) will gain this task's own rows at QA as usual; editing an *existing* line in them is out of scope. See AC-9 Rule 1.
- **No CLI-level enforcement of the human-decision requirement.** `--reroute` gains no interactive confirmation prompt, no new flag, and no code-level check for "was this human-decided" — that would be undetectable mechanically (a CLI invocation carries no such signal) and is not this task's mechanism anyway (see AC-13). The requirement is documented, not enforced in code, matching how `--reroute`'s other operator-facing expectations (e.g. writing an Amendment section yourself, not for an agent to fabricate) already work today.
- **No fix for the pre-first-QA uncommitted-artifact window.** Rerouting from `code_review` or `qa`-pending happens before the QA-end commit, so task artifacts may be uncommitted (see *Known Risks*). Reroute performs no git operation, so nothing is destroyed; closing that window is a separate structural change already tracked in `docs/patterns.md` §"Operator git surgery before first QA…".

## Acceptance Criteria

- [ ] **AC-1 — admission widened.** `--reroute` is admitted, and proceeds to reset `status.json`, when every named task's current phase is `code_review`, `qa`, or `human_review`, for any `status`/`verdict` on that phase. Verified by unit tests in `tests/run-task-reroute-preflight.test.ts`, each with the required Amendment heading present, covering at least: `code_review` `blocked` + verdict `changes_requested` (the loop-cap auto-block); `code_review` `changes_requested` + verdict `changes_requested` (the auto-loop state); `code_review` `in_progress` (an orchestrator that died mid-review); `code_review` `pending` + verdict `''` (review never ran); `code_review` `done` + verdict `approved` with `qa` `pending`; `qa` `in_progress`; `human_review` `pending` (pre-existing case, must still pass); `code_review` `blocked` + verdict `spec_gap` (pre-existing case, must still pass). Each asserts exit 0 and that the written `status.json` shows `implement.status === 'pending'`, `implement.rerouted === true`, and `implement.reroute_count` incremented by 1.
- [ ] **AC-2 — pre-implement and completed states still rejected without mutation.** `--reroute` dies, and no named task's `status.json` file changes byte-for-byte, when any named task's current phase is `implement`, `plan`, `spec_review`, `spec`, or `complete`. Verified by unit tests covering at least: a single task with `implement.status === 'pending'`; a single task with `plan.status !== 'done'`; a single task with every phase `done`; and a bundle mixing one admitted task with one `implement`-phase task (the pre-existing off-phase-sibling case). Each asserts a non-zero exit, that the abort message contains the per-task `Current state:` summary naming each task's current phase, and byte-identical `status.json` before and after.
- [ ] **AC-3 — mixed-phase bundles within the admitted set are accepted and normalised.** A bundle whose members sit at different admitted phases (e.g. one at `qa`, one at `human_review`), each carrying its required Amendment heading, is admitted; after the reroute every member's `status.json` derives the same current phase (`spec_review` on full tier, `implement` on fast tier). Verified by a unit test asserting exit 0 and the identical derived phase across members.
- [ ] **AC-4 — the exemption predicate is unchanged.** `implement.reroute_exempt` / `implement.reroute_exempt_prior_verdict` are written only on a spec_gap-entry reroute (every named task at `code_review` with status `blocked`, at least one with verdict `spec_gap`), and only for the non-`spec_gap` members. Verified by (a) the pre-existing exemption tests in `tests/run-task-reroute-preflight.test.ts` — `rerouteFromHumanReview reroutes mixed spec_gap bundle when only gap task is amended`, both `rerouteFromHumanReview preserves <verdict> verdict for exempt failing sibling` rows, and `rerouteFromHumanReview second spec_gap reroute requires round-2 headings for amended and previously exempt tasks` — continuing to pass with their `reroute_exempt` assertions **unmodified**; and (b) a new test that a bundle of two tasks at `code_review` `blocked` with verdict `changes_requested` (no `spec_gap`), where only one carries an Amendment, aborts, and that neither task's written `status.json` contains `reroute_exempt`.
- [ ] **AC-5 — a `spec_gap` task is never rerouted unamended.** For every admitted entry state, if a named task carries `code_review.verdict === 'spec_gap'` and its active `spec.md` lacks the heading for its required round, the invocation aborts naming that task (or, with `--force`, emits the per-task warning naming it) and that task's `status.json` is never written with `reroute_exempt: true`. Verified by unit tests covering: a spec_gap-entry bundle whose gap task lacks the required heading; and a bundle of two tasks where one carries verdict `spec_gap` with `code_review.status === 'changes_requested'` rather than `blocked` (so the spec_gap-entry exemption does not apply) and lacks the heading while its sibling has one — the invocation must abort naming the gap task.
- [ ] **AC-6 — Amendment pre-flight scope and `--force` behaviour unchanged.** A single named task at any admitted phase without its required Amendment heading aborts with the existing per-task failure block (task id, spec path, required round, expected heading, reason); the same invocation with `--force` proceeds to reset and emits one warning per failing task, granting no exemption. Verified by a paired unit test (abort / `--force` proceeds), the `--force` case additionally asserting no `reroute_exempt` in the written `status.json`.
- [ ] **AC-7 — the reroute banner reflects the real entry state.** The info line emitted before the reset names each named task's actual entry phase, and identifies a spec_gap-entry reroute as such, instead of the hard-coded `human_review` / `code_review spec_gap` pair. Pinned by a **state-varying pair** of assertions (per `docs/patterns.md` §"Build a state-dependent operator message from one parameterized clause builder"): for a `code_review`-`blocked`-`changes_requested` reroute the label names that entry state and does **not** contain `human_review` or `spec_gap`; for a `human_review` reroute the label names `human_review` and does **not** contain `code_review`. The assertions must target the **entry-state label only** — the segment of the banner preceding the `→` — because the text after the arrow legitimately lists `code_review` and `qa` among the phases being reset, so a whole-line `doesNotMatch` would fail on the reset list rather than on the label. A `match`-only assertion does not satisfy this AC.
- [ ] **AC-8 — the `human_review`-only admission predicate is gone.** `grep -n 'allAtHumanReview' src/orchestrator/main.ts` returns no output. (`allCodeReviewBlocked` / `someSpecGap` / `isSpecGapReroute` are deliberately **retained** — they now serve only the exemption decision and the AC-7 banner, not admission.)

## Known Risks

- **Silent widening without operator awareness.** An operator used to `--reroute` failing outside `human_review` may now trigger a full reset from a `code_review` block they meant to inspect first. The Amendment pre-flight is the mitigation and is unchanged — a reroute still cannot proceed without deliberately-written new spec content — but the AC-7 banner is what makes the widening *visible*, which is why it must name the real entry state rather than a generic label. A banner that reads `human_review` for a `code_review` reroute is worse than no banner.
- **Phase-neutral prompts lose real grounding on a genuine `human_review` reroute.** This is the accepted cost of AC-10. Today the implement-reroute preamble tells Codex "your previous work shipped, the human tried it" — concrete, useful, and true when the task actually reached `human_review`. After this change no reroute prompt can say *that specific implementation-review claim*, because the entry phase is gone by render time — but every rewritten prompt still names a human as the one who decided to reroute (AC-10(d)); only the "reviewed the shipped work" specificity is lost, not the human actor. The mitigation is that the amendment text itself carries the specifics: a human rerouting after a hands-on rejection writes what they observed into the Amendment section, which is the channel the prompts already point at. The failure mode to watch for is over-correction — a preamble so generic it stops conveying that *prior shipped work exists and only the delta is wanted*, or one that drops "human" entirely in favor of an impersonal "the pipeline"/"the operator" framing. Keep the human actor and the prior-work-exists framing; drop only the origin-review claim.
- **Rerouting inside the pre-first-QA uncommitted-artifact window.** `code_review` and `qa`-pending entry states sit before the QA-end commit, so `handoff.md`, `review.md`, `notes.md`, and `status.json` may be uncommitted in the worktree (`docs/patterns.md` §"Operator git surgery before first QA can still discard uncommitted pipeline state"). Reroute itself runs no git command, so it destroys nothing — but the widened gate makes reroute newly reachable inside that window, so any operator `git reset --hard` / `stash drop` afterwards can now discard a *rerouted* state. Out of scope to fix (Non-Goals); the §"Human Reroute" doc edit should note it.
- **Golden regeneration is the easiest way to ship an accident.** `UPDATE_GOLDENS`-style regeneration accepts every rendered difference, including ones this spec never asked for — a stray edit to a shared helper would land in the golden file looking exactly like an intended update. AC-11's line-by-line diff review is the only gate; the expected blast radius is six of sixteen entries, and anything outside that set — the two `promptQa*` entries especially — is a defect.
- **Mixed-phase bundles lose an accidental consistency signal.** Today a bundle at inconsistent phases aborts with `Current state:`, which incidentally warns the operator that the bundle drifted. AC-3 admits mixed *post-implement* bundles, removing that warning for that case. Mitigated by AC-7: the banner must name each task's entry phase when they differ, so the drift stays visible rather than silently normalised.
- **The rewritten tests are the easiest things to get wrong, in two different ways.** In `tests/run-task-reroute-preflight.test.ts`, `rerouteFromHumanReview rejects non-spec-gap code_review and off-phase bundle siblings without mutation` currently asserts the removed behaviour *and* pins the old abort wording; the failure mode is loosening its regex until it passes, converting an invariant test into a tautology. In `tests/run-task-prompts.test.ts`, the bundle test's `doesNotMatch(/THIS IS ROUND \d+ OF HUMAN REVIEW/)` becomes vacuously true the moment that phrase is deleted from the codebase — it must be re-pointed at the replacement anchor phrase (AC-10c) or it silently stops guarding the bundle-banner regression it was written for.
- **The AC-9 sweep is the widest-blast-radius instruction in this spec, in both directions.** Over-applied, it rewrites dated history — `docs/BACKLOG.md` alone carries a dozen reroute/`human_review` hits, and the closed `operator-review-recovery` entry *quotes the old rule as the problem it filed*. Under-applied, it leaves one of the five live surfaces stating the old rule (which is exactly how round 2 found the second CLI help block). Rule 1's "must not appear in the diff" check catches the over-application mechanically; nothing but the enumerated five-surface list catches the under-application, which is why AC-9(a) pins each surface to a file and line rather than describing it. Treat a hit whose class is genuinely ambiguous as a Blocker to raise, not a judgement call to make silently.
- **Two independently-authored CLI help blocks will drift again.** AC-9 requires the same rule in `src/cli/index.ts` and `src/orchestrator/cli.ts`, which round 2 caught precisely because they had already drifted. Nothing in this task's scope prevents the next drift; deduplicating them is a separate refactor. The mitigation here is only that both are named in Affected Files and the AC-9 grep spans `src/`.
- **`--force` from a widened entry state is a sharper tool than it was.** `--force` bypasses the Amendment abort and grants no exemption, so an un-amended task gets the non-exempt prompt line pointing at an `## Amendment` heading that does not exist — Codex then re-implements against the unchanged spec. That is pre-existing documented `--force` behaviour, but the widened gate makes it reachable from more states. Not fixed here; the doc edit should keep the existing "escape hatch when you intentionally want Codex to re-implement against the existing spec" framing rather than softening it.
- **AC-13's guardrail is documentation, and documentation is not enforcement.** Nothing stops an autonomous agent (or a human who skips reading the skill) from invoking `--reroute` from a newly-admitted state without a human actually having decided to. This is an accepted limitation, not a gap this task can close: `--reroute` has never had an interactive confirmation step, and adding one is a materially different, larger change than a gate-admission widening. The mitigation is that widening admission is exactly what makes this guidance newly load-bearing — `human_review`-only admission made the human's presence structural (a human is already in the loop by definition at that phase); the new states remove that structural guarantee, so the two agent-facing surfaces (AC-13) are what carries the requirement forward. If this repo's own operating norms (`AGENTS.md` / `CLAUDE.md`, not shipped to adopters) already require asking before pipeline-state-changing actions, this task doesn't weaken that — it makes the adopter-facing equivalent explicit for the first time.
- **This is orchestrator hot-path work and is flagged `delicate: true`.** The change sits in phase-routing/state-reset code that every task runs through; per `docs/patterns.md` §"Treat the `delicate` flag as load-bearing for the orchestrator's *own* surfaces," the bar is "an undetected bug here corrupts every task that runs after the change lands." A gate that wrongly *admits* resets a task's phase state from a point the operator did not intend; a gate that wrongly *rejects* only inconveniences. Bias the implementation toward the reject side on any ambiguity, and keep the byte-identical-`status.json` before/after assertions on every rejection test (AC-2).
- **Verdict-agnostic admission includes states nobody has exercised.** `code_review` `in_progress` (an orchestrator that died mid-review) and `code_review` `changes_requested` with a stale verdict are both admitted. The concurrent-run guard covers the live-orchestrator case; the reset loop clears the stale verdict and per-loop counters. AC-1 must actually cover these rows rather than assume them.

   Expected: refused for the same reason.

   Expected: refused, telling the operator to add an amendment section first, and offering the deliberate-override option. Overriding proceeds and warns that the implementer will work against the unchanged spec.

   Expected: unchanged from today — accepted, with the approved sibling riding along and no amendment required of it.
10. Bundle a task waiting on QA with a task waiting on human review, amend both, and reroute the pair.
    Expected: accepted; the message names both entry points; afterwards both tasks are at the same point in the pipeline.
11. Read the reroute guidance in the reference documentation and in the pipeline-driving skill.
    Expected: both say plainly that deciding to reroute a task is a call only a human makes — an assistant driving the pipeline on someone's behalf should not decide to reroute on its own, even when it's otherwise operating without asking for confirmation on other steps.

## Implementation Notes (non-binding — owned by plan/implement)

- The admitted set is expressible as a membership test over the value `getCurrentPhase()` returns; it needs no separate `implement.status === 'done'` check, since `deriveTopLevelStatus()` already guarantees it. An explicit assertion of that equivalence would be redundant but harmless.

- Inventory of the origin-claiming strings AC-10 targets, as of this spec: `src/orchestrator/context.ts` `modeExplain.reroute`; `src/orchestrator/prompts/index.ts` in `promptImplementReroute()` — the round-≥2 banner, the round-1 banner, the bundle banner, the non-exempt per-task line, and the non-resumed preamble; and the opening/framing line of each of the three reroute templates.
