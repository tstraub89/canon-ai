**Pre-handoff self-check** — after you make your changes and before you run validation and write handoff.md, check the change in this order:
1. **Test integrity.** For each test this pass added or changed to pin new or altered behavior: would it fail if the change were reverted? Does it assert the specific reason — the message, value, or state the change produces — rather than only that something failed or passed? Regenerated snapshots and pure fixture updates are exempt. Where a cheap run against the base commit confirms the failure, do it. A red-first regression-test AC still follows the red-first checkpoint; this check does not replace it.
2. **Restatement sweep.** For every contract the change alters — an operator-facing string, flag, format, heading, verdict, or config key — search the repository for other places that state the same contract, and bring them in line.
3. **Sibling parity.** For every guard, check, or branch the change adds, find the parallel paths that handle the same input — other commands, modes, entry points, or platform variants — and confirm each one either gets the same treatment or deliberately does not.

Record each check's evidence in handoff.md's `## Self-Check` table (`Check` | `Evidence`, one row each for `Test integrity`, `Restatement sweep` and `Sibling parity`): the tests and the assertion that pins each one's failure reason, and how you know it fails without the change; the search pattern(s) you ran for each changed contract, and how each hit outside Affected Files was handled; the parallel paths you examined, and whether each got the same treatment. Write `N/A — <reason>` for a check that does not apply, and `\|` for a literal pipe. Write the section even if the handoff template you are using lacks it: code review rejects a handoff without a filled `## Self-Check` section, and the reviewer checks each row against the diff.

If a check finds an edit needed in a file outside the spec's Affected Files, do not make it: record it under Blockers in handoff.md.

**How to approach this:**
0. If a task's line above marks it EXEMPT, skip steps 1-2 for that task entirely — its spec has NO Amendment section and its plan has NO Reroute Plan section, by design. For exempt tasks, follow the task-specific line above: approved siblings only need shared-behavior re-verification, while siblings with prior review findings must still address those findings.
1. For each task above, read `tasks/<id>/spec.md` from your current working directory (the worktree). REPO_ROOT's copy is the pre-implement scaffold and does NOT contain operator amendments. Locate the exact heading named in its entry — `## Amendment` for round 1, or `## Amendment Round N` for round 2+. Each task carries its own reroute round (bundles may mix rounds), so use the heading specified in that task's line, not a bundle-wide assumption. That section holds the newest requirements and wins where it conflicts with an earlier section; earlier sections (the original ACs and prior amendment rounds) stay binding wherever their work is not yet implemented.
2. Check `tasks/<id>/plan.md` for `## Reroute Plan` (round 1) or `## Reroute Plan Round N` (N = that task's reroute round). If present, use that section as this round’s plan guide. If absent (fast-tier reroute with no conversational reroute plan), read the base plan for orientation.
3. Establish the current state from the worktree, not from memory: run `git status` and `git diff` against the task's base branch to see what is actually implemented, committed or not. The prior implementation round may be complete or partial — a reroute can follow a finished round or interrupt one that was stopped, crashed, or blocked mid-way, leaving uncommitted edits behind. Treat tasks/<id>/handoff.md as a record of prior work only if it has been filled in (after an aborted first pass it may still be the unfilled template); even then it predates the amendment.
4. Determine this round's scope: the amendment, plus any unfinished work from the original ACs and earlier amendment rounds, plus unresolved blocking findings in the archived review named in the task's entry, if any. Note which ACs are new, which changed, and which the worktree already implements.
5. Implement that scope. Correct existing work stays; change it only where the amendment or an unmet AC requires. If the amendment conflicts with a prior AC, the amendment wins.
6. Re-run ALL applicable validation checks (lint, type-check, test, build, e2e as applicable per the spec's Validation Required). Required checks must be recorded as Pass or Fail; do not mark a required check N/A.
7. **Rewrite handoff.md** to reflect the complete current state of the implementation — including earlier work that still applies, any unfinished work from the original ACs and earlier amendment rounds, and this round’s amendment work. The Changes table must list every file this task has changed — committed on the branch or dirty in the worktree (`git status --porcelain`), including uncommitted edits left by an interrupted earlier round; a modified tracked file the table omits blocks canon's auto-commit (or, if no listed file is uncommitted, is caught only by the QA-end check), while an untracked file is committed only if the table lists it — otherwise it is left out of the commit, unseen by code review, until the QA-end check rejects it. Delete leftovers from an interrupted round that the amendment makes obsolete rather than listing them. Carry existing Red-First Evidence rows forward. The rewritten `## Self-Check` table covers all work on the branch: carry earlier rounds' Self-Check evidence forward (the baseline rows and any Iteration `### Self-Check` rows), updated to the current diff. The reviewer reads handoff.md as the single source of truth, not your prior session's context.

**Citing files in task artifacts:** cite every repository file by its full path from the repository root, including any workspace or package prefix — never a path relative to a package or to the current directory. For a file that does not exist — one this task deleted, or one only planned — use the markdown-link form `[path](path)` instead of backticks, because `docs-refs-check` reports a backticked path to a missing file as a broken reference.

**Spec ACs are binding** — including both original ACs and amendment ACs. If you think an amendment AC is infeasible as written, document it under Blockers in handoff.md. Do not silently drop any AC.

**Bug/flake-fix red-first checkpoint** — if the amendment adds or modifies a red-first regression-test AC, or an original or earlier-round red-first AC is unfinished because the prior round was partial: write and run the test **before** making the fix edits, and confirm it fails *for the reason the spec states*; then apply the fix and confirm it passes. Keep any carried-forward Red-First Evidence row that already satisfies its AC; do not re-run it. Record each new red run as a row in the rewritten handoff’s `## Red-First Evidence` table, next to the rows carried forward from earlier rounds (AC, command, the commit it ran against, observed failure, post-fix result). The pre-fix state is the task branch’s committed HEAD. Write and run the test before changing any non-test code; files that exist only to support tests count as test files. If the worktree already holds aborted-round edits, first copy every tracked and untracked non-test leftover to a temporary directory. Confirm every set-aside copy exists and matches its worktree file before changing any worktree path. Note any tracked file the aborted round deleted or renamed; it has no copy to make. Only after all copies are verified: for tracked leftovers, restore their paths to committed contents; remove untracked non-test leftovers from the worktree — never a bare `git stash`. Run the red test against that isolated state, then restore every set-aside file (tracked and untracked) and re-apply each noted deletion or rename before applying the fix. Difficulty isolating the edits is not grounds for skipping the red run. If it cannot be made to fail for the stated reason, record a `[wrong-premise]` Blocker instead of implementing on an unconfirmed premise. If the spec relies on the environment-bound-and-impractical escape, run its named deterministic alternative if it is executable in your sandbox and record the outcome in the Red-First Evidence section; if it is not executable (e.g. a documented manual repro), state that instead — never report an outcome for a run that did not happen. If no isolated pre-fix run is possible and the spec names no environment-bound escape, record a `[wrong-premise]`-style Blocker and do not implement the fix on an unconfirmed premise.

Append to tasks/<id>/notes.md for any surprising behavior found while re-reading the codebase (prefix: `[implement-reroute]`).
