# Spec: qa-drafts-pr-body — QA drafts a filled PR body for --pr

> Written by: Claude | Review by: Codex
> Status: draft | reviewed | approved | implemented

## Problem

When `canon run --pr` opens a draft PR for a repo that has a PR template, it passes the **raw, unfilled template** as the PR body ([`createDraftPRForTask` → `--body-file templatePath`](../../scripts/run-task/main.ts) ~main.ts:778). The operator (the "GP" dogfood report, 2026-05-19: *"PR body is the canon stub, not the project template"*) then hand-fills every section. That is a high-friction step on the path canon otherwise automates end-to-end.

The QA phase already reads every artifact (`spec.md`, `handoff.md`, `review.md`) to write `done.md` and has the richest context for describing what shipped — but it produces nothing the PR body can use. This task closes that gap: QA drafts a filled PR body, and `--pr` uses it.

This is **half (1)** of the `/canon-pr` skill + QA-phase PR body draft BACKLOG entry (`docs/BACKLOG.md`, "Tooling & Dev Experience"). Half (2) — the interactive `/canon-pr` refinement skill — stays deferred.

## Decision

The QA phase writes an outward-facing, filled PR body to `tasks/<id>/pr-body.md`. `canon run --pr` prefers that artifact for single-task PRs, with a soft, logged fallback to today's behavior.

Concretely:

- **QA fills the adopter's own template.** When the repo has a PR template (any location `findPullRequestTemplate` probes, resolved worktree-first to match `--pr`), QA fills *that* template's structure. When no template exists, QA writes a default skeleton (Summary / Changes / How to test / Notes for reviewer). Filling the adopter's own template — rather than canon shipping a generic one — is what sidesteps cross-project template variability.
- **The body is outward-facing and carries no canon footprint.** It reads as if a human authored it. No "generated by canon" / AI-tool attribution (preserves the 1.3.0 "ninja mode" decision). It is a distinct artifact from `done.md`, which is inward-facing (open-questions-for-human, operator-directed decisions, raw validation dumps) and stays unchanged.
- **`--pr` consumes it.** New body-resolution order: `CANON_PR_BODY` env (unchanged) → populated `tasks/<id>/pr-body.md` → repo PR template file → `--fill`. Used for single-task runs.
- **Soft fallback, never a hard gate.** If `pr-body.md` is absent or still the unfilled template stub, `--pr` falls back to the prior behavior (template file → `--fill`) and emits a visible log line explaining the fallback. The QA phase is **not** gated on `pr-body.md` (unlike `done.md`).
- **Bundles fall back in v1.** Multi-task runs (N IDs → one PR) do not combine per-task bodies; `--pr` uses today's behavior and logs that per-task QA bodies aren't combined. Bundle synthesis (one QA-authored body across all tasks) is a deferred follow-up.

## Non-Goals

- **Bundle PR-body synthesis** — single-task only in v1; bundles log + fall back. (Follow-up tracked in the `/canon-pr` BACKLOG entry; concatenating per-task bodies is explicitly rejected — it breaks structured templates.)
- **No hard QA phase gate** on `pr-body.md`. Soft fallback only.
- **No `/canon-pr` interactive refinement skill** (half (2) of the BACKLOG entry).
- **No canon attribution / tool-leak** in the body.
- **No change to `CANON_PR_BODY` semantics** (incl. `$LABEL`/`$TITLE` substitution) or to the existing template/`--fill` fallbacks. The change is purely additive.
- **Not shipping a default `.github/pull_request_template.md` to adopters.** We fill whatever template they have (or a default skeleton in the body itself); we do not impose a template file. (Generating a project-specific template at init is a separate BACKLOG entry.)
- **No backfill or migration of existing in-flight tasks.** Tasks created before this lands have no `pr-body.md`; `--pr` falls back per AC-4. Do not add a migration/backfill step or treat the missing file as an error — absence is a supported, expected state.

## Acceptance Criteria

- [ ] **AC-1 (QA writes a filled body):** After the `qa` phase completes for a single task, `tasks/<id>/pr-body.md` exists and is populated (not the unfilled template stub). When the repo has a PR template, the body's structure follows that template's sections; when it does not, the body uses the default skeleton (Summary / Changes / How to test / Notes).
- [ ] **AC-2 (outward-facing, no footprint):** The produced body contains no canon/AI-tool attribution and none of `done.md`'s inward-facing sections (operator open-questions, operator-directed decisions, raw validation-outcomes tables). `done.md` content and format are unchanged by this task.
- [ ] **AC-3 (`--pr` precedence):** For a single-task `--pr`, the PR body is resolved as `CANON_PR_BODY` (if set) → populated `pr-body.md` → repo PR template file → `--fill`. A populated `pr-body.md` is used as the body when `CANON_PR_BODY` is unset.
- [ ] **AC-4 (soft fallback + log):** When `pr-body.md` is absent or a stub, single-task `--pr` falls back to the prior behavior (template file → `--fill`) and prints a visible log line stating it fell back and why. No phase is blocked and no error is raised by the absence/stub.
- [ ] **AC-5 (bundles fall back):** For a multi-task `--pr`, per-task `pr-body.md` files are not used; `--pr` uses today's behavior (template / `--fill`) and logs that per-task QA bodies aren't combined in this version.
- [ ] **AC-6 (artifact registration):** `pr-body.md` is a canon-managed artifact template — scaffolded into new tasks by `canon task new`, synced by `canon upgrade`, mirrored under `templates/` (so `sync-templates:check` passes), and committed alongside the other task artifacts at `--pr` time. Registration is **purely declarative**: `canon upgrade` iterates `CANON_OWNED` generically (`upgrade.ts` ~226), so the `CANON_OWNED` entry is the whole upgrade-sync mechanism — **no upgrade-path code change**. Likewise, tasks created *before* this lands simply have no `pr-body.md`; that absent case is handled by AC-4's fallback — **no backfill or migration of existing tasks**.
- [ ] **AC-7 ("populated" is well-defined):** A stub-vs-populated check (sibling of `isDoneMdTemplate`) is the single definition of "populated" that AC-3/AC-4 use. The unfilled `pr-body.md` template scaffold reads as a stub; a QA-filled body reads as populated.
- [ ] **AC-8 (no regression):** With `CANON_PR_BODY` set, its value (with `$LABEL`/`$TITLE` substitution) is still used verbatim. A repo with a PR template but no `pr-body.md` opens a PR identically to today. `done.md`'s existing hard gate is unchanged.

## Design

> **Mechanics deferred to plan/implement.** ACs above are behavioral contracts; exact function signatures, sentinel strings, and the default-skeleton wording are an implementation concern. The notes below name the touch points and the one non-obvious constraint per point.

The QA phase ([`qa.ts`](../../scripts/run-task/phases/qa.ts)) resolves the PR template **from the active worktree first** (mirroring `--pr`'s worktree-then-REPO_ROOT precedence at main.ts ~775 — a task branch may have edited/added the template) and injects it (or a "no template; use default skeleton" signal) into the QA prompt via [`promptQa`](../../scripts/run-task/prompts/index.ts). [`qa.md`](../../scripts/run-task/prompts/templates/qa.md) instructs QA to write `pr-body.md` as a required, outward-facing deliverable with no attribution.

`--pr` body resolution ([`createDraftPRForTask` / `resolveCanonPrBody`](../../scripts/run-task/main.ts)) inserts the populated-`pr-body.md` branch between the `CANON_PR_BODY` check and the template/`--fill` fallback, gated on `taskIds.length === 1`. "Populated" is the new stub detector in [`validation.ts`](../../scripts/run-task/validation.ts) (sibling of `isDoneMdTemplate`).

### Interaction Dependencies

- **`--push`** uses the same body? No — `--push` opens no PR (push only), so it's unaffected. Only `--pr` builds a body.
- **Reroute**: if a task reroutes from `human_review` and QA re-runs, QA overwrites `pr-body.md` from the latest state (acceptable; see Known Risks for the operator-edit-loss note).
- **`canon task new`** scaffolds the new template into every new task (via `listTemplateFiles` globbing `.canon/templates/*.md`).

### Data Model Changes

None. No `status.json` schema change — `pr-body.md` is a file artifact, not a status field. No new phase.

## Known Risks

- **PR-body prose quality expects human iteration.** QA is an LLM filling a template; first-pass bodies may be uneven. This is a perception/quality surface — expect at least one round of QA-prompt iteration during dogfooding. Mitigated by: the draft PR + human_review gate (human reads the body before marking ready), and the soft fallback. **Ship the prompt, observe, iterate** — this is exactly why we kept it soft and single-task for v1.
- **Canon-attribution regression breaks ninja mode.** If the QA prompt (or a future edit) lets attribution leak into `pr-body.md`, the 1.3.0 ninja-mode guarantee is silently broken. Reviewer guardrail: verify the prompt forbids attribution and the default skeleton carries none.
- **Worktree-vs-REPO_ROOT template resolution.** QA must resolve the template from the worktree (branch-HEAD) — resolving from REPO_ROOT could fill a stale or absent template that differs from what `--pr` will later find. Both QA-side resolution and `--pr`-side resolution must use the same worktree-first precedence.
- **Stub-detector calibration.** Poorly chosen sentinels could classify a populated body as a stub (→ unnecessary fallback) or a stub as populated (→ an ugly raw-template PR). Mirror the `isDoneMdTemplate` sentinel approach and cover both directions in tests.
- **Reroute overwrites operator edits.** If an operator hand-edits `pr-body.md` after QA and then reroutes, the QA re-run overwrites those edits. Acceptable for v1 (regenerate-from-latest is the safer default); interactive refinement is the deferred `/canon-pr` skill's job.
- **Non-canonical template headings.** Because QA fills the template via the LLM (not heading-name matching), it adapts to whatever section names the adopter uses — lower risk than a convention-based filler, but worth a dogfood check against a real adopter template.

## Human Test Plan

1. In a repo that **has** a PR template, run a task through the pipeline to the QA step. Read the drafted PR body and confirm it follows the template's sections, describes what actually shipped, and reads like a person wrote it — with no mention of canon or AI tooling.
2. Open the draft PR via the normal "open a PR" step. Confirm the PR opens pre-filled with that body, not an empty template.
3. In a repo with **no** PR template, run a task to QA and confirm the drafted body still has a sensible structure (summary, what changed, how to test, notes).
4. Set the PR-body override you'd use to suppress canon's body, run the same flow, and confirm your override still wins.
5. Take a task where the body wasn't drafted (or clear it), open the PR, and confirm it still opens — falling back to the previous behavior — with a visible note explaining why it fell back.
6. Expected overall: single-task PRs open with filled, human-sounding bodies by default; missing bodies degrade gracefully with an explanation; nothing reveals that canon authored the PR.
