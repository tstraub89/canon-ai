# Spec: worktree-root-in-repo — Move the default worktree root to `.canon/worktrees/`

> Written by: Claude | Review by: Codex
> Status: draft (revision 5 — responds to spec review round 4 by correcting the run-only boundary to account for the pre-existing invocation-root guard)

## Problem

Canon's default worktree root is the literal sibling directory `../dev-worktrees`, resolved in `src/orchestrator/env.ts:66-68` (`WORKTREES_ROOT`) and mirrored by `effectiveWorktreesRoot()` (`src/orchestrator/state.ts:9`). That default has three costs, all of which land on adopters at first use:

1. **Sibling collision.** Two canon-adopting repositories that sit side by side under one parent directory share a single worktree root. Their task worktrees intermingle, and a same-id task in both repos collides outright because `git worktree add` refuses a non-empty target.
2. **An unexplained folder outside the repo.** A new adopter runs one task and finds a `dev-worktrees/` directory next to their project with nothing in it to say what created it. The name is arbitrary and predates canon being a product.
3. **Extra trust and permission surface.** Codex keys project trust on the path it is launched in, and canon launches `codex exec` inside the worktree, so a sibling root needs its own trust entry separate from the repo's. An operator driving canon from their own interactive Claude Code session must add the sibling root to `additionalDirectories` for that session to reach the worktrees. Both grants disappear when worktrees live under the repo root.

Claude Code's own worktree feature uses an in-repo dot-directory, so the layout is established practice. Exploration confirmed the move needs no change to canon's containment logic: `classifyInvocationRoot()` (`state.ts:49`) tests the main checkout by exact equality *before* testing worktree containment, so an in-repo worktree is not misclassified. Every dirty-tree gate runs `git status --porcelain` without `--ignored`, so a gitignored `.canon/worktrees/` is invisible to them. Neither `canon init` nor `canon upgrade` enumerates `.canon/` wholesale; both operate on named files from `CANON_OWNED`.

### The one thing changing the default does not deliver

A task that already has a worktree at `../dev-worktrees/<id>` keeps resolving there after the default moves, because resolution finds a task's worktree **by branch and by content, not by location**. Two independent paths do it: `findExistingWorktreeForBranch()` returns the first registered worktree on the task's branch wherever it lives (exported at `worktree.ts:74`, private copy at `state.ts:194`), and `scanWorktreesForSecondaryOwnership()` (`state.ts:162`) matches any registered worktree whose nested `tasks/<id>/status.json` claims the task and whose checked-out branch matches. So without an explicit refusal, canon would silently run an unmigrated task in the old sibling directory — and then break anyway, because `assertManagedInvocationRoot()` (`state.ts:93`) already classifies a worktree outside the effective root as `foreign-worktree` and refuses. Canon would hand the old directory to an agent and then refuse that agent's own `canon task phase` call from inside it. That incoherence, not tidiness, is why this task has to say something about out-of-root worktrees.

### Why revision 4 deletes the root-scoping mechanism instead of hardening it again

Revisions 1–3 answered that by narrowing resolution itself — root-scoping the lookups so an out-of-root worktree becomes unfindable and therefore *missing*. Three review rounds each found a different consumer or lifecycle corner that narrowing broke, and round 3's finding is fatal to the approach as specified:

- Round 1: the branch lookup is an unscoped fallback (two copies, five call sites).
- Round 2: the "legacy worktree" state revision 2 invented was not taught to `resolveShipCwd()`/`shipTasks()` (`main.ts:2128-2138`) or `teardownWorktree()` (`worktree.ts:453`).
- Round 3: narrowing cannot produce the required *missing* behavior for the **canonical** first-worktree state at all. `ensureBranch()` writes the task branch into the *worktree* copy of `status.json` and deliberately leaves the main-checkout copy blank so the main tree stays clean — `tests/run-task-safety.test.ts:1719-1727` asserts both the empty `branch` and a clean `git status` for that file. With a blank branch, `isOrphanedWorktreeState()` returns `false` at its blank-branch guard (`state.ts:257-258`) and `resolveTaskCwd()` takes the ownership-scan path and, once scoped, falls through to `return REPO_ROOT` (`state.ts:312`). The result is not a loud refusal: it is silent resolution of task state to the main checkout while the true state sits in the old worktree — the exact split-brain `assertManagedInvocationRoot()` exists to prevent.

All three rejections share one structural root: **narrowing resolution redefines an existing state for every consumer, and there are more consumers and more lifecycle states than any round enumerated.** Recovering round 3's case would require writing the branch into the main-checkout copy (blocked by the main-clean contract above) or reintroducing out-of-root detection inside resolution (revision 2's mechanism, which round 2 killed). Per the escalation rule for scope-expanding review rounds, revision 4 drops the mechanism class rather than hardening it a fourth time.

**Resolution is left exactly as it is.** The refusal moves to one place: `canon run` checks the task's resolved working directory once, before any phase executes, and refuses when it is a worktree outside the effective root. That is a single new site with a single new message, and it makes every round-2 and round-3 finding moot by construction:

| Round 2/3 finding | Why it no longer applies |
|---|---|
| `resolveShipCwd()`/`shipTasks()` need a contract | `--ship` is exempt and resolution is unchanged, so ship behaves exactly as today |
| `teardownWorktree()` can't clean a non-derived path | Teardown is unchanged; it still removes `worktreePath(taskId)` or no-ops |
| Blank-branch main-checkout status can't be classified | Nothing classifies it; resolution returns the true worktree and the guard reads that path |
| `canon task list` row wording | Unchanged — the task resolves, so the list shows its real state, not `INVALID` |

### What the new refusal covers, and what the pre-existing guard already covers

The new refusal covers `canon run` (including `--pr`, `--reroute`, `--full-send`, and `--dry-run`), keyed on the task's **resolved worktree location**. It is not the only thing that changes behavior for an unmigrated task, because canon already has a second guard keyed on something different: `assertManagedInvocationRoot()` (`state.ts:93`) classifies the **directory canon was invoked from**. It is called at exactly two seams — `taskCmd()` (`src/task/index.ts:1554`, before any subcommand dispatch) and `main()` (`src/orchestrator/main.ts:3452`, the `canon run` entry) — and it compares the invocation toplevel against the effective worktrees root. `REPO_ROOT` is derived from `git rev-parse --git-common-dir` (`env.ts:26-56`), so it stays anchored on the main checkout even when canon is invoked from inside a linked worktree; moving the root therefore reclassifies the old sibling directory from `canon-worktree` to `foreign-worktree` with no code change to the classifier.

Both guards keyed together, the boundary for an unmigrated task is:

| Invocation | Result after this change |
|---|---|
| `canon run <id>` from the main checkout | New refusal (AC-7): names the out-of-root path, the expected root, both remedies |
| `canon run --ship <id>` from the main checkout | Runs — explicitly exempt; merges and archives, leaves the old directory behind |
| `canon task phase/accept/status/list` from the main checkout | Runs, and resolves to the old worktree — reads and writes the task's true state there |
| Any `canon task` or `canon run` invocation from **inside** the old sibling directory | Pre-existing invocation-root refusal (`foreign-worktree`), which now fires where it previously passed |

The last row is a real behavior change and the one round 4 caught revision 4 misstating. It is also the correct outcome and requires no new mechanism: an operator standing in a directory canon no longer considers part of its managed root gets told so, and the existing message already names the effective root and offers `CANON_WORKTREES_ROOT` as a remedy — one of the two migration paths. Its one inaccuracy is that it calls the directory "hand-created", which an unmigrated canon-created worktree is not; AC-13 requires one sentence appended to that message covering the previous-default case, and nothing else about the guard changes.

It cannot strand an in-flight task, because canon's own agents only ever run `canon task phase` from a worktree `canon run` created for them, and `canon run` refuses the unmigrated task before any agent session starts. Reaching the last row takes a human deliberately `cd`-ing into a pre-3.0.0 worktree.

So the honest guarantee is narrower than revision 4 claimed: **task state remains readable and writable for an unmigrated task, from the main checkout.** The task cannot be *run* until it is migrated, and the old directory is no longer a valid place to stand.

This is a breaking change for existing adopters (two known) and ships as a rider on the 3.0.0 open-source launch release. The design was settled in the canon-ai backlog on 2026-09-02.

**Delicate call.** Worktree machinery is a listed delicate surface in `docs/product-context.md`. This task is deliberately `delicate: false`, and revision 4 strengthens that further: the change is a path constant, a gitignore pattern, a `git worktree prune` call, one refusal at the run entry, and documentation. It changes no resolution logic and no teardown logic, so no existing state's behavior is redefined. Every failure mode is a `die()` before any agent session starts.

## Decision

Default the worktree root to `<repo>/.canon/worktrees/<task-id>/`. Add `.canon/worktrees/` to canon's managed `.gitignore` block so `canon init` writes it, `canon upgrade` upserts it, and `canon doctor` warns when it is missing. Run `git worktree prune` before the create-or-reuse decision so a stale registration left by a hand-deleted directory cannot wedge task creation. `CANON_WORKTREES_ROOT` continues to override the default with unchanged semantics.

**No legacy run.** `canon run` refuses a task whose worktree lives outside the effective worktrees root, before any phase executes and before any agent session starts. The refusal names the out-of-root path, the root canon expects, and the two remedies (move the directory and `git worktree repair`, or pin `CANON_WORKTREES_ROOT`). `--ship` is exempt: a task at `human_review` still merges and archives, leaving the old directory and its registration for the operator to remove.

**The old directory stops being a valid place to stand.** Because the effective worktrees root moves, canon's pre-existing invocation-root guard reclassifies a pre-3.0.0 sibling worktree as foreign and refuses any `canon` command invoked from inside it, pointing the operator back at the main checkout. This needs no new mechanism — only one sentence added to that guard's existing message so it does not describe a canon-created worktree as hand-created. Task state for an unmigrated task stays fully readable and writable via `canon task` from the main checkout.

**Everything else about worktree resolution is unchanged.** A task's worktree is still found by branch and by content, wherever it is registered. That keeps `ensureWorktree()`'s reuse path, the bundle leader's shared worktree, operator-renamed directories, orphan detection, `--ship`'s partial-cleanup recovery, and teardown behaving exactly as they do today.

Observable differences for an adopter after upgrading:

- A first task creates `.canon/worktrees/<task-id>/` inside the repo. No directory is created beside the repo.
- `git status` in the main checkout stays clean while worktrees exist, because the ignore rule is in place.
- Deleting a worktree directory by hand and re-running the task no longer fails on a stale worktree registration.
- A task whose worktree is still under `../dev-worktrees` refuses to run, with a message naming that directory, the new expected root, and both remedies. Its `canon task list` row still shows its real phase, read from that worktree.
- `canon` commands invoked from a shell sitting *inside* that old directory are refused by the existing invocation-root guard and told to run from the main checkout; the same commands work from the main checkout.
- `--ship` on such a task still merges and archives it, leaving the old directory and registration for the operator to remove.
- Bundle secondaries keep resolving to the leader's worktree, unchanged.

The change is documented as BREAKING with a migration note.

## Non-Goals

- **No change to worktree resolution.** Neither copy of `findExistingWorktreeForBranch()` nor `scanWorktreesForSecondaryOwnership()` gains a location filter, and `resolveTaskCwd()`, `isOrphanedWorktreeState()`, `getActiveCwd()`, `resolveShipCwd()`, and `ensureWorktree()` keep their current logic and messages. AC-6 makes this structural rather than a matter of trust.
- **No change to `teardownWorktree()`.** It still removes `worktreePath(taskId)` and no-ops when that path is absent. The pre-existing gap — it cannot clean a worktree resolution returned from a differently-named directory — stays open and is tracked in the canon-ai backlog. Widening it while resolution is unscoped would let `--ship` force-remove an out-of-root directory, which is the one destructive outcome this task must not create.
- **No *new* refusal mechanism outside `canon run`.** `canon task` subcommands **invoked from the main checkout** continue to resolve to wherever the task's worktree actually is, and read and write its true state there. What does change outside `canon run` is a consequence of the root moving, not a new guard: `assertManagedInvocationRoot()` — already called at the `canon task` entry (`src/task/index.ts:1554`) — now classifies a pre-3.0.0 sibling worktree as `foreign-worktree` and refuses invocations from inside it. No exemption is added for that case; the only edit to the guard is the message sentence in AC-13. See Problem §"What the new refusal covers" for the full invocation matrix.
- **No automatic migration** of existing worktree directories, and no auto-repair. The refusal message plus the changelog note are the mechanism; canon does not move directories or run `git worktree repair` itself.
- **No change to `getActiveCwd()`'s missing-worktree message.** Revision 3 proposed adding the expected path to it; in every non-test path `resolveTaskCwd()`'s `die()` — which already names the expected path and the branch — fires first, via the `readStatus()` call `getActiveCwd()` opens with. The edit would be unobservable.
- **No change to `CANON_WORKTREES_ROOT` semantics**, to `warnWorktreesRootMismatch()` (which already fires only when the override is set), or to `checkCodexProjectTrust()` in `canon doctor`.
- **No change to `classifyInvocationRoot()`, `isPathInside()`, `isContainedIn()`, or any dirty-tree gate.** AC-3 adds coverage proving they already behave correctly under a nested root; it does not modify them. `assertManagedInvocationRoot()`'s classification logic, call sites, and `CANON_TASKS_DIR_OVERRIDE` early return are likewise unchanged — AC-13 appends one sentence to its refusal message and nothing else.
- **No change to `canon task list`'s orphan row wording or to `src/task/index.ts`.**
- **No submodule initialization in worktrees.** Canon has never run `git submodule update` in a worktree under any layout; that is a pre-existing gap tracked separately in the canon-ai backlog.
- **No `.git/info/exclude` writes.** The ignore rule travels in the tracked managed block only.
- **No version bump.** The 3.0.0 bump is human-owned at release time per `docs/decisions.md` §"Versioning and release policy". This task adds the changelog entry under `[Unreleased]`.
- **No edits to canon-ai's own `.claude/settings.json`.** Its `additionalDirectories` entry for `../dev-worktrees` stays until in-flight canon-on-canon worktrees drain and the released engine is installed globally; dropping it is an operator step after release.

## Known Risks

- **Prune ordering.** `git worktree prune` must run at `REPO_ROOT` *before* the lookup consults `git worktree list`; if it runs after, a stale entry for the same branch is still returned and the reuse path hands back a path that does not exist. AC-5's red-first test is shaped to catch exactly this ordering mistake.
- **Prune has side effects.** It removes registrations for any worktree whose directory is missing, including one the operator deleted deliberately and intended to restore with `git worktree repair`. Canon's contract is that worktrees are created and removed through canon, so this is acceptable — but it is adopter-visible and AC-12 requires the changelog to say so.
- **Guard placement is the whole mechanism.** Too late and it misses `--dry-run` or fires after runtime files are written; too broad and it breaks `--ship`; missing the `CANON_TASKS_DIR_OVERRIDE` exemption and much of the existing suite fails, because test setups routinely point the tasks dir at a temp tree. AC-7's four negative cases exist to pin all of this, and the reviewer should check the exemption specifically.
- **The guard is not the only loud path.** Two pre-existing refusals can fire ahead of AC-7's, and in both cases the operator sees the older text rather than the migration text. (a) For a task whose main-checkout `status.json` *does* carry a branch and whose worktree is gone, `resolveTaskCwd()` dies first with the missing-worktree message. (b) For `canon run` invoked from *inside* an unmigrated worktree, `assertManagedInvocationRoot()` fires at `main.ts:3452`, which the Implementation Notes place immediately before the new guard — so AC-7's message is unreachable from that cwd. All three are loud and all three name paths; AC-13(i)'s message sentence is what keeps (b) accurate. Deliberate accepted overlap, not a gap.
- **Moved-but-not-repaired worktree.** An operator who moves `../dev-worktrees/<id>` to `.canon/worktrees/<id>` without running `git worktree repair` leaves the registration pointing at the old path. `resolveTaskCwd()` returns the new directory (its nested `status.json` exists), the guard passes, and git commands inside may then fail on a stale admin back-pointer. The changelog and docs both name `git worktree repair` as part of the migration; canon does not detect this state.
- **Partial coverage by design, and the boundary is cwd-dependent.** The new refusal covers `canon run` only, keyed on the task's resolved worktree. `canon task phase`/`accept` from the main checkout still write to the old worktree — that is the retained guarantee. But the *existing* invocation-root guard is keyed on cwd, so the same commands are refused from inside the old directory. Two guards on two different keys is the trickiest thing about this change to explain; the invocation matrix in Problem is the single place that states it, and AC-12 requires the changelog to carry the operator-facing half ("run it from the main checkout").
- **macOS path canonicalization.** With the root inside the repo, `worktreesRoot` and `mainRoot` now share a prefix, and temp-dir tests will see `/var` vs `/private/var` on one side if either is not realpath'd. Every new comparison in AC-1, AC-3, AC-4, AC-6, and AC-7 must canonicalize both sides (`docs/patterns.md` §"Test-writing pitfalls (canon-specific git/worktree gotchas)").
- **Adopter tooling that walks the tree.** Root-anchored `**/` globs (vitest default include, prettier, coverage, Docker build contexts, IDE indexers) will see one copy of the codebase per active worktree until the adopter excludes `.canon/worktrees/`. This is documented, not engineered around; a support question is the expected cost, not a defect.
- **`git clean -ffdx` destroys in-flight worktrees.** A nested worktree is a git repository inside the tree, so plain `git clean -fdx` skips it but double-force removes it. Documented in AC-9 and AC-12.
- **Base-drift gate at `--pr`.** Every `dist/` artifact and both sides of each templates mirror must appear in Affected Files or the `--pr` gate rejects the undeclared one. The table declares both dist bundles, `templates/.gitignore`, and `templates/docs/pipeline-orchestrator.md`.
- **Dogfood asymmetry.** This task's own pipeline run uses the installed 2.9.0 engine and the old root, so a green run does not exercise the new default. Reviewers should weight the test evidence and not read the dogfood worktree location as confirmation either way.

## Amendment

> Round 1, 2026-09-03; revised five times after amendment reviews. Revision E drops the entry auto-prune altogether: canon now refuses to run while any canon task worktree is registered but missing on disk, which closes the secondary-only gap from review D by construction. Source: `code_review` `spec_gap` (three-lens convergence, archived in `review-prior-1.md`). Approved ACs 1–13 stand unchanged except where this section says otherwise.

### What the review found

The spec promised, in Decision §"Observable differences", Human Test Plan step 3, and the AC-12 changelog sentence, that a hand-deleted worktree is recovered on "the next run." The only prune call is inside `ensureWorktree()`, reached solely through `ensureBranch()` from the `implement` phase. For a task whose next phase is `code_review`, `qa`, or `human_review`, `canon run` resolves the task's cwd first (`readStatus()` → `resolveTaskCwd()` → `findExistingWorktreeForBranch()`), the stale registration is returned as a live path, and downstream file and subprocess operations fail with a raw error.

Five amendment-review rounds established what a correct fix must respect:

- **Pruning makes things worse, not better.** In the canonical post-bootstrap state the main-checkout `status.json` has a blank `branch` (`ensureBranch()` writes the branch only into the worktree copy, `git.ts:276-301`). Once a stale registration is pruned, `resolveTaskCwd()` finds nothing by branch or content and falls through to `REPO_ROOT`, so the run silently proceeds in the main checkout. The same silent fallthrough already exists today for a bundle secondary run alone after its leader worktree is deleted, because the content scan cannot read a missing directory. Any auto-prune keyed on the invocation's task ids leaves that case open (review D).
- **The task branch is not a sound bootstrap marker.** `ensureWorktree()` supports creating a worktree from a pre-existing branch (`worktree.ts:332-340`), so a leftover `refs/heads/task/<id>` can exist without bootstrap.
- **A fresh worktree from the branch is not the deleted worktree.** Post-implement artifacts (`handoff.md`, `review.md`, the worktree copy of `status.json`) stay uncommitted until the QA-end commit (`docs/patterns.md:127-129`).

The stale registration itself is exact evidence, independent of which task is being run: it exists only because a worktree was created, and its directory being gone is the precise hazard. So canon stops auto-pruning at the entry and instead refuses to run while that evidence exists.

### Decision change

1. **Refuse while any canon task worktree is registered but missing.** At the `canon run` entry, after `assertManagedInvocationRoot()` and before task cwd resolution and the AC-7 guard, canon enumerates registered worktrees once via the existing `listWorktreesWithBranches()` (`state.ts:146-184`). Every entry whose checked-out branch starts with `task/` and whose `worktree` path does not exist on disk (git also marks these `prunable` in `--porcelain` output; the on-disk check is the contract, the marker is corroboration) is a *missing canon worktree*. If there is at least one, `canon run` stops before any phase and before any runtime file is written. Detection is not keyed on the invocation's task ids: a stale registration for any canon task can make any task resolve to the wrong place, and a bundle secondary run alone has no main-checkout link to its leader, so the only safe rule is repo-wide. Worktrees on non-`task/` branches (an operator's own) are ignored.
2. **Fail closed on enumeration failure.** If `listWorktreesWithBranches()` reports failure, `canon run` stops with git's stderr and the words `git worktree list failed`, writing no runtime file. Its failure result gains git's stderr (additive field, Affected Files).
3. **The refusal names every missing worktree and both remedies.** For each: the registered path, its branch, and (a) restore a checkout from the branch with `git worktree add -f <path> <branch>` (`-f` is required because git otherwise refuses a registered-but-missing path), noting that anything not yet committed to the branch was lost with the directory; or (b) discard the registration with `git worktree remove --force <path>`. Both commands were verified against git on 2026-09-03. Canon does not run either itself.
4. **Canon does not prune or otherwise mutate worktree registrations at the entry.** `ensureWorktree()`'s own prune (AC-5) is unchanged and remains a defensive guard inside the create path; it is no longer an operator-facing recovery promise, because the entry refusal fires first whenever a canon registration is stale.
5. **Scope.** Steps 1–3 run for every `canon run` mode that passes `assertManagedInvocationRoot()`, except `--dry-run` (documented read-only) and `--ship` (documented unchanged; it keeps the existing partial-cleanup path). A run refused by the invocation-root guard from inside an old sibling directory never reaches them. `CANON_TASKS_DIR_OVERRIDE` skips them the same way it skips the AC-7 guard.
6. **Resolution stays untouched.** Non-Goals "No change to worktree resolution" and AC-6 remain binding.
7. **The recovery claim is narrowed to what is true.** After a hand-deletion of a registered canon worktree, the next `canon run` stops before any phase, names it, and gives the two commands. Canon recreates nothing itself.
