The orchestrator spawns headless Claude sessions with `--dangerously-skip-permissions` (`src/orchestrator/agents/claude.ts`) — necessary today because headless `-p` sessions cannot answer permission prompts and adopter validation commands cannot be allowlisted in advance. But it is the bluntest option and asymmetric with the Codex side, which runs under `--sandbox workspace-write` OS confinement.)*
  - **Evaluate**: Claude Code's sandboxed-bash settings (OS-sandboxed execution with escalation only on sandbox escape) and `--allowedTools` scoping as a replacement or partial confinement. Key risk to test: adopter validation commands that legitimately need network or system paths (installs, e2e suites, dev servers) breaking under the sandbox — the reason this can't be a blind swap.
  - **Probed 2026-09-04 (Claude Code 2.1.252 and 2.1.260)**, headless `claude -p` against a throwaway repo with four commands (write inside cwd, `npm --version`, `curl` to an external host, `rm` outside cwd):

This is the symmetric counterpart to Codex's `--sandbox workspace-write`. Adopters would supply `sandbox.network.allowedDomains` / `excludedCommands` (canon-ai's own settings already exclude `npm`/`npx` for this reason), so it should ship as an opt-in adopter setting, not a default swap.
    - **`--permission-prompts none` (2.1.259+)** turns a would-prompt into a deterministic "no approval surface … denied automatically" tool result instead of a stalled "I need your permission" reply. Useful for any non-bypass mode so the orchestrator can fail the phase cleanly; it does not replace the bypass on its own.
  - **Regardless of outcome, document the trust model** (pre-launch item): what pipeline sessions can do, what confines them (worktrees isolate git state, not the filesystem; budget caps bound cost, not access), and why the flag is there. README-level, near the permission-allowlist section.

- [ ] **Single chokepoint for the `human_review` `node_modules`-staging invariant** *(filed 2026-08-09 from `worktree-workspace-node-modules-links`'s code_review escalation. **Priority: medium — the invariant currently holds, but by accumulated patch rather than by construction; the next change to any of the three sites is the likeliest regression trigger.**)*
  - **Problem**: The invariant "no `node_modules` path is ever staged or committed by the `human_review` gate, and any non-exempt `node_modules` entry aborts" is enforced by three call sites that each normalize and match porcelain paths independently — `isExemptNodeModulesEntry()`'s allowlist filter, `buildHumanReviewStagePaths()`'s stage-path builder, and the `git add` pathspec construction at the directory-form-prefix call site in `commitHumanReviewFiles()` (`src/orchestrator/main.ts`).   - **Fix shape**: compute the final staged path set once, from a single canonicalized representation of the dirty entries, and enforce the `node_modules` invariant at that one point — so the allowlist, the stage-path builder, and the `git add` arguments read from the same source and cannot disagree with each other on quoting, Unicode normalization, or path-segment matching.

- [ ] **Implementation-prompt preloads read `REPO_ROOT`, not the active task worktree** *(filed 2026-07-30 from a source audit; confirmed against the post-1.5.0 worktree-canonical state model. **Priority: medium — prompt grounding can be materially stale on revision and reroute passes, even though Codex executes in the worktree.**)*
  - **Problem**: `buildContextBlock()` and `summarizePreloadStatus()` in `src/orchestrator/context.ts` resolve every `Affected Files` path from `REPO_ROOT`. Both are injected into the initial implement and reroute prompts via `promptImplement()` / `promptImplementReroute()` (`src/orchestrator/prompts/index.ts`). By the time either prompt is created, `runImplementPhase()` has already called `ensureBranch()` and selected `activeCwd = getActiveCwd(taskIds)` — the task worktree for a normal worktree-backed task — but the prompt's quoted source is still from the base checkout. The safety predicate has the same root assumption (`isSafeRepoPath()` checks against `REPO_ROOT`).
  - **Concrete reproduction**: start a worktree-mode task, let implement change an affected source file, then enter a code-review revision or human reroute while `REPO_ROOT` remains on the base branch. The prompt's `## Relevant Files` block includes the base version, while Codex's tool cwd and the task's `spec.md` / `handoff.md` point to the evolved worktree. A concurrent main-checkout change makes the mismatch worse: the prompt can preload unrelated main-only edits that do not exist in the branch Codex is editing.
  - **Why this matters**: the block is intended to ground the implementer before it writes code, so stale source can bias a revision toward already-fixed code paths or hide branch-only interfaces. This also contradicts the deliberate worktree-canonical rule: `buildKnownPitfalls()` already reads `getActiveCwd(taskIds)`, and `taskDirFor()` correctly resolves the worktree's task artifacts.
  - **Fix shape**: resolve the active cwd once for context construction and use it consistently for the safety check, reads, and byte-count summary. Preserve the current symlink-escape protection, but validate real paths against that resolved active cwd (not the main checkout). Avoid silently falling back to `REPO_ROOT` when a worktree is expected; the existing worktree resolver is deliberately fail-closed. Consider passing the resolved cwd into the context helpers so a single prompt render cannot resolve different roots mid-render.
  - **Verification**: add focused tests with a declared affected file that has distinct base and worktree contents; assert that both fresh/revision and reroute prompts quote the worktree content and never the base content. Cover a branch-only new file and a symlink escaping the active cwd. Retain a non-worktree fixture to prove in-place tasks still preload from `REPO_ROOT`.
  - **Effort**: `S` — context-root plumbing plus targeted prompt tests; no routing or artifact-schema change.

- [~] **Telemetry discrimination gate at scaffold-commit time** *(carved out of `worktree-canonical-task-state` 2026-05-25 after 5 spec_review iterations each finding new bugs in the parser-based design; parked 2026-05-26 as `tasks/telemetry-discrimination-gate/` with the SINGLE-LAYER dirty-at-entry design fully spec'd; the size-trajectory layer was carved out as a separate entry below after 2 rounds of new-bug-class findings in pre-pipeline review. **Why parked**: the gate catches a real-but-rare operator-error class (dirty telemetry from interrupted prior `canon run` absorbed under a new task's scaffold). No actual misattribution incident has driven it; touching `commitTaskArtifactsToBase` (auto-commit hot path) for a low-frequency safety net is risk-asymmetric, and the simplified design still has a documented limitation on concurrent worktree-mode pipelines that operator discipline already handles. Operator-discipline note in CLAUDE.md Quick Refs remains the active mitigation. Pick up when an actual misattribution incident appears in canon-ai or an adopter. Spec at `tasks/telemetry-discrimination-gate/spec.md` is the start point.)*
  - **Problem**: When `commitTaskArtifactsToBase` absorbs dirty `PIPELINE_TELEMETRY_FILES` (`docs/pipeline-invocations.md`, `docs/task-quality-log.md`, `docs/lessons-learned.md`) into the per-task scaffold commit (worktree-canonical-task-state, AC-22d), there is no check that the absorbed rows actually belong to the current invocation. If the operator runs `canon run B` while `pipeline-invocations.md` still has uncommitted rows from a prior `canon run A`, Task A's rows get committed under Task B's scaffold message — misattribution baked into git history.
  - **Why operator discipline is the interim mitigation** *(documented in CLAUDE.md Quick refs)*: the failure requires a specific operator mistake (leaving prior-task telemetry uncommitted across invocations); the rows have task IDs in their content, so misattribution is detectable in PR review; recovery is `git revert` + re-commit under the right task. Acceptable trade-off for now.
  - **Why the parser-based design didn't ship** *(carve-out from worktree-canonical-task-state iter 5)*: original AC-22g proposed per-file parsers — markdown table with Task at column index 2 for `pipeline-invocations.md`, table with Task at column index 2 for `task-quality-log.md` (different leading columns), and a heading-bounded entry walker with source-marker regex for the prose `lessons-learned.md`. Plus bundle-label `+`-splitting, plus both-staged-and-unstaged diff inspection, plus append-only discipline (every dirty line must be a current-task append; deletions, header edits, preamble edits, and in-place modifications all fail closed). Five spec_review iterations each found a new bug in a different sub-concern (bundle labels, lessons-learned format, staged-vs-unstaged, column index, append vs whole-file commit). A sixth was already queued — iter-5 pre-flight caught the source-marker regex `[a-z0-9._+-]` rejecting ~95% of real entries (real values use `v1.3.0`, `PR #82`, `CLAUDE.md`, mixed case + spaces). The iteration cost (hours of pipeline time + Codex/Claude tokens per round) exceeded the value of the gate. The parser surface is intrinsically too big — three formats, two diff streams, hunk-header arithmetic, header/separator detection, preamble carve-outs.
  - **Candidate design — snapshot-offset, not parser-based**: telemetry files are written exclusively via `fs.appendFileSync` (verify at `src/orchestrator/metrics.ts:30` and the QA-phase appends in `agents/claude.ts`). At pipeline entry (before any pre-implement phase runs), `fs.statSync` each `PIPELINE_TELEMETRY_FILES` entry and record byte length in an in-memory snapshot. At `commitTaskArtifactsToBase` time, bytes past the snapshot offset are current-invocation appends *by construction*; pre-snapshot bytes that have changed are foreign edits (deletions, in-place modifications, header edits — anything not produced by this invocation). The gate becomes one comparison per file: "did anything before the snapshot offset change?" If yes → die / `--force`. If no → absorb the appended bytes. Format-agnostic. Survives future telemetry file additions for free. No regex. No column-index dispatch. No entry walker. Bundle-label / Date-column / preamble-edit bug classes from worktree-canonical-task-state iters 2-5 cannot exist.
  - **Shape**:
    - Module-local map in (probably) `src/orchestrator/main.ts` or a new `src/orchestrator/telemetry-snapshot.ts`: `Map<string, number>` keyed by absolute file path, populated at orchestrator entry by `fs.statSync(file).size` for each `PIPELINE_TELEMETRY_FILES` entry that exists.
    - `commitTaskArtifactsToBase` gains an `options: { force: boolean }` third parameter. Before the absorption phase, for each dirty `PIPELINE_TELEMETRY_FILES` entry: compare current `fs.statSync(file).size` and `fs.readFileSync(file).slice(0, snapshot[file])` against the snapshot. If pre-snapshot bytes are unchanged AND the file has grown, absorb only. If pre-snapshot bytes have changed (anywhere — deletion shrinks the file, edit changes a byte before the offset), this is a foreign edit → die unless `--force`. Die message names which file's pre-snapshot region changed.
    - `--force` plumbing through `runImplementPhase` exactly as the carved-out AC-22g specified — that part of the design was sound (Codex didn't object to the plumbing, only the parser).
    - Tests: snapshot-then-append → silent absorb; snapshot-then-edit-pre-snapshot-byte → die without `--force`, warn-and-absorb with `--force`; snapshot-then-delete-row → die; no-snapshot-recorded (orchestrator crashed and restarted mid-pipeline) → fall back to fail-closed (anything dirty dies unless `--force`).
  - **What's NOT in scope**:
    - Cross-orchestrator-process discrimination — if the operator restarts the orchestrator mid-pipeline (e.g., bash session died, see related fragility entry), the in-memory snapshot is gone. Recovery: fall back to `--force`-required for any dirty telemetry. Acceptable: restart is rare, and the operator who restarts already knows they're carrying state across processes.
    - Persisting the snapshot to disk to survive orchestrator restarts. Could be added later if dogfood shows restart-recovery is frequent; YAGNI for v1.
    - Discrimination at finer granularity than file-level (per-row task-ID attribution). The snapshot approach answers "did this invocation produce these bytes?" not "which task within a bundle produced row N?" — bundle-mode rows are attributed to the bundle as a whole, which matches how `metricsContext.taskId = taskIds.join('+')` already labels them.
  - **Risks to watch**:
    - **Non-`appendFileSync` writer regression**: if a future change introduces an in-place write to a telemetry file (e.g., a "fix typo" automation), the snapshot approach correctly flags that as a non-current-invocation edit and dies. Same failure mode as the parser approach would have had; both depend on the append-only invariant. Document this in the `docs/decisions.md` entry: "do not introduce non-append writers to `PIPELINE_TELEMETRY_FILES`."
    - **Race against pre-implement phase telemetry**: spec_review and plan phases append rows; the snapshot must be taken BEFORE those phases run, not at `commitTaskArtifactsToBase` entry (by which time current-invocation appends are already in the file and would be wrongly classified as pre-snapshot). Solution: snapshot at orchestrator entry, before `dispatch()` runs any phase. Verify with an integration test that runs spec_review → plan → implement and asserts no false foreign-detection.
    - **File doesn't exist yet at snapshot time**: a fresh project might not have `docs/lessons-learned.md` yet. Snapshot records absence (e.g., `snapshot[file] = 0` or sentinel); if the file later exists and is dirty, the whole file counts as "current-invocation append" (correct). If the file existed and was deleted (rare, operator edit), the snapshot offset would be > current size → treat as foreign edit → die.
  - **Sequencing**: `worktree-canonical-task-state` has shipped (PR #104 / 1.5.0); this gate now layers on top of AC-22d's unconditional absorption commit. Actionable for v1.5+.
  - **Effort**: `S`. Snapshot map (~10 lines), comparison function (~20 lines), `--force` plumbing (~30 lines mirroring the carved-out AC-22g design), tests (~50 lines). Total ~110 lines vs. the carved-out parser-based AC-22g's ~80-line spec text alone (implementation would have been multiples of that).

- [ ] **Scoped Audits Framework + `guard_audit` as the First Audit** *(designed 2026-05-07 from a multi-agent review thread)*
  - **Scope**: Generalize `code_review` from one omnibus reviewer into a *stage* that fans out to N specialist auditors, each scoped to a single concern. The current code-review prompt asks the reviewer to check a long list of things in one pass — spec compliance, validation gates, citation grounding, plan deviations, cross-cutting guards, and so on. Specialist agents with focused prompts and dedicated artifacts are easier to author, easier to evolve, harder to skip silently, and parallelizable. - [ ] **`architect_review` lens — semantic sign-off as a cold sub-agent in the multi-agent review system** *(designed 2026-05-09 as a standalone phase; reframed 2026-06-05 — the design is sound but the right vehicle is a cold sub-agent lens in `multi-agent-code-review`, not a separate pipeline phase)*
  - **Reframe**: The original design called for a new pipeline phase between `code_review` and `qa`. With `multi-agent-code-review` (currently in `plan`) restructuring code review into multiple cold/anchored lenses + a synthesis foreman, the architect reviewer is better realized as one of those cold lenses. The phase-level infrastructure (new `PHASE_ORDER` entry, new routing in `checkAndRoute`, new `status.json` phase block, new templates) goes away; the prompt design — context isolation, adversarial persona, forced counterfactual, four shape questions, three-way verdict — is exactly what a cold sub-agent lens should do. This entry is preserved for the prompt design detail below; whoever specs the architect lens in `multi-agent-code-review` should draw from it.
  - **Original scope (still valid as lens design)**: A cold sub-agent that asks a fundamentally different question than the anchored reviewer: "ignoring whether the patch technically works, is this the right *solution shape* for the problem?" Fresh session, strict context isolation, opinionated senior-engineer persona, forced counterfactual. Three-way verdict: `agree`, `concern_for_human_attention`, or `block_due_to_architecture_risk`.
  - **Why it's wanted**: code review is line-level — "does this implementation match the spec?" QA is operational — "can we verify behavior with tests?" Neither asks the 30k-ft question: "did this *solve the stated problem*, or did it just satisfy the ACs?" "Are we painting ourselves into a corner?" "Is the spec's framing still right in light of what got built?" Today that check is implicit in the human gate — the human reads `done.md` and either notices semantic drift or doesn't. A structured architect review pre-flags specific shape concerns rather than relying on the human to spot them cold.
  - **Why same-model is acceptable here (the no-self-review principle, refined)**: canon's no-self-review rule strictly read is "no same-model review of the same question with the same context." Architect review asks a *different question* than code review (solution shape vs. line-level correctness), in a *different context* (fresh session, no code-review rationale, opinionated persona). It is not self-review under the strict reading even though both phases are run by Claude. Persona-shift produces independence of question, not independence of blind spots — accepted weakness. This is the *best* place to relax cross-model purity because the failure modes that matter at 30k ft (corner-painting, scope drift, "satisfied ACs but didn't solve the problem") are intuition-level, not LLM-blind-spot-level. The principle should be promoted into `AGENTS.md` as part of this work so the rule is explicit before the phase ships.
  - **Triggering rules**:
    - **Required** for `task_size ∈ {M, L, XL}` and any `delicate: true` task.
    - **Skipped** for `task_size = S` non-delicate (overhead not justified for tiny patches).

  - **Phase shape and gating**:
    - Runs only when `code_review.verdict ∈ {approved, approved_with_nits}`. If code review is `changes_requested`, the pipeline iterates implement → code review as today. Architect review is downstream of code-review approval; it never fires against a known-broken state.
    - **Single-shot, no review-loop.** Architect review is not iterative — its concerns are upstream-of-implementation (spec / plan / shape), not implementation defects. A `block_due_to_architecture_risk` verdict halts and routes to the human, who decides whether to revise spec, replan, or override. No automatic bounce back to Codex (different from `code_review` failures).
    - `agree` → orchestrator advances to `qa` silently.
    - `concern_for_human_attention` → orchestrator advances to `qa`, sets a flag the QA prompt reads to surface the concern in `done.md` under a new *Architect concerns* section.
    - `block_due_to_architecture_risk` → orchestrator halts, prints the concern, exits non-zero. Operator triggers `--reroute` (existing mechanism) to route back to spec/plan, or overrides via manual phase update.
  - **Inputs (context isolation is load-bearing)**:
    - `spec.md`, `plan.md` (full).
    - The diff (`git diff <baseline>...HEAD`).
    - `code_review.verdict` only — **NOT** the rationale or finding text. Sharing rationale anchors the architect review onto the code review's prior conclusions, defeating the persona-shift. Worth A/B testing whether to share the verdict at all (see Risks).

    - **Explicitly excluded**: `review.md` body, `notes.md`, prior architect-review artifacts.
  - **Prompt design constraints**:
    1. **Fresh session, adversarial persona.** "You are a senior engineer pulled in to challenge this result, not bless it. Default disposition is skeptical. If the work looks fine, you must defend that conclusion against your own challenge."
    2. **Question explicitly different from code review.** Asks: "Did this solve the problem stated in the spec, or just satisfy the ACs?" "Does anything look like a corner-painting choice future work will regret?" "Is the spec itself still the right framing in light of how this came out?" Does NOT ask "is the code correct" or "does the diff match the spec line-by-line."

    4. **Output schema forces explicit position.** Three-way verdict mandatory. Free-text concern justification required only on `concern_for_human_attention` or `block_due_to_architecture_risk`. Verdict is not the path of least resistance — the model must actively choose a stance, including a defended `agree`.
  - **Artifact and status integration**:
    - New artifact: `tasks/<id>/architect-review.md`. Template carries the four-question structure (problem still correctly framed? solution shape appropriate? hidden future-cost / corner-painting risk? human attention warranted?) plus the verdict and (when non-`agree`) the concern justification.

  - **What's built (estimated 400–600 lines)**:

    - Artifact template `.canon/templates/architect-review.md`.
    - QA prompt update for *Architect concerns* surfacing.

    - `CLAUDE.md` updates: pipeline-mode role lists architect review; explicit guidance on the persona, context isolation, and counterfactual.
    - `docs/task-quality-log.md` schema additions.
  - **Failure mode to watch — "architect-review-as-cosplay"**: same-model review with a thin persona produces bland approvals that look like signal but aren't. Symptoms: high `agree` rate with vague concerns, the model echoing code review's framing despite isolation, "looks good" with no counterfactual content. Mitigations are all in the prompt: force the counterfactual, exclude code-review rationale, structure the output schema to require explicit position-taking, monitor verdict distribution in the quality log.   - **Risks to watch**:

  - **Problem**: `guardConcurrentRun` (`src/orchestrator/main.ts:166`) reads `.canon-pid` and `.heartbeat.json` and dies if either points to a live foreign process. The check is a read-only preflight — two `canon run` invocations that start within the same Node-boot window (~200ms) can both observe an empty task dir before either writes a runtime file, and both proceed to the pipeline loop against the same task, corrupting each other's git state.
  - **Why it doesn't bite in practice**: the guard was introduced to block the "operator accidentally started a new run in the middle of an existing run" scenario, which always has seconds between the two invocations (human reaction time). The race window requires two starts within milliseconds — only possible via a script or CI system, which should be using distinct worktrees and branches (the safe multi-task pattern).
  - **Decision (proposed)**: make the initial claim atomic using `O_EXCL`. Before spawning the child, the parent writes `.canon-claim` via `fs.writeFileSync(path, pid, { flag: 'wx' })` — first writer wins, second gets `EEXIST` and dies. The parent removes `.canon-claim` immediately after writing `.canon-pid` (heartbeat then owns liveness). Stale claims (dead PID in `.canon-claim`) are cleaned up by the guard before the write attempt.
  - **Affected files**: `src/orchestrator/detach.ts` (`detachAndExit` — claim write before spawn, removal after PID write); add `removeCanonClaim` to the shutdown-hook registry alongside `removeCanonPid`; `tests/detach.test.ts` (2 new cases: concurrent parent wins, concurrent parent loses).
  - **Effort**: `S`. ~30 lines in `detachAndExit` + shutdown hook wiring + 2 tests.
