- [ ] **Evaluate confining pipeline Claude sessions instead of `--dangerously-skip-permissions`** *(filed 2026-08-13 during open-source prep. The orchestrator spawns headless Claude sessions with `--dangerously-skip-permissions` (`src/orchestrator/agents/claude.ts`) — necessary today because headless `-p` sessions cannot answer permission prompts and adopter validation commands cannot be allowlisted in advance. But it is the bluntest option and asymmetric with the Codex side, which runs under `--sandbox workspace-write` OS confinement.)*
  - **Evaluate**: Claude Code's sandboxed-bash settings (OS-sandboxed execution with escalation only on sandbox escape) and `--allowedTools` scoping as a replacement or partial confinement. Key risk to test: adopter validation commands that legitimately need network or system paths (installs, e2e suites, dev servers) breaking under the sandbox — the reason this can't be a blind swap.
  - **Probed 2026-09-04 (Claude Code 2.1.252 and 2.1.260)**, headless `claude -p` against a throwaway repo with four commands (write inside cwd, `npm --version`, `curl` to an external host, `rm` outside cwd):
    - **Auto mode is not a candidate yet.** `--permission-mode auto` is silently demoted in print mode: the stream-json `init` event reports `permissionMode: "auto"`, a `status` event flips it to `"default"` before the first tool call, and every command is denied with the plain "This command requires approval" text, never a classifier verdict. Same result when set via `--settings '{"permissions":{"defaultMode":"auto"}}'`, with `--permission-prompts host` or `none`, under a pseudo-TTY, and `--debug` logs no reason. The headless docs claim auto mode works in `-p`; it does not on these builds. Re-test when a release notes headless classifier support; until then this is likely worth a Claude Code issue.
    - **`--allowedTools` works headless but doesn't fit.** Listed commands run, unlisted ones hard-deny mid-phase, and canon cannot know an adopter's validation commands in advance — the same constraint as above, now confirmed.
    - **The sandbox is the real candidate.** `sandbox.enabled` + `autoAllowBashIfSandboxed` under default mode ran the cwd write and `npm --version`, blocked `curl` with a `deny network-outbound` violation surfaced in the tool result, and blocked the write outside cwd. This is the symmetric counterpart to Codex's `--sandbox workspace-write`. Adopters would supply `sandbox.network.allowedDomains` / `excludedCommands` (canon-ai's own settings already exclude `npm`/`npx` for this reason), so it should ship as an opt-in adopter setting, not a default swap.
    - **`--permission-prompts none` (2.1.259+)** turns a would-prompt into a deterministic "no approval surface … denied automatically" tool result instead of a stalled "I need your permission" reply. Useful for any non-bypass mode so the orchestrator can fail the phase cleanly; it does not replace the bypass on its own.
  - **Regardless of outcome, document the trust model** (pre-launch item): what pipeline sessions can do, what confines them (worktrees isolate git state, not the filesystem; budget caps bound cost, not access), and why the flag is there. README-level, near the permission-allowlist section.
  - **Effort**: `S` for the trust-model doc; `M` for the confinement evaluation (needs empirical testing against real adopter-style validation commands).

- [ ] **Full-send `spec_gap` auto-amend** *(deferred from `multi-agent-code-review` MVP, 2026-06-06)*
  - **Context**: `multi-agent-code-review` added the `spec_gap` verdict: the synthesis foreman classifies a finding as `spec_gap` when the implementation is correct but the spec is missing/wrong/ambiguous, and the orchestrator **halts for human amendment** rather than rerouting to implement. In the MVP this halt fires **even under `full_send`** — full-send tasks still stop at a spec_gap.
  - **Problem**: a `full_send: true` task is an explicit "don't interrupt me before the PR" call, yet a `spec_gap` breaks that contract by halting. The MVP chose halt-always because auto-amending a spec from an LLM verdict is delicate (it mutates the human-authored `spec.md` on the strength of a review finding) and the infra to do it safely didn't exist yet.
  - **Decision (proposed, when picked up)**: under `full_send`, on a `spec_gap` verdict, have a focused Claude session draft a spec **Amendment** section addressing the gap, re-run `spec_review` on the amendment, then continue the pipeline — instead of halting. Gate behind `full_send` only; non-full-send stays halt-for-human. Relates to the existing "QA auto-amends spec.md's Affected Files when promoting" idea (below) — both mutate spec.md programmatically and should share whatever guardrails that boundary needs (provenance marker, human-visible diff in `done.md`, never touch ACs without a re-review).
  - **Risks**: auto-mutating human-authored `spec.md`; an LLM `spec_gap` that's actually a code bug in disguise would get papered over by a spec edit. Mitigate by always routing the auto-amendment back through `spec_review` before resuming, and surfacing the amendment prominently at human_review.
  - **Effort**: `M`. New full-send branch in the spec_gap handler + amendment-drafting prompt + re-review wiring + tests; the delicate part is the guardrails, not the plumbing.

- [~] **Telemetry discrimination gate at scaffold-commit time** *(carved out of `worktree-canonical-task-state` 2026-05-25 after 5 spec_review iterations each finding new bugs in the parser-based design; parked 2026-05-26 with the SINGLE-LAYER dirty-at-entry design fully spec'd, and since moved to `tasks/_archive/telemetry-discrimination-gate/` **without ever shipping** — its `status.json` is still `spec_review` / `pending`, so the archive location records abandonment, not delivery; the size-trajectory layer was carved out as a separate entry below after 2 rounds of new-bug-class findings in pre-pipeline review. **Why parked**: the gate catches a real-but-rare operator-error class (dirty telemetry from interrupted prior `canon run` absorbed under a new task's scaffold). No actual misattribution incident has driven it; touching `commitTaskArtifactsToBase` (auto-commit hot path) for a low-frequency safety net is risk-asymmetric, and the simplified design still has a documented limitation on concurrent worktree-mode pipelines that operator discipline already handles. Operator-discipline note in CLAUDE.md Quick Refs remains the active mitigation. Pick up when an actual misattribution incident appears in canon-ai or an adopter. Spec at `tasks/_archive/telemetry-discrimination-gate/spec.md` is the start point.)*
  - **Problem**: When `commitTaskArtifactsToBase` absorbs dirty `PIPELINE_TELEMETRY_FILES` (`docs/pipeline-invocations.md`, `docs/task-quality-log.md`, `docs/lessons-learned.md`) into the per-task scaffold commit (worktree-canonical-task-state, AC-22d), there is no check that the absorbed rows actually belong to the current invocation. If the operator runs `canon run B` while `pipeline-invocations.md` still has uncommitted rows from a prior `canon run A`, Task A's rows get committed under Task B's scaffold message — misattribution baked into git history.
  - **Why operator discipline is the interim mitigation** *(documented in CLAUDE.md Quick refs)*: the failure requires a specific operator mistake (leaving prior-task telemetry uncommitted across invocations); the rows have task IDs in their content, so misattribution is detectable in PR review; recovery is `git revert` + re-commit under the right task. Acceptable trade-off for now.
  - **Why the parser-based design didn't ship** *(carve-out from worktree-canonical-task-state iter 5)*: original AC-22g proposed per-file parsers — markdown table with Task at column index 2 for `pipeline-invocations.md`, table with Task at column index 2 for `task-quality-log.md` (different leading columns), and a heading-bounded entry walker with source-marker regex for the prose `lessons-learned.md`. Plus bundle-label `+`-splitting, plus both-staged-and-unstaged diff inspection, plus append-only discipline (every dirty line must be a current-task append; deletions, header edits, preamble edits, and in-place modifications all fail closed). Five spec_review iterations each found a new bug in a different sub-concern (bundle labels, lessons-learned format, staged-vs-unstaged, column index, append vs whole-file commit). A sixth was already queued — iter-5 pre-flight caught the source-marker regex `[a-z0-9._+-]` rejecting ~95% of real entries (real values use `v1.3.0`, `PR #82`, `CLAUDE.md`, mixed case + spaces). The iteration cost (hours of pipeline time + Codex/Claude tokens per round) exceeded the value of the gate. The parser surface is intrinsically too big — three formats, two diff streams, hunk-header arithmetic, header/separator detection, preamble carve-outs.
  - **Candidate design — snapshot-offset, not parser-based**: telemetry files are written exclusively via `fs.appendFileSync` (verify at `src/orchestrator/metrics.ts:30` and the QA-phase appends in `agents/claude.ts`). At pipeline entry (before any pre-implement phase runs), `fs.statSync` each `PIPELINE_TELEMETRY_FILES` entry and record byte length in an in-memory snapshot. At `commitTaskArtifactsToBase` time, bytes past the snapshot offset are current-invocation appends *by construction*; pre-snapshot bytes that have changed are foreign edits (deletions, in-place modifications, header edits — anything not produced by this invocation). The gate becomes one comparison per file: "did anything before the snapshot offset change?" If yes → die / `--force`. If no → absorb the appended bytes. Format-agnostic. Survives future telemetry file additions for free. No regex. No column-index dispatch. No entry walker. Bundle-label / Date-column / preamble-edit bug classes from worktree-canonical-task-state iters 2-5 cannot exist.
  - **Shape**:
    - Module-local map in (probably) `src/orchestrator/main.ts` or a new `src/orchestrator/telemetry-snapshot.ts`: `Map<string, number>` keyed by absolute file path, populated at orchestrator entry by `fs.statSync(file).size` for each `PIPELINE_TELEMETRY_FILES` entry that exists.
    - `commitTaskArtifactsToBase` gains an `options: { force: boolean }` third parameter. Before the absorption phase, for each dirty `PIPELINE_TELEMETRY_FILES` entry: compare current `fs.statSync(file).size` and `fs.readFileSync(file).slice(0, snapshot[file])` against the snapshot. If pre-snapshot bytes are unchanged AND the file has grown, absorb only. If pre-snapshot bytes have changed (anywhere — deletion shrinks the file, edit changes a byte before the offset), this is a foreign edit → die unless `--force`. Die message names which file's pre-snapshot region changed.
    - `--force` plumbing through `runImplementPhase` exactly as the carved-out AC-22g specified — that part of the design was sound (Codex didn't object to the plumbing, only the parser).
    - Tests: snapshot-then-append → silent absorb; snapshot-then-edit-pre-snapshot-byte → die without `--force`, warn-and-absorb with `--force`; snapshot-then-delete-row → die; no-snapshot-recorded (orchestrator crashed and restarted mid-pipeline) → fall back to fail-closed (anything dirty dies unless `--force`).
  - **What's NOT in scope**:
    - Cross-orchestrator-process discrimination — if the operator restarts the orchestrator mid-pipeline (e.g., bash session died, see related fragility entry), the in-memory snapshot is gone. Recovery: fall back to `--force`-required for any dirty telemetry. Acceptable: restart is rare, and the operator who restarts already knows they're carrying state across processes.
    - Persisting the snapshot to disk to survive orchestrator restarts. Could be added later if dogfood shows restart-recovery is frequent; YAGNI for v1.
    - Discrimination at finer granularity than file-level (per-row task-ID attribution). The snapshot approach answers "did this invocation produce these bytes?" not "which task within a bundle produced row N?" — bundle-mode rows are attributed to the bundle as a whole, which matches how `metricsContext.taskId = taskIds.join('+')` already labels them.
  - **Risks to watch**:
    - **Non-`appendFileSync` writer regression**: if a future change introduces an in-place write to a telemetry file (e.g., a "fix typo" automation), the snapshot approach correctly flags that as a non-current-invocation edit and dies. Same failure mode as the parser approach would have had; both depend on the append-only invariant. Document this in the `docs/decisions.md` entry: "do not introduce non-append writers to `PIPELINE_TELEMETRY_FILES`."
    - **Race against pre-implement phase telemetry**: spec_review and plan phases append rows; the snapshot must be taken BEFORE those phases run, not at `commitTaskArtifactsToBase` entry (by which time current-invocation appends are already in the file and would be wrongly classified as pre-snapshot). Solution: snapshot at orchestrator entry, before `dispatch()` runs any phase. Verify with an integration test that runs spec_review → plan → implement and asserts no false foreign-detection.
    - **File doesn't exist yet at snapshot time**: a fresh project might not have `docs/lessons-learned.md` yet. Snapshot records absence (e.g., `snapshot[file] = 0` or sentinel); if the file later exists and is dirty, the whole file counts as "current-invocation append" (correct). If the file existed and was deleted (rare, operator edit), the snapshot offset would be > current size → treat as foreign edit → die.
  - **Sequencing**: `worktree-canonical-task-state` has shipped (PR #104 / 1.5.0); this gate now layers on top of AC-22d's unconditional absorption commit. Actionable for v1.5+.
  - **Effort**: `S`. Snapshot map (~10 lines), comparison function (~20 lines), `--force` plumbing (~30 lines mirroring the carved-out AC-22g design), tests (~50 lines). Total ~110 lines vs. the carved-out parser-based AC-22g's ~80-line spec text alone (implementation would have been multiples of that).

- [ ] **Scoped Audits Framework + `guard_audit` as the First Audit** *(designed 2026-05-07 from a multi-agent review thread)*
  - **Scope**: Add an *audits* stage that fans out to N specialist auditors, each scoped to a single concern. **Current baseline (2026-09-04)**: `code_review` is already multi-agent — three cross-family lenses (anchored Claude via `.claude/agents/code-review-anchored.md`, cold spec-blind Claude via `.claude/agents/code-review-cold.md`, and a cold Codex pass) synthesized by a foreman (`src/orchestrator/prompts/templates/code-review-foreman.md`). Scoped audits are a **different axis** than review lenses: lenses vary the *reviewer's* perspective over the whole diff, while audits are repeatable domain checks (a11y, perf, breaking-change, guard preservation) selected from a registry by condition, each with a focused prompt and a dedicated artifact — easier to author, easier to evolve, harder to skip silently, and parallelizable. Step 1 is the framework + first audit (`guard_audit`); Step 2 (deferred until Step 1 has shipped through one delicate task on a real project) adds a second audit to prove the generalization.
  - **Framework shape**: A new pipeline stage `audits` sits between `code_review` and `qa`. It runs zero-or-more registered audits sequentially (parallelize later if wall time grows). Each audit is a small plugin: `{ name, when(status, files) → boolean, promptBuilder, artifact, collector?, config? }`. Registry lives in `src/lib/pipeline-policy.ts`. Verdict aggregation: any audit FAIL → reroute to implement (audit artifacts join `review.md` as feedback); all PASS → advance to qa. Implement-revision prompt updated to read `tasks/<id>/audits/*.md` for FAILED audits alongside `review.md §Round N`.
  - **`status.json` shape**: `phases.audits` becomes a container with sub-items (`items.<name>.status`, `items.<name>.verdict`, `items.<name>.iterations`) mirroring the existing phase shape so the dispatcher reuses most routing logic. `src/task/index.ts` gains a subcommand to advance audit items.
  - **Artifact layout**: `tasks/<id>/audits/<name>.md`, one per audit. Templates in `.canon/templates/audits/<name>.md`. Each audit's artifact follows the same skeleton: per-item verification table, verdict checkbox, required actions if FAILED.
  - **First audit — `guard_audit`**: Triggered by `delicate: true`. Hybrid script + LLM. The collector (`scripts/guard-audit-collect.ts`) reads a project-defined registry at `.canon/guards.json` (a small list of guard helper names — auth helpers, feature-gating wrappers, mutation-chokepoint validators — registered per-project), greps the task baseline and HEAD for call sites of each guard, extracts the containing function for each call site, and emits structured JSON. The LLM step (focused Claude phase) reads the JSON + `spec.md` + diff and decides per call site: PRESERVED / RELOCATED (guard moved up the call stack to a wrapper that still gates every entry point) / DROPPED (operation still exists but guard is gone — automatic FAIL) / OBSOLETE (operation no longer requires the guard and `spec.md` authorizes removal — citation required). Writes verdict to `audits/guard.md`.
  - **Triggering failure pattern**: A delicate refactor that consolidates mutation entry points (e.g., moves several call sites into a single store action or shared helper) can silently drop the cross-cutting guards that wrapped the original sites. The general code-review prompt has too much else to check; a specific "for each pre-refactor guard call site, find the post-refactor equivalent and verify the guard survives" pass is what catches this reliably. The CLAUDE.md/AGENTS.md rule alone has historically not been enough — a memory rule that didn't stick becomes a deterministic check.
  - **What's built in Step 1**: `audits` field in `status.json` + `src/task/index.ts` subcommand; `Audit` type + registry in `pipeline-policy.ts`; `runAuditsPhase()` in `run-task.ts` (sequential dispatch loop); reroute-on-failure routing in `checkAndRoute`; the `guard_audit` collector + prompt + template; implement-revision prompt updated; `AGENTS.md` / `CLAUDE.md` docs on the new phase. Estimated 600–800 lines total.
  - **Marginal cost of audit #2**: ~150 lines (prompt builder + template + registry entry + optional collector). The framework absorbs the structural cost.
  - **Punted to later iterations**: auto-detection of which audits to enable from changed paths (start manual: opt in via flags or simple conditions like `delicate: true`); parallel audit execution; per-audit iteration limits and round-2+ slim prompts (audit count is small enough that shared iteration counters and full prompts every round are fine for now); audit-level session resume (audits are stateless one-offs like QA, no resume needed).
  - **Future audits worth adding** (each is a separate ~150-line addition once the framework exists, not separate backlog entries):
    | Audit | When | What it checks |
    |---|---|---|
    | **a11y** | Affected Files include UI component paths | WCAG AA — contrast, focus order, keyboard nav, ARIA |
    | **perf** | Affected Files include hot-path components / hooks | direct DOM writes preserve framework reconciliation contract; no re-render thrash; paint regressions |
    | **breaking-change** | Affected Files include public type surfaces | exported types preserved or deprecations documented |
    | **e2e-locator-coverage** | Diff touches user-visible labels/buttons | every changed label has updated e2e locator (catches the "test deferred while button name changed" pattern) |
    | **citation-grounding** | docs-check flagged any package | every flagged package has a real API cited in handoff. Often inside the omnibus code-review prompt today; extracting it tightens that prompt and gives citations a dedicated artifact. |
    | **deploy-smoke** | Affected Files include deployment config (vercel.json, next.config.js, route configs) | required preview-environment HTTP checks (`/`, `/login`, key routes); local build pass is not enough for route/config tasks. Surfaced from TokenAnxiety dogfood discussion #27 — ui-001 passed local validation but the Vercel preview exposed 404s from `cleanUrls: true` interacting with rewrite destinations. |

    Project-specific audits register their own conditions; canon ships the framework and a couple of generic audits, projects layer on what they need.
  - **Risks to watch**: (a) false positives on legitimate guard consolidation — if a refactor pulls multiple guards into one wrapper, the script flags multiple "DROPPED"; the LLM RELOCATED verdict handles this but the prompt must explicitly check "is the wrapper reachable from every entry point?"; (b) `.canon/guards.json` registry drift — needs a maintenance home, probably appended during the periodic lessons-sweep when a new guard helper is introduced; (c) scope leakage — should the audit grep all of `src/` or just files in spec's Affected Files? Probably all of `src/`, since *unlisted* call sites are exactly where guards get silently dropped.
  - **Why this generalizes the multi-agent-review pattern**: Specialist agents with different scopes are the direction the ecosystem is heading — OpenHands has SecurityAnalyzer, Aider's architect mode externalizes the planner/editor split, hobbyist setups are ad-hoc fanning out review concerns to multiple Claude calls. This framework is the orchestrator-level realization of that pattern: each audit is an agent with a single concern, focused prompt, and dedicated artifact, all routed by data rather than handcrafted dispatch logic. Audit #2 is the proof that generalizes.

- [ ] **`canon init --ninja-mode` (interactive prompt during `canon init`)** *(framed 2026-05-19 from GP work-repo dogfood)*
  - **Scope**: During `canon init`, ask the operator whether canon's on-disk footprint should be **tracked in the repo** (the current default — `.canon/`, `.claude/`, `.codex/`, `AGENTS.md`, `CLAUDE.md`, `CODEX.md`, `docs/`, `tasks/` all become committed adopter content) or kept **local-only / "ninja mode"** (written to `.git/info/exclude`, never `.gitignore`, so the canon infrastructure stays invisible to teammates and PR diffs). 1.3.0 already ships the PR-body half of ninja mode via `CANON_PR_BODY` env var; this entry covers the filesystem half.
  - **Why it's wanted**: adopters using canon in work/employer repos often don't want to advertise the tool — either because the repo has a strict committed-content policy, because the team hasn't adopted canon yet and the canon files would clutter teammate diffs, or for personal preference. Today they have to either (a) commit canon infra and live with the leak, (b) hand-edit `.git/info/exclude` after every `canon init` and `canon upgrade`, or (c) abandon canon for that repo.
  - **Working pattern (from the GP work-repo dogfood)**: the operator's `.git/info/exclude` contained exactly these lines and the run was clean end-to-end:
    ```
    .canon/
    .claude/
    .codex/
    AGENTS.md
    CLAUDE.md
    CODEX.md
    docs/
    tasks/
    ```
  - **Proposed shape**:
    - **`canon init` prompt**: after detecting it's running in a git repo, ask "Track canon infrastructure in this repo, or keep it local-only (ninja mode)?" with the trade-offs described inline. Default to tracked (current behavior).
    - **`--ninja-mode` flag**: non-interactive opt-in for scripting (`canon init --ninja-mode`). Mirrors the prompt's "local-only" answer.
    - **`--no-ninja-mode` flag**: explicit opt-out for the prompt-suppressed case (e.g. `CI=true`).
    - On "local-only", append a canon-delimited block to `.git/info/exclude` (creating the file if missing) with the pattern above. Use the same `<!-- canon:start --><!-- canon:end -->` delimiters as the existing `mergeDelimited` for upgrade safety.
    - On `canon upgrade` re-run that delimited block so adopters who add new canon-managed files later get the updated exclusion list automatically.
    - Persist the ninja preference in `.canon/version`'s sibling metadata (or a new `.canon/config.json`) so `canon doctor` can detect "ninja mode is active but somehow canon files are tracked" drift.
  - **Edge cases to handle**:
    - **Pre-existing collisions are the hard part — the all-or-nothing block above is a sledgehammer**: an adopter repo might already have its own `AGENTS.md`, `CLAUDE.md`, `CODEX.md`, `docs/`, or even `.claude/` settings from an existing Claude Code setup. The naive exclude rule (a) hides canon's overwrite of those files in `git status`, so adopters can't see when canon has touched them; (b) interacts confusingly with `canon upgrade`'s dirty-managed-file refusal from #63 — the dirty file is invisible but the refusal still fires. Two plausible paths: **(i) collision detection at init time** — diff each canon-managed path against the adopter's existing version, list collisions, ask per-file whether to overwrite + exclude or skip; **(ii) scoped exclude pattern** that only hides paths canon actually wrote, tracked in a manifest like `.canon/owned-files.txt`. Path (ii) is more work but produces no surprises. Either way, the all-or-nothing block in the prompt above is the v1 simple-case shape; the collision-handling design needs its own round of grilling before any of this lands.
    - **Existing `docs/` tracked in adopter repo**: subset of the collision case above — the exclude rule only hides *new* untracked files in `docs/`, but operators might be confused when their existing tracked files keep showing up while canon's don't.
    - **`.git/info/exclude` already has user-authored lines**: never overwrite — append the delimited block at the end.
    - **Multi-clone case**: `.git/info/exclude` is per-clone, not per-machine. Fresh clones of the same repo need re-init. Mention this in the prompt's trade-offs section.
    - **`canon upgrade` semantics**: ninja-mode adopters running `canon upgrade` should still get the canon-managed files updated on disk; the existing dirty-tree refusal logic from #63 already handles "canon-managed file was modified by the operator" gracefully.
    - **`CANON_PR_BODY` pairing**: `canon init --ninja-mode` should also print a hint suggesting the operator set `CANON_PR_BODY=""` (or leave it unset — the 1.3.0 default already produces neutral PR bodies). The two halves of ninja mode are independent but commonly used together.
  - **What's NOT in scope**:
    - Migrating already-tracked canon files to local-only (`git rm --cached` flow). Adopters who switch mid-stream can do that by hand.
    - Per-file granularity (e.g. "track `docs/decisions.md` but not `tasks/`"). Start with the all-or-nothing block; add granularity only if real adopters ask for it.
    - A `canon doctor --fix` mode that retroactively applies the exclude block. Detection is fine; auto-applying without an `init` re-run is too invasive.
  - **Effort**: `S` — most of the surface is one prompt + one `mergeDelimited` write to `.git/info/exclude`. The detection-on-upgrade path adds maybe ~30 lines.

- [ ] **Manual / off-pipeline canon mode with post-hoc independent review** *(filed by James, issue #85, 2026-05-19)*
  - **Scope**: An explicit `execution_mode: "manual_canon"` (or similar) recorded on a task's `status.json` for the case where a user asks an agent to run a long Canon-shaped workflow directly — producing specs/plans/reviews/implementation artifacts without the orchestrator owning every phase transition. Useful in messy real projects and probably unavoidable, but blurs canon's normal guarantees unless the task state records that an operator substitution happened.
  - **What the canonical flow guarantees that manual mode breaks**: Claude writes specs/plans/reviews/QA, Codex reviews specs and implements, no agent reviews its own work, orchestrator owns phase routing and artifact gates. Manual end-to-end runs may produce canon-shaped artifacts and even run useful checks, but downstream readers can over-trust them as if all phase ownership and cross-review gates held.
  - **Proposed status.json shape**:
    ```json
    {
      "execution_mode": "manual_canon",
      "operator_substitution": {
        "agent": "claude|codex|human",
        "reason": "long-running bundle / emergency CAPA / external constraints",
        "requires_post_hoc_independent_review": true
      }
    }
    ```
  - **Behavior**:
    - `canon task list/status` displays `manual_canon` visibly.
    - `canon run` refuses to advance to `qa`/`human_review` until an independent post-hoc review artifact exists (different agent than the one who wrote the manual artifacts).
    - `done.md` / handoff templates carry a short disclosure when manual mode was used.
    - `canon doctor --tasks` warns if a manual-mode task lacks the required independent review.
  - **Why it matters**: keeps canon pragmatic without weakening guarantees. Manual end-to-end runs stay supported, but the task record honestly distinguishes orchestrator-owned vs. canon-shaped manual runs that still need independent review before being treated as done.
  - **Risks to watch**: scope creep into a parallel pipeline. The mode should be a flag and a few gates, not a rebuild of the orchestrator. Also: the "independent post-hoc review" needs a concrete mechanism — likely a new artifact `independent-review.md` plus a phase gate that requires it, signed by a different agent slot than the one named in `operator_substitution.agent`.

- [~] **`docs-refs-check`: treat backtick refs to current-diff deletions as resolved, not broken** *(framed 2026-06-01 from retire-codex-md's code_review round-1 catch-22; lesson logged in `docs/lessons-learned.md`. **Parked 2026-06-01 — decided NOT to build:** the fix needs a `--base-ref` CLI flag + a CI base-fetch + a git diff, disproportionate to a cosmetic papercut with a working workaround. Documented the convention instead — deleted-file refs never use backticks; the parsed `handoff.md` Changes-table cell requires the `[path](path)` markdown-link form, while free prose in `review.md` / `done.md` may use markdown-link or bare text (see `.canon/templates/handoff.md` Changes-table note + `AGENTS.md` §artifact refs). This entry stays as the design-of-record; revisit only if the convention proves insufficient.)*
  - **Problem**: A file-deletion task hits a tooling catch-22. (1) The orchestrator's diff→handoff reconciliation requires **every** file in `git diff <base>...HEAD` — including deletions — to appear in the handoff Changes table with a backtick-path or markdown-link first column (`parseHandoffPathCell` in `src/orchestrator/validation.ts`). (2) `docs-refs-check` flags a backtick file-path ref to a non-existent file as broken, and `handoff.md` is **not** in its exempt set. So when a task deletes a file under a `validDir` (e.g. `templates/CODEX.md` — `templates` is a valid dir via the adopter config `scripts/docs-refs-config.mjs`), the *mandatory* handoff entry trips `docs-refs-check`, failing the "docs-refs passes" AC and the CI job. Asymmetry that hides it: a bare top-level ref like `` `CODEX.md` `` escapes (a top-level filename isn't a `validDirs` prefix), so only deletions *under a valid dir* bite — easy to miss until a task deletes one.
  - **Interim workaround (used by retire-codex-md)**: list the deleted file with the markdown-link cell form `[path](path)` instead of a backtick path. `parseHandoffPathCell` reads the path from the link label (satisfies the orchestrator), while `docs-refs-check`'s anchor-link validator only fires on links containing `#`, so a plain `[path](path)` isn't validated as a file ref. Works, but every file-deletion task must remember this hand-authored special case (hence the `lessons-learned` entry).
  - **Candidate design**: teach `docs-refs-check` to skip a backtick file-path ref whose target is a `D`-status path in the current `git diff <base>...HEAD`. Compute the deletion set once at startup (mirror the batched `git check-ignore --stdin -z` pattern already in the script), and in the class-1 backtick-path validator treat a ref to a current-diff deletion as resolved-but-deleted rather than missing. Fixes the conflict generally for any deletion-under-`validDir` task and lets the handoff keep its mandatory entry in normal backtick syntax. Add a focused test (delete a file under a validDir, ref it in a scanned doc, assert no finding).
  - **Scope / not-in-scope**: suppress only for deletions in the *current* diff — a ref to a file deleted in some unrelated past commit should still flag. The markdown-link path keeps working unchanged. No adopter-config change needed.
  - **Why it may wait**: the markdown-link workaround is cheap and now documented; this only bites tasks that delete committed files under a valid dir (rare). Pick up the next time a deletion task hits the papercut, or bundle with other `docs-refs-check` work.
  - **Effort**: `S`. Deletion-set lookup + one guard in the class-1 validator + a test (~30-40 lines).
